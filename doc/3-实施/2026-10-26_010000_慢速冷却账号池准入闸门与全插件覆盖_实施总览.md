# 慢速冷却账号池准入闸门与全插件覆盖 实施总览

- 时间：2026-10-26 (GMT+8)
- 对应需求：`doc/2-需求/2026-10-25_235000_慢速冷却账号池准入闸门与全插件覆盖需求.md`
- 状态：已实现，待发布

## 1. 方案要点

用户要求「账号大于 20（启用+停用）才触发」，避免池子不足时 P25 基线退化造成误判。
本轮的三个关键设计决策：

### 1.1 闸门放在打点之前，不只在判定里

`noteSlowObservation` 是唯一打点入口（每次成功请求调用）。如果只在
`evaluateSlowAccount` 里拦，账号不足时样本照记，池子涨到 21 个的瞬间会拿着
一整批陈旧样本立刻判一轮——等于用不成立的历史数据误判账号。
因此在 `noteSlowObservation` 就 `return`，两条路径都不进入。

### 1.2 账号总数用周期缓存，不进热路径

账号枚举唯一可靠来源是宿主 RPC `host.auth.list`（返回全部账号含 `Disabled`）。
但 `noteSlowObservation` 挂在每次成功请求的成功路径上，同步调 RPC 会把
跨进程往返成本加到每个请求上。

**方案**：独立 ticker（`slowPoolSizeLoop`，10 分钟）刷新 `slowPoolSize` 缓存，
判定入口只读内存变量。

- 探测失败**保留上一次已知值**：RPC 偶发失败不该让闸门忽开忽关。
- 首轮**立即探测**，不留 10 分钟盲区。
- 缓存零值（从未探测成功）**一律视为不达标**：宁可晚一个周期生效，也不能在
  未知规模下用退化基准误判。

### 1.3 计数含停用账号

用户明确要求「启用+停用」。停用多是临时的（额度耗尽、探活中），池子真实规模
应按账号归属算；若只数可路由账号，一次批量临时禁用就会让机制忽开忽关。

## 2. 各插件实现差异

| 插件 | 账号枚举 | 判定入口 | 路由拦截点 | 备注 |
| --- | --- | --- | --- | --- |
| workbuddy | `hostAuthList()` | `noteSlowObservation` / `evaluateSlowAccount` | 四处 | 模板实现 |
| traework | `hostAuthList()` | 同上 | 四处 | `setLoadedSlowConfig` 加参 |
| qoderwork | `hostAuthList()` | 同上 | `pickNextAuth` 变参 | 行解析配置 |
| zcode | 新增 `countHostAuthFiles()` | 同上 | `accountRoutable` 单点 | 只数文件名，不逐号拉凭据 |
| workbuddy-ai | `hostAuthList()` | 同上 | `accountRoutable` 变参 + 调度直连 | 本轮新增机制 |
| qoder-ai | `hostAuthList()` | 同上 | `accountRoutable` 变参 + 调度直连 | 本轮新增机制 |
| qwenwork | `hostAuthList()` | 同上 | `accountRoutable` 变参 + 调度直连 | 本轮新增机制 |

**zcode 的特殊处理**：`listHostAuthFiles()` 会逐个拉取凭据 JSON。闸门每 10 分钟
刷新一次且只需要数量，逐号拉取会让一次刷新变成 N 次跨进程 RPC。故新增
`countHostAuthFiles()`，只按文件名前缀计数。

## 3. 新移植三插件的前置改造

### 3.1 per-attempt TTFT 计时隔离（阻断项）

三者原本都是 `ttftNS(started)` 用请求级时间戳。补 `collector.attemptStarted` +
`markAttemptStart`：

- 异步流：新建 collector 时打点一次。
- 同步 collect：collector 由调用方跨 attempt 复用，**每轮循环内重设**，否则上一轮
  失败耗时累积进本轮。

### 3.2 非流式 TTFT 恒为 0（真实缺陷）

三者非流式路径 `publishUsage(..., 0)` 恒传 0，慢速冷却完全没有样本可判。
逐插件改造：

| 插件 | 非流式函数 | 聚合函数 |
| --- | --- | --- |
| workbuddy-ai | `doExecuteOnce` → 返回 `uint64` | `aggregateCompletion`（已有 firstByteAt） |
| qoder-ai | `doExecuteOnceQoder` → 返回 `uint64` | `aggregateQoderSSE` → `aggregateCompletion` |
| qwenwork | `doExecuteOnceQwenWork` → 返回 `uint64` | `aggregateOpenAISSE` / `aggregateQoderSSE` → `aggregateCompletion` |

打点位置：**首个可解析分片**到达时（不是读完正文），语义与流式的「首字」一致。

### 3.3 路由接入

- `accountRoutable(authID string, model ...string)`：变参避免改动 6~7 处调用点。
- 调度函数 `handleSchedulerPick` 里另有候选过滤循环，直接用 `req.Model` 归一化后判断。

## 4. 验证

### 4.1 测试

七插件全部 `cgo-shim build + vet + test` 全绿：

```
workbuddy / workbuddy-ai / traework / qoderwork / qoder-ai / qwenwork / zcode
```

新增用例（每插件）：

- `TestSlowAccount_PoolSizeGateBlocksJudgement`：20 不判 / 21 放行
- `TestSlowAccount_PoolSizeGateSkipsSampling`：闸门在打点前
- `TestSlowAccount_PoolSizeUnknownStaysClosed`：未探测保守关闭
- `TestSlowAccount_PoolSizeGateConfigurable`：阈值可配置
- `TestTTFTNS_UsesAttemptBase` 等 3 个：per-attempt 计时隔离

### 4.2 变异验证

| 变异 | 结果 |
| --- | --- |
| 闸门恒放行（`return true`） | KILLED（3 个用例同时捕获，七插件） |
| 闸门只拦判定不拦打点 | KILLED（`PoolSizeGateSkipsSampling` 精确命中） |
| `>` 改 `>=`（20 也放行） | KILLED（边界用例捕获） |
| per-attempt 退回请求级基准 | KILLED（`TTFTNS_UsesAttemptBase`） |

## 5. 生产影响

加闸门后按 2026-10-25 实测池规模，**只有 workbuddy（37 个）会继续运行慢速冷却**：

| 插件 | 账号总数 | 闸门后 |
| --- | --- | --- |
| workbuddy | 37 | 生效 |
| qoderwork | 18 | 休眠 |
| coze | 17 | 休眠（且无机制） |
| traework | 16 | 休眠 |
| workbuddy-ai | 2 | 休眠 |
| zcode | 1 | 休眠 |
| qoder-ai / qwenwork / copilot / cursor | 0 或未启用 | 休眠 |

这正是用户意图：机制在位、按池子规模自动上下线，不会因账号不足产生噪音。

## 6. 未做项（用户裁定）

coze / copilot / cursor **三者都不做**。补齐前置条件（TTFT 采集、统一路由判定函数）
的工作量远大于移植状态机本身，且生产均未启用或无池子。缺口已记录在需求文档 6.3 节。
