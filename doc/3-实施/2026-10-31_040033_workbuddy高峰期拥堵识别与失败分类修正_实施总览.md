## 0. 当前计划最终方案的简要说明

不在面板上「显示拥堵状态」，而是**修正拥堵被误判为账号故障的处置链路**：新增 `failureScopeUpstreamBusy`（渠道满载，不罚号不换号）与 `failureScopeModelRateLimit`（模型级限流，只隔离账号×模型不禁用账号）两个分类维度，让 `classifyUpstreamFailure` 先于通用限流识别 6021/6004；同时给写盘禁用加连续失败门限（默认 3 次、只作用于瞬时类失败），并补齐顶层业务码帧识别、5xx 同请求换号、探活兜底模型三处断点。

选这条路的原因：用户真正的问题是「高峰期几乎不可用」，而不可用的放大器是「一次失败即禁用 → 池子缩小 → 压力转移 → 更多拥堵」这条雪崩链，不是缺一个状态字段。只做 UI 展示不能让任何一次请求更容易成功。

## 1. 问题与目标

见需求文档第 2 节。核心是四条缺陷 D1–D4 串成的雪崩链：

```
拥堵（6004/6021/5xx）
  ├─ D1 顶层码帧未识别 → 拥堵帧被当正文透传，不记账
  ├─ D2 5xx 不换号 → 用户承受第一跳失败
  └─ D3 一次失败即写盘禁用 → 池子缩小 + 会话亲和打散
        └─ D4 探活标记缺失 → 被禁号永久失联（2026-10-29 实证 8 小时）
              └─ 剩余账号压力上升 → 更多拥堵（回到起点）
```

## 7. 阶段计划与最小任务

### TASK-001 顶层业务码帧识别

- 落点：`workbuddy/stream.go:951` `sseErrorFrame`、`workbuddy/stream.go:997` `topLevelCodeText`
- 动作：无 `error` 包裹时取顶层 `code`；为 `""` 或 `"0"` 返回空；`float64` 去小数尾巴（否则 `6004` 变 `"6004.0"` 导致后续匹配全落空）；拼 `code + ": " + message`。
- 完成条件：6 个用例（数字码 / 字符串码 / 码 0 / 无码 / 有 message / 无 message）全绿。

### TASK-002 拥堵失败分类

- 落点：`workbuddy/failure_class.go:72/80/158/192/209/231`
- 动作：新增两个维度与派生判据；`classifyUpstreamFailure` 判定顺序改为 硬额度/账号级 4xx → **6021** → **6004** → 5xx/传输 → 11128 → 限流文案 → none。
- 关键约束：6021 必须早于通用限流与 5xx 判定（它常以 429/5xx 承载）；6004 同理。
- 完成条件：10 个表驱动边界用例 + 记账/禁用矩阵用例全绿。

### TASK-003 拥堵免罚

- 落点：`workbuddy/accountFailover.go:388`、`workbuddy/accountFailover.go:246`、`workbuddy/stream.go:194`
- 动作：`recordCooldownScoped` 入口改 `scope.recordsCooldown()`（拥堵维度返回 false，既不冷却也不禁用）；5xx 纳入同请求换号（`shouldRotateOnStatus`）；6021 显式排除换号并追加 `upstreamBusyHint`。
- 完成条件：拥堵不写冷却、不禁用、不换号三件事各有独立断言。

### TASK-004 写盘禁用门限 + 探活兜底

- 落点：`workbuddy/accountFailover.go:59/125/138/415`、`workbuddy/failover_disable.go:629/690/703`、`workbuddy/usage_config.go:144`、`workbuddy/main.go`
- 动作：
  1. 连续失败门限默认 3，配置项 `failover_disable_min_count`（填 1 恢复旧行为）；
  2. **门限只作用于瞬时类失败**——`isTransientUpstreamFailure` 判为确定性的（401/403/404/405、402 额度、11128 拦截）跳过门限直接禁用；
  3. 探活标记缺失时回落 `failoverStateSnapshotModel` → `failoverProbeFallbackModel`，消除永久失联死角。
- 完成条件：门限 3/1 两档、模型级限流即使达门限也不禁用、探活兜底成功/失败两侧用例全绿。

## 9. 实施中的自我修正（如实记录）

初版把门限无差别作用于所有失败，直接打破 5 个既有测试（`TestModelBlockedDualWritesCooldownAndDisable`、`TestProbeSuccessClearsBothCooldownAndDisable`、`TestProbeFailureKeepsAccountDisabled`、`TestAccountLevelFailureDualWritesCooldownAndDisable`、`TestRunFailoverProbeWithoutFailedModelSkips`）。

审查结论是**设计缺陷而非测试过时**：401/403 凭据问题与 11128 模型拦截是确定性故障，在同一个号上必然重演，让用户多失败两次没有任何收益。修正为新增 `isTransientUpstreamFailure` + `recordFailureScopedWithCause` 透传 status/body，门限只作用于瞬时类。

另：`TestRunFailoverProbeWithoutFailedModelSkips` 原本断言的正是 2026-10-29 事故的根因机制（无模型即跳过），已改写为新语义（兜底回放）并补失败侧用例——这条测试在修复前是在**固化缺陷**。
