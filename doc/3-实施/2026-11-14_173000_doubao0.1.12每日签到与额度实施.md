# doubao-provider 0.1.12 每日签到与活动赠送额度实施

- 日期：2026-11-14
- 状态：已实施（代码 + 面板 + 测试全绿）
- 来源需求：`doc/2-需求/2026-11-14_170000_doubao每日签到与免费额度调研.md`
- 实施范围：档 1（只读签到状态与免费额度）+ 档 2（`chosen_type=0` 条件下的单次真实签到）
- 目标版本：`doubao-provider` 0.1.11 → **0.1.12**

## 1. 当前方案的简要说明

在 `doubao` 插件内新增签到与额度能力：面板新增「今日签到与免费额度」区块与「今日签到」按钮；后端新增两个只读/写一次的管理路由 `/checkin/status` 与 `/checkin/run`；每日 `10:00` 与 `22:00` 各跑一轮自动签到。真正的写请求被 `chosen_type` 渠道闸门与「已签即跳过」双重前置挡住，单账号每日最多一次提交，失败即停。

主落点是新建的 `doubao/checkin.go`（接口调用、状态判定、额度递归提取、定时器），`protocol.go` / `models.go` / `completion.go` 零改动——19 键网页端 query、`endpointURL`、`SamanthaDoubao` UA、`postBusinessJSON` 全部现成可复用。

## 2. 问题与目标

- **问题**：豆包「免费用豆包工作」活动每日可领 200 活动额度（周一翻倍、30 天累计上限 8800），但插件此前完全没有签到能力（`doubao/` 下 grep `checkin|签到|campaign|quota` 零命中），只能靠用户手工点。
- **目标**：让面板能看见每个账号今日的签到状态与活动赠送额度，并在平台允许的渠道上自动完成签到；平台改投桌面端的账号如实上报而不做无效写请求。
- **本轮范围**：签到状态查询、活动赠送额度查询、条件签到、手动触发、每日两轮定时、面板展示。
- **非范围**：桌面端 CDP 自动点击（档 3，插件跑在无桌面的 Linux 容器内不可行）、任务奖励自动领取、`a_bogus` / `biz_params` / `AgwCommonParam` 等风控字段伪造。

## 3. 关键假设与依据

| 假设 | 依据 |
|---|---|
| 签到成功判据只能是详情回查的 `daily_checkin.checked_in_today=true` | 生产账号1 已签回执为 `idempotent:true`，单看 `code=0` 分不清「刚签成功」与「早已签过」 |
| `chosen_type=0` 才可网页签到，`=3` 必然 `710010702` | 生产两账号对照 + 8 种参数变体全部失败，`landing_cards` 文案为「前往豆包桌面端即可领取」 |
| `daily_signin` 只在 web 形态下发 | 同账号客户端形态详情 `tasks` 仅 5 条且不含 `daily_signin`，web 形态 7 条含它 |
| 活动组标识可从详情请求直接固定为 `pc_incentive_task_mvp_v3` | `launch` 的 `ug_campaign_info.campaign_group_code` 两账号一致；`ug_campaign` 为空串不可用 |
| 裸 HTTP 单次请求不会必然污染 session | 账号1 裸 HTTP 拿到正常幂等回执；`hiclaw` 笔记的「反复裸请求致受限」边界被本轮实测收窄 |

## 7. 任务完成条件

1. `python scripts/cgo-shim-build.py doubao` 输出 `all green (doubao)`。
2. `gofmt -l` 对 `checkin.go` / `checkin_test.go` / `main.go` / `management.go` 无输出。
3. `panel.html` 两个 `<script>` 块 `node --check` 通过，`renderCheckin` 运行时冒烟全部断言为真。
4. 生产热重载后 `GET /plugins/doubao-provider/checkin/status` 返回 200 且 `accounts` 非空。
5. 生产 `POST /plugins/doubao-provider/checkin/run` 对已签账号返回 `state=done`，对 `chosen_type=3` 账号返回 `state=desktop_only` 且无写请求。
6. 生产 12 个账号的 `GET /checkin/status` 状态与上游真实渠道一致：`chosen_type=0` 的账号出 `done` 或 `ready`，`chosen_type=3` 的账号出 `desktop_only`，不得出现「活动已下线」误判。

## 8. 任务停止 / 结束条件

- 上述 5 条全部有真实证据 → 任务完成。
