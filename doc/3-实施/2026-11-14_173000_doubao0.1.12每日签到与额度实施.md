# doubao-provider 0.1.12 每日签到与活动赠送额度实施

- 日期：2026-11-14
- 状态：已实施（代码 + 面板 + 测试全绿）
- 来源需求：`doc/2-需求/2026-11-14_170000_doubao每日签到与免费额度调研.md`
- 实施范围：档 1（只读签到状态与免费额度）+ 档 2（`chosen_type=0` 条件下的单次真实签到）
- 目标版本：`doubao-provider` 0.1.11 → **0.1.12**

## 1. 当前方案的简要说明

在 `doubao` 插件内新增签到与额度能力：面板新增「今日签到与免费额度」区块与「今日签到」按钮；后端新增两个只读/写一次的管理路由 `/checkin/status` 与 `/checkin/run`；每日 `10:00` 与 `22:00` 各跑一轮自动签到。真正的写请求被 `chosen_type` 渠道闸门与「已签即跳过」双重前置挡住，单账号每日最多一次提交，失败即停。

主落点是新建的 `doubao/checkin.go`（接口调用、状态判定、额度递归提取、定时器），`protocol.go` / `models.go` / `completion.go` 零改动——19 键网页端 query、`endpointURL`、`SamanthaDoubao` UA、`postBusinessJSON` 全部现成可复用。

## 2. 问题与目标

- **问题**：豆包「免费用豆包工作」活动每日可领 200 活动额度（周一翻倍、30 天累计上限 8800），但插件此前完全没有签到能力（`doubao/` 下 grep `checkin|签到|campaign|quota` 零命中），只能靠用户手工点。
- **目标**：让面板能看见每个账号今日的签到状态与活动赠送额度，并在平台允许的渠道上自动完成签到；平台改投桌面端的账号如实上报而不做无效写请求。
- **本轮范围**：签到状态查询、活动赠送额度查询、条件签到、手动触发、每日两轮定时、面板展示。
- **非范围**：桌面端 CDP 自动点击（档 3，插件跑在无桌面的 Linux 容器内不可行）、任务奖励自动领取、`a_bogus` / `biz_params` / `AgwCommonParam` 等风控字段伪造。

## 3. 关键假设与依据

| 假设 | 依据 |
|---|---|
| 签到成功判据只能是详情回查的 `daily_checkin.checked_in_today=true` | 生产账号1 已签回执为 `idempotent:true`，单看 `code=0` 分不清「刚签成功」与「早已签过」 |
| `chosen_type=0` 才可网页签到，`=3` 必然 `710010702` | 生产两账号对照 + 8 种参数变体全部失败，`landing_cards` 文案为「前往豆包桌面端即可领取」 |
| `daily_signin` 只在 web 形态下发 | 同账号客户端形态详情 `tasks` 仅 5 条且不含 `daily_signin`，web 形态 7 条含它 |
| 活动组标识可从详情请求直接固定为 `pc_incentive_task_mvp_v3` | `launch` 的 `ug_campaign_info.campaign_group_code` 两账号一致；`ug_campaign` 为空串不可用 |
| 裸 HTTP 单次请求不会必然污染 session | 账号1 裸 HTTP 拿到正常幂等回执；`hiclaw` 笔记的「反复裸请求致受限」边界被本轮实测收窄 |

26. `doubao/web` 必须在宿主模型目录、面板测试下拉、活跃测试严格校验三处同时可见，且不得把其它模型的 `WorkMode` 带走（0.1.22）。

- 0.1.16 生产验证（2026-11-15 01:35）只证明了「插件侧签名被上游接受」（同一 body 带签名 → `ack=True` 落账号级分支，去掉签名 → `710022002`），**尚未观察到补 `ms_token` 后成功出字**：12 个账号此刻同时处于 `-1` / `semantic_reasoning` / `710022002` 三种上游风控分支中。待风控解除后，用一次真实书签授权补齐 `ms_token` 并复跑 `test-active`，才能收口「端到端可用」这一条。
- 0.1.17 修复的是「拿到 msToken 却写不进去」这一类落盘缺陷，不改变 msToken 的采集方式：仍需用户浏览器侧点一次授权书签。修复后生产日志应出现 `[doubao] ms_token saved for <auth_id> (len=…, path=/usr/local/src/cli-proxy-api/auths/…)`；若仍出现 `ms_token missing`，说明授权脚本未回传，需检查书签版本而非落盘链路。
- 0.1.18 修复的是授权链路自身的传输层配置，不改变任何请求内容与判据逻辑：判据 GET 在传输层失败时最多重试 3 次，令牌兑换 POST 只在「请求未送出」时重试。修复后若仍出现 `net/http: TLS handshake timeout`，说明抖动超过 20s 或落在重试窗口之外；该阈值是 `doubao/transport.go` 里的常量 `upstreamTLSHandshakeTimeout`，无运行期配置项，需改代码重新发版才能上调——不要回退本次改动。
- 0.1.18 的 `requestNeverSent` 依赖 transport 的固定错误文本 `TLS handshake timeout` 判定「请求未送出」；Go 版本升级若改动该文案，令牌重试会退化为「永不重试」（保守方向，不会重复消费令牌），需在依赖升级时同步核对。
- 出站 Cookie 过滤是「按域名硬编码黑名单」的实现，若上游改判据（换名或换端点）需同步调整 `blockedHostCookieNames` 与 `siteHostname`。
- 替代会话 Cookie 目前只认 `ttwid`；若站点改为下发别的名字，预热会「成功但补不上」，表现为静默空响应（0.16s、零事件），排查时先看这一点。
- 0.1.20 只改文案与注释，不改变任何请求行为：`710022004` 依然会触发 `isRateLimit` 的账号冷却换号。若后续希望「遇到验证码就暂停整池而不是逐个换号」，需要单独评估——逐个换号会让每个账号都被弹一次验证码，反而扩大影响面。
- 验证码能否程序化提交未评估：`rmc.bytedance.com` 的 verify 提交端点可能有签名与设备指纹校验，且实测有时限（第二轮拖拽即「验证超时」）。若上游后续把验证码换成滑块或点选，人工引导文案需同步更新。
- 0.1.20 关于「`710022004` 是人工语义选图验证码」的定性已作废：那次验证码是「全新 Chrome profile + 注入账号 Cookie」自造的假象（新 profile 指纹与账号未绑定），用户日常 profile 从不弹。以 0.1.21 的「fp 必须真实」为准。
- 0.1.21 要求用户重新授权一次才能补上 `s_v_web_id`；12 个账号里 11 个仍 `sign=missing`，逐个重新点书签是恢复整池的必经运维动作。面板上暂时看不到 fp 采集状态（`signStateOf` 只判 `ms_token`），如需在卡片上显示需单独评估。
- 「假 `device_id` + 真 `fp` 能出字」只是当前观测；上游若改为强绑定 `device_id`，还需把 `device_id` / `web_id` / `tea_uuid` 一并改成采集真实值。届时 `deviceIDFor` 的派生逻辑要整体废弃，`TestDeviceIDForIsStable` 需重写。
- `s_v_web_id` 是 52 字符的普通 Cookie（非 HttpOnly），值含 `%7C` 等 URL 转义；采集脚本要用 `decodeURIComponent` 还原，否则拼进 query 会被二次编码。
