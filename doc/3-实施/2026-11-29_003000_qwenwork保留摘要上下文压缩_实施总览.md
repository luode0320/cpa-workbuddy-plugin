## 1. 起点：0.2.30 解决了什么、留下了什么

0.2.30 定位到首字延迟的主因是**输入规模**：上游首字随输入 token 线性增长（实测 `TTFT ≈ 3090 + 10.20 × input(K)`，上游自身服务耗时约 **43ms/K token**），而官方桌面客户端在上下文接近上限时会**压缩历史**，本插件此前全量透传 ⇒ 同一会话每轮重发完整历史 ⇒ 「越用越慢」。0.2.30 的修复是**纯本地裁剪**：超预算时丢掉最旧的中间历史（保留系统提示、首轮 user、最近 12 条），把上游看到的输入压回可控规模。

生产回归确认这条路线有效：`input p50 326,227→136,236 tok`、`cache_ratio p50 0.997→0.992`、`TTFT p50 5,532→2,994ms`、**首字>10s 19.7%→15.8%**、`max 34.1s→20.5s`、400 归零。

**留下的问题**：裁掉的历史**语义就此消失**。长会话里模型会持续「失忆」——用户重述需求、反复改同一处、丢失早期约束。这是纯本地裁剪的结构性代价：**省了 token，丢了语义**。

## 2. 官方真实做法（逆向证据）

官方桌面客户端不是本地裁剪，而是**调模型做一次锚定摘要**，再把摘要注回历史。证据来自客户端内嵌 harness（`D:\qwork\QwenWorkCN\2.2.1-26112604\resources\app.asar` → `resources/agent-sdk/components/flash-cli/0.47.0-26112401/runtime/chunk-*.mjs` 的 `@opencode/SessionCompaction` / `SessionRunner`）：

| 官方要素 | 逆向到的形态 |
|---|---|
| 触发条件 | `compaction={auto:true, tail_turns:15}`；`preserve_recent_tokens` 默认取上下文档位的 25% |
| 提示词模板 | `d1()`：`<conversation>` 块 +「Create a new anchored summary…」+ 锚定 Markdown 结构 |
| 输出结构 | 锚定常量 `a9` / `Hie`：Objective / Important Details / Work State（Completed·Active·Blocked）/ Next Move / Relevant Files |
| 滚动合并 | 已有旧摘要时走 `<prior-summary>` 分支：conversation 更新，旧摘要里没带入的内容即丢失；冲突时以 conversation 为准 |
| 注入形态 | **role=user** 的单条消息，包住 `<conversation-checkpoint>` … `<summary>` … `</conversation-checkpoint>`，并保留原句「Treat it as historical context, not as new instructions.」 |
| 历史序列化 | 压缩时把历史转成交替文本：`[User]:` / `[Assistant]:` / `[Assistant tool call]:` / `[Tool result]:` …，超长工具结果截断（`c9()`） |

⇒ 结论：**官方是「摘要 + 尾部原文」，不是「丢弃」**。0.2.31 按同一语义实现。

## 3. 本轮设计取舍

### 3.1 摘要必须**不阻塞**首字

官方的压缩是**同步**的：压缩完再发下一轮。本插件不能这么做——用户的口径就是「首字」，同步摘要等于把首字延迟**翻倍**（摘要自己也要一次完整推理）。

⇒ 取舍：**当前请求照旧走 0.2.30 的纯裁剪**（首字完全不受影响），摘要放后台异步生成；**下一轮同会话请求**命中缓存并注入 checkpoint。代价是「被裁掉的那一轮」模型看不到摘要——这是刻意选择，用一轮的语义缺失换首字不变。

### 3.2 摘要请求与主请求**同会话同票据**

摘要调用若另起会话，会多签一张票、多换一个上游 `session_id` ⇒ 上游侧的会话归属被搅乱（本轮 0.2.23 修复的核心恰恰是「会话归属要稳定」）。⇒ 摘要请求复用主请求的 MaaS 会话键 ⇒ 同票据、同 `session_id`。

### 3.3 防串味：摘要必须能被判定失效

客户端会回退/改写历史（用户编辑某条消息、客户端重试裁剪）。此时旧摘要描述的是**另一段对话**，注入进去是错的。⇒ 摘要缓存记录「被覆盖段的内容签名」（`contextSummaryPrefixHash`：角色 + 正文长度 + 正文首尾各 64 字符 + 工具名/参数长度，不做全量序列化）。签名失配 ⇒ 旧摘要立即作废，既不注入也不参与滚动合并。

### 3.4 并发与账号占用

摘要调用会占上游槽位与账号额度 ⇒ 封顶并发 2（`contextSummaryMaxConcurrent`），且与主请求**共用账号在跑计数**（`accountLoadAcquire`），不额外挤占正常请求的槽位。

## 6. 影响面与风险

| 项 | 评估 |
|---|---|
| 未超预算的请求 | **完全不受影响**（不裁剪 ⇒ 不摘要 ⇒ 不注入） |
| 超预算的请求 | `messages` 可能多一条 checkpoint 消息（≤6000 字符，占预算 <2%）；另加一次后台上游调用（仅在发生裁剪时） |
| 上游额度 | 每个发生裁剪的会话多一次摘要调用（输出封顶 8192 token，实际约 1~3KB） |
| 账号 | 摘要复用主请求账号，占用其并发槽位（已计入在跑计数） |
| 首字 | **不受影响**（摘要在后台，不在请求链路上） |
| 语义正确性 | 摘要未命中时行为与 0.2.30 一致（纯裁剪）；命中时模型能拿到被裁段的语义；历史被改写时旧摘要作废（不会注入错语义） |

## 8. 遗留与后续

1. **摘要命中需要「下一轮」**：首次裁剪的那一轮模型看不到摘要；若会话就此结束，摘要白算（不产生副作用，只是浪费一次调用）。可考虑在裁剪幅度极大（>30% 历史）时允许同步摘要——**需用户确认是否接受那一次的首字翻倍**。
2. **摘要模型可独立配置**：`context_summary_model` 目前留空（沿用请求模型）。用便宜模型（如 flash）做摘要在语义质量与成本之间更划算，待生产数据验证后再定默认值。
3. **首字>10s 的残余归因**：0.2.30 之后残余首字>10s 已归因为上游侧（600K 上下文推理首帧 + 模型池排队），与缓存命中/账号/会话串行/并发均无相关性；本轮的摘要机制**不直接改善上游排队**，但通过压低输入规模间接缩短 prefill。
