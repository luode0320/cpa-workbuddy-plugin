# workbuddy 禁用状态经 CPA 管理接口同步_实施总览

- 日期：2026-10-28
- 对应需求：`doc/2-需求/2026-10-28_150000_workbuddy禁用状态经CPA管理接口同步.md`
- 实施对象：`workbuddy-provider`
- 生产目标：**新机 155.103.157.254**（alias `cpa-server-new`，容器 `cli-proxy-api`，宿主 127.0.0.1:8317）

## 0. 当前计划最终方案的简要说明

新增 `cpa_disable_sync.go`，把「插件判定禁用/恢复」这件事的**权威落点**从「直写物理文件」改为「调用宿主 `PATCH /v0/management/auth-files/status`」，物理写盘降级为失败兜底；宿主管控地址与密钥来自新增配置项 `cpa_management_url`（默认 `http://127.0.0.1:8317`）与 `cpa_management_key`（config_yaml 优先、env `WB_CPA_MANAGEMENT_KEY` 兜底）。归属判断继续只靠 sidecar，API 只负责把 `disabled` 写进宿主真相源（MySQL）。

选这条路的原因：宿主判状态与路由只认 `AuthData.Disabled`（MySQL 持久化），插件直写 disk mirror 的 `disabled` 会被下一次宿主 persist 覆盖，这是旧机实测出的结构性缺陷；而 `PATCH /auth-files/status` 是宿主认证文件管理页 toggle 的同一条链路（`applyAuthDisabledState` + `authManager.Update` → `persist` → MySQL），是唯一能真正改写路由真相源的通道。

## 1. 问题与目标

- **问题**：三类禁用（failover / low_credit / exhausted）都只写物理文件，宿主 MySQL 存储下 `disabled` 会被覆盖回 false，宿主选择器继续把这些号发给插件 → 双源分叉、探活在坏号上做无效 429 循环。
- **目标**：插件判定禁用后，宿主 `GET /v0/management/auth-files` 里该账号立即 `disabled:true status:disabled`；恢复后回到 `disabled:false status:active`；sidecar / 宿主 / 面板三方集合一致。

## 2. 本轮范围

### 做

1. 新增配置项解析：`cpa_management_url`（默认 `http://127.0.0.1:8317`）、`cpa_management_key`（config_yaml 优先 → env `WB_CPA_MANAGEMENT_KEY`）。
2. 新增 `cpa_disable_sync.go`：封装 `setHostAuthDisabled(name, authIndex, disabled) error`，调用宿主 API 并区分成功/未配置/调用失败。
3. 三类禁用动作接入：API 优先，失败回落现有 `persistAuthDirect`，日志区分降级。
4. 三类恢复动作接入：同样 API 优先 + 写盘兜底。
5. 单测覆盖：成功、未配密钥、API 非 2xx、超时、写盘兜底、未配密钥时的零回归。

### 不做

- 其他插件（coze / qoderwork / qoder-ai / traework / zcode / workbuddy-ai / cursor / qwenwork / copilot）
- 宿主侧任何配置或代码改动
- 探活周期、冷却阶梯、goroutine 累积问题（已单独立项）
- 不改 `host.auth.save` 相关既有约束

## 3. 非范围与前置约束

| 项 | 说明 |
|---|---|
| 归属标记 | 仍只存 sidecar + 物理文件；API 不承载归属。宿主侧看不到「谁禁的」，人工排查需查 sidecar |
| 密钥安全 | 明文只从 config_yaml / env 读，禁止写日志、禁止进面板回显、禁止进错误信息 |
| 调用频率 | 禁用/恢复是低频事件（只在状态翻转时调），不做批量、不加缓存 |
| 端口假设 | 默认 8317；非默认端口靠 `cpa_management_url` 覆盖，不做自动探测 |

## 5. 实施周期与最小任务

### 周期 1：配置与通道（1 个任务）

**T1 配置解析 + 宿主禁用通道**

- 落点：
  ```
  workbuddy/
  ├── cpa_disable_sync.go          （新增：通道封装 + 配置读取）
  ├── cpa_disable_sync_test.go     （新增：单测）
  └── usage_config.go              （改：新增两个配置项解析分支）
  ```
- 内容：
  - `cpaManagementURL()` / `cpaManagementKey()`：锁保护的读函数 + setter，解析顺序 config_yaml → env → 默认值
  - `setHostAuthDisabled(name, authIndex string, disabled bool) error`：
    - 密钥/URL 未配置 → 返回哨兵 `errCPAManagementNotConfigured`
    - `PATCH {url}/v0/management/auth-files/status`，body `{"name":..., "disabled":...}`，`Authorization: Bearer <key>`，超时 5s
    - 2xx 视为成功；其它状态码返回带状态码与响应体截断的错误
- 真实验证：`python scripts/cgo-shim-build.py workbuddy` 全绿 + 新增单测全绿
- 完成条件：配置能正确解析（含 env 覆盖）、通道在 mock server 上走通成功与失败两路

### 周期 2：三类禁用接入（3 个任务，逐类闭环）

**T2 failover 禁用/恢复接入**

- 落点：`failover_disable.go`（`disableAccountForFailover` / `reenableAccountForFailover`）
- 顺序：先 `failoverStateMarkDisabled` → 再调 `setHostAuthDisabled`；成功则跳过写盘，失败则走现有 `failoverPersistFn` 并日志标记 `api-failed fallback to disk`
- 真实验证：`failover_disable_test.go` 现有用例全绿 + 新增 API 路径用例

**T3 low_credit 禁用/恢复接入**

- 落点：`credit_disable.go`（`disableForLowCredits` / `reenableForLowCredits`）
- 真实验证：`credits_*_test.go` 全绿 + 新增用例

**T4 exhausted 禁用/恢复接入**

- 落点：`lifecycle.go`（自动耗尽禁用分支与 `reenableAuth`）
- 注意：`lifecycle.go` 同时承载 manual toggle 分支，**manual 分支不改**（用户手动的禁用由宿主 UI 自己走 API，插件不介入）
- 真实验证：lifecycle 相关测试全绿 + 新增用例锁定「manual 分支不调 API」

## 8. 任务停止 / 结束条件

出现以下任一情况立即停止并上报：

- 宿主 API 返回 401/403 且确认密钥正确（说明宿主管控语义与源码不符）
- API 写入后宿主 auth-files 仍报 `disabled:false`（说明持久化链未打通，需重新定位）
- API 写入导致插件归属标记被抹掉且无法通过 sidecar 恢复（破坏归属模型，需重新设计）
- 热重载后出现 panic 或请求失败率上升

## 9. 最大推进边界

- 只改 `workbuddy/` 目录内文件
- 只发布 `workbuddy-provider` 一个插件
- 只部署到 155.103.157.254
- 不重启容器；热重载未生效时先停下确认，不自行重启
- 不碰宿主 config.yaml、不碰 `config_store` 表
