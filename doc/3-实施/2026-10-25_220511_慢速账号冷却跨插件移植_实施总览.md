# 慢速账号冷却跨插件移植 · 实施总览

- 文档时间：2026-10-25 22:05:11
- 状态：实施中
- 来源需求：workbuddy 0.21.0/0.21.1 已上线的「慢速账号 TTFT 拥堵自动冷却」，用户要求横向铺开到其它 plugin
- 关联文档：`doc/3-实施/2026-10-25_190000_workbuddy慢速账号TTFT拥堵自动冷却_实施总览.md`

## 一、当前计划最终方案的简要说明

把 workbuddy 已验证的慢速冷却机制移植到 **traework / qoderwork / zcode** 三个插件，每个插件都先补 per-attempt TTFT 计时隔离（阻断项）再接入状态机与路由过滤，全部改完后批量发布。workbuddy-ai 与 qoder-ai 本轮**只落文档计划、不改代码**——两者账号池分别为 2 与 0，P25 基线不成立，等它们成为主力池再做。

## 二、对问题的理解

### 目标

同一模型下，显著慢于同池水平的账号在该模型上让出流量，到期自动恢复，不写盘、不标记故障。

### 本轮范围

- **实施**：traework、qoderwork、zcode
- **仅文档**：workbuddy-ai、qoder-ai
- 每个实施插件包含：per-attempt TTFT 隔离、`slow_account.go` 状态机、四处路由接入、6 个 `slow_*` 配置键、面板 `slow_cooling_models` 徽标、判定日志

### 非范围

- 不改判定算法与默认阈值（沿用 workbuddy：2.5 倍 / 15 分钟窗 / 5 样本 / 10 分钟冷却 / 3000ms 下限）
- 不动现有失败冷却、轮换冷却、写盘禁用链路
- 不做跨插件的公共库抽取（各插件独立编译单元，且结构差异大）

### 当前优先闭环

traework → qoderwork → zcode，逐个插件完成「per-attempt 计时 → 状态机 → 路由接入 → 测试全绿」，三者都完成后统一发布。

### 关键前提（阻断项）

**per-attempt TTFT 计时隔离必须先修**。五个插件（除 workbuddy 外）的 TTFT 都用请求级 `started`：

- workbuddy-ai / qoderwork / qoder-ai：`usage.go` 的 `ttftNS(started)` 直接 `firstByteAt.Sub(started)`
- traework：`ttftNSBetween(ctx.Started, result.FirstOutputAt)`，`ctx.Started` 在请求入口取一次
- zcode：主链路 `publishUsage(..., 0)` 恒传 0，TTFT 根本没采集

后果：账号 A 失败耗时 10s → 换到 B、B 首帧 2s，被记成 **12s**，A 的失败耗时算到健康号 B 头上。慢速判据吃这个样本会误禁健康账号，**比不加该机制更糟**。这是 workbuddy 0.21.0 上线时的阻断缺陷。

## 三、三插件现状差异（侦察结论）

| 维度 | traework | qoderwork | zcode |
|---|---|---|---|
| 账号×模型冷却 | 有 `isAuthModelCoolingDown`（accountFailover.go:433） | **无**，只有账号级 `isAccountCoolingDown` | **无**，无内存冷却体系 |
| 轮换冷却 | 有（usage_rotation.go:241） | 有（usage_rotation.go:239） | **无** |
| TTFT 现状 | `ctx.Started` 请求级 + `firstOutputAt` attempt 级 | `ttftNS(started)` 请求级 | 主链路恒传 0 |
| 重试循环 | executor.go:219 / 423 / 656（3 处） | stream.go:230 / 472 | executor.go:52 / 147 |
| 换号入口 | `pickNextAuthForModel`（failover_retry.go:44） | 只有 `pickNextAuth` | `pickNextAuth`（scheduler.go:73） |
| 调度过滤 | scheduler.go:104 / 110 | scheduler.go:110 / 115 | scheduler.go:20 `accountRoutable` |
| 配置解析 | config.go:137 `applyConfigLines` | usage_config.go:149 | main.go:369 `configurePlugin` |
| 面板结构体 | `traeAccountView`（active_auth.go:96） | `wbAccount`（panel.go:16） | `accountSummary`（management.go:85） |
| 失败真相源 | 内存 + 写盘禁用 | 内存 + 写盘禁用 | **仅写盘禁用**（内存冷却已下线） |

### 关键差异带来的适配点

1. **qoderwork 缺账号×模型维度**：现有 `isAccountCoolingDown` 是账号级。慢速冷却按账号×模型生效，需独立新增 `slow_account.go` 而不改动账号级判定。
2. **qoder-ai 连轮换都没有**（本轮不实施，但记录）：说明它比 qoderwork 更旧，未来实施时接入点更少。
3. **zcode 架构断层最大**：`failover.go` 明确「内存阶梯冷却已下线」，真相源是写盘 `disabled`。慢速冷却走内存、不写盘，与它的现有哲学相反，需要独立新增模块而非复用 `failover.go`。

## 四、实施周期

### 周期一：traework（预计最小闭环）

1. **per-attempt 计时隔离**：给三个重试循环各加 `attemptStarted`，改 `ttftNSBetween` 的首参为 attempt 级；补用例锁「重试后 TTFT 不含上次失败耗时」。
2. **`slow_account.go`**：整文件移植（状态机与插件无关，仅调整 authID 归一化前缀为 `traework-`）。
3. **路由接入**：`pickNextAuthForModel`（failover_retry.go:44）、`handleSchedulerPick`（scheduler.go:104）、三处入口预检（executor.go:211 / 407 / 647）。
4. **成功打点**：在真实成功路径调 `noteSlowObservation`，传 attempt 级 TTFT。
5. **配置 + 面板**：6 个键登记进 `ConfigFields`（main.go:292）、解析写入 `applyConfigLines`、面板加 `SlowCoolingModels`。
6. **测试**：cgo-shim 全绿 + 5 项变异 KILLED。

### 周期二：qoderwork

结构与 traework 相近，但缺 `isAuthModelCoolingDown` 与 `pickNextAuthForModel`：

1. per-attempt 计时隔离（stream.go:230 / 472 两个循环）
2. `slow_account.go` 移植（authID 前缀 `qoderwork-`）
3. 路由接入：`pickNextAuth`（failover_retry.go:69）、`handleSchedulerPick`（scheduler.go:110）、入口预检（stream.go:216 / 465）
4. 成功打点 + 配置 + 面板
5. 测试

### 周期三：zcode（架构改造，工作量最大）

1. **先补 TTFT 采集**：主链路 `publishUsage(..., 0)` 改传真实首字节时延；流式侧已知 `stream.go:145-150` 有 `ttftNS = time.Since(startTime)` 观测点，但需改为 attempt 级。
2. **建账号×模型慢速状态**：zcode 无内存冷却体系，需全新引入 `slow_account.go`，与写盘 `disabled` 真相源并存不冲突。
3. **路由接入**：`accountRoutable`（scheduler.go:20）、`pickNextAuth`（scheduler.go:73）、`handleSchedulerPick`（scheduler.go:98）、入口预检（executor.go:52 / 147）。
4. 配置 + 面板 + 测试

### 周期四：批量发布

三个插件全部改完、测试全绿后，连续执行三轮发布（bump → CI → registry → 生产热重载 → 验收），最后统一汇总。

## 六、真实测试方案

- **入口**：`python scripts/cgo-shim-build.py <plugin>`（Windows 无 CGO）
- **必须覆盖**：
  1. per-attempt 隔离：模拟「attempt 0 失败耗时 10s → attempt 1 首帧 2s」，断言样本为 2s 而非 12s
  2. P25 基线：多账号池、慢号占多数时仍能判出慢号
  3. 防抽干：全池判慢时放开一半
  4. 路由接入：每处过滤点用真实路由入口驱动（不能只测状态机）
  5. 到期恢复：冷却过期后重新参与判定，不陷入「解冷即再冷却」
  6. 判定日志：中位数/基线/倍数/阈值齐备
- **通过标准**：cgo-shim build+vet+test 全绿 + 变异验证全部 KILLED + gofmt 干净

- 任一插件测试无法全绿且 30 分钟内无法定位 → 暂停该插件，其余继续，如实记录
- 发布链任一环节失败（CI 红 / 校验不符 / 热重载未生效）→ 停止后续发布，先定位
- 生产验收发现账号丢失或流量异常 → 立即回滚该插件到上一版本并停止
