## 1. 当前计划最终方案的简要说明

**推荐方案**：在 `qwenwork/` 内做 **3 个垂直切片**的最小改动，全部对齐 GitHub QwenWork 社区已验证口径（`dsh-qwenwork-connector` 会话种子链、`modelmux` 排队判据与首帧静默上限、workbuddy 已修的 `host_callback_id` 透传与分阶段超时），**不新增依赖、不改宿主、不改协议**。落点集中在 5 个生产文件 + 3 个测试文件。理由：5 个根因全部是「我方实现与社区/兄弟插件口径不一致」，属对齐类修复而非架构变更；对齐后既消除排队与缓存串味，也让既有的慢号让位机制真正生效。

## 2. Agent 对当前问题的理解

- **问题 / 目标**：QwenWork 经 CPA 插件调用时，部分推理请求很慢且出现排队；同一客户端直连 QwenWork 官方无此现象。目标：消除排队、消除无缓存请求的极端首字延迟，并让慢号能真正让位。
- **本轮范围**：仅 `qwenwork/` 插件源码与其单测；发版与生产热重载。
- **非范围**：宿主 `config.yaml`（`retry.request-retry: 100` 等）——属宿主配置，需用户单独决策；其它插件；新增本地 FIFO 排队限流器（社区可选能力，另案）。
- **当前优先闭环**：CYCLE-01（会话种子塌缩）→ CYCLE-02（慢号让位 + 排队/429 分类）→ CYCLE-03（断连取消 + 分阶段超时）。
- **关键假设 / 待确认点**：
  1. 假设上游 MaaS 以 `session_id` 维度承载会话隔离与前缀缓存（社区三份独立实现一致，且明确记载「撞成同一会话 → 越聊越慢」）。若生产实测缓存命中率未随之改善，回退到「按账号分片 + 请求体哈希二级分片」的折中方案。
  2. 假设 `host_callback_id` 透传后宿主能取消上游请求（workbuddy 同链路已在生产验证）。
  3. 待确认（用户）：宿主 `retry.request-retry: 100` 是否下调——本轮不动，仅在收口时提示。

### 11.2 0.2.29 的关键产出：首字延迟的分段计时

`hostHTTPDoStream` **本就返回上游响应头**但 pump 里写 `_` 丢弃，且 SSE 扫描器对不认识的行直接 `continue` ⇒ 上游在首个内容帧前发的一切都被忽略。新增 `sse_signature.go` 把这段「黑区」变成可见：

- **响应头白名单摘要**（`x-*` / `ratelimit-*` / `retry-after` / `content-type` / `server` / `via`，取值截断 80 字符；**凭据类头显式排除**）；
- **帧结构签名**（顶层键名 + `event`/`type`/`status`/`object`/`index`/`error.code` 等枚举型标识；**不含消息内容**）；
- collector 记首帧前最多 3 帧签名；慢请求日志新增 `upstream=[...]` 与 `prelude=...`。

实测产出（决定性）：**首字 = 上游模型服务自身 4.7~14.7s（`X-Envoy-Upstream-Service-Time`）+ 上游边缘 CDN 层 1.1~6.8s（`Via: ens-cache*`）+ 插件 ~0.2s** ⇒ 插件只占 ~6%；**协议形态（`anthropic/messages` vs `chat/completions`）无法改变 prefill ⇒ 该假设被物理 refute**（原列「剩余最可能差异」不成立，未实施双协议转译）。

同时用三项独立判据证明「我们没有自造排队」：同会话在飞并发仅 1/380 为 2、相邻同会话「间隔 < 前一条耗时」0 次、同会话 TTFT lag-1 自相关 −0.018（无实例亲和 ⇒ 0.2.25 亲和头假设被证伪）。残余慢请求呈**潮汐成簇**（相邻慢请求间隔中位 46s、83% ≤120s）⇒ **跨时段 A/B 必然得出相反结论**。

### 11.3 0.2.30 的关键产出：补齐官方客户端的上下文压缩行为

官方客户端的模型目录带 `context_config`（窗口 1M / 200K / 400K）⇒ **接近上限即压缩历史**；插件此前**全量透传** ⇒ 同一会话每轮重发完整历史、输入随轮次线性膨胀 ⇒ **「官方客户端不慢、我们慢」的差就在这里**（官方发给上游的是压缩后的上下文）。

落地（对齐同仓 `traework` 0.5.65 先例，但消息形态改为 OpenAI 兼容）：

- `qwenwork/context_budget.go`：超预算时裁掉**最旧的中间历史**；恒保留 system / 首轮 user / 最近 12 条；被裁 `assistant.tool_calls` 对应的 tool 结果**成对清理**；末尾单轮即超预算时先削尾部但保住最后一条。
- 配置项 `context_char_budget`（默认 **460,000 字符**，填 `0` 关闭裁剪 = 恢复全量透传）。
- **裁剪与会话身份解耦**：`prepareUpstreamBody` 返回**原始**请求体对象的浅拷贝供会话键派生（头 2 条恒保留 ⇒ 首轮 user 不动 ⇒ 会话键逐条稳定）。
- 裁剪只在请求预处理层做 ⇒ 流式 / 非流式两条路径共用同一入口。

### 11.5 本轮最终判定
