# qwenwork-provider 推理「慢 + 排队」修复 实施总览

- 日期：2026-11-28
- 关联 Bug 主文档：`doc/4-bugs/2026-11-28_161500_qwenwork推理请求慢与排队根因诊断.md`
- 目标插件：`qwenwork/`（生产 0.2.21 → 目标 0.2.22）

## 1. 当前计划最终方案的简要说明

**推荐方案**：在 `qwenwork/` 内做 **3 个垂直切片**的最小改动，全部对齐 GitHub QwenWork 社区已验证口径（`dsh-qwenwork-connector` 会话种子链、`modelmux` 排队判据与首帧静默上限、workbuddy 已修的 `host_callback_id` 透传与分阶段超时），**不新增依赖、不改宿主、不改协议**。落点集中在 5 个生产文件 + 3 个测试文件。理由：5 个根因全部是「我方实现与社区/兄弟插件口径不一致」，属对齐类修复而非架构变更；对齐后既消除排队与缓存串味，也让既有的慢号让位机制真正生效。

## 2. Agent 对当前问题的理解

- **问题 / 目标**：QwenWork 经 CPA 插件调用时，部分推理请求很慢且出现排队；同一客户端直连 QwenWork 官方无此现象。目标：消除排队、消除无缓存请求的极端首字延迟，并让慢号能真正让位。
- **本轮范围**：仅 `qwenwork/` 插件源码与其单测；发版与生产热重载。
- **非范围**：宿主 `config.yaml`（`retry.request-retry: 100` 等）——属宿主配置，需用户单独决策；其它插件；新增本地 FIFO 排队限流器（社区可选能力，另案）。
- **当前优先闭环**：CYCLE-01（会话种子塌缩）→ CYCLE-02（慢号让位 + 排队/429 分类）→ CYCLE-03（断连取消 + 分阶段超时）。
- **关键假设 / 待确认点**：
  1. 假设上游 MaaS 以 `session_id` 维度承载会话隔离与前缀缓存（社区三份独立实现一致，且明确记载「撞成同一会话 → 越聊越慢」）。若生产实测缓存命中率未随之改善，回退到「按账号分片 + 请求体哈希二级分片」的折中方案。
  2. 假设 `host_callback_id` 透传后宿主能取消上游请求（workbuddy 同链路已在生产验证）。
  3. 待确认（用户）：宿主 `retry.request-retry: 100` 是否下调——本轮不动，仅在收口时提示。

## 4. 实施周期与阶段计划

### CYCLE-01：会话种子塌缩修复（主因）

| 步骤 | 落点 | 验证点 |
|---|---|---|
| 1.1 新增 `sessionKeyFromPayload(payload []byte) string`：`prompt_cache_key` → `user` → (system + 首条 user 消息) sha256 前 16 hex | `qwenwork/session_auth.go` | 单测：三种来源各自命中；同对话稳定、异对话不同 |
| 1.2 executor 两入口改为「payload 派生优先、header 链兜底」 | `qwenwork/main.go` | 单测：header 恒定 + 不同 payload → 不同会话键 |
| 1.3 票据缓存加淘汰（TTL + 容量上限） | `qwenwork/maas.go` | 单测：过期条目被清、容量上限生效 |
| 1.4 续期提前量 30min → 10min（对齐官方客户端） | `qwenwork/maas.go` | 单测：提前量常量断言 |

### CYCLE-02：慢号让位 + 排队/限流分类

| 步骤 | 落点 | 验证点 |
|---|---|---|
| 2.1 TTFT 计时基准移到发请求之前 | `qwenwork/stream.go` | 单测：注入延迟首帧 → TTFT > 0 且含等待时间 |
| 2.2 异步流 upstreamModel 传参修正（别名 → 真实模型） | `qwenwork/main.go` | 单测：pump 收到的 upstreamModel == 解析后模型 |
| 2.3 慢速准入闸门按插件池规模下调（20 → 4） | `qwenwork/slow_account.go` | 单测：池 8 时允许判定、池 3 时仍拒绝 |
| 2.4 排队判据补 `serviceAvailable:false`；裸 429「模型池忙」归 503 不冷却账号 | `qwenwork/policy.go`、`qwenwork/accountFailover.go` | 单测：`All models failed` 429 不进冷却阶梯、信封带 503 |

### CYCLE-03：断连取消 + 分阶段超时

| 步骤 | 落点 | 验证点 |
|---|---|---|
| 3.1 `host_callback_id` 全链路透传（wire + executorStreamRequest + 三个执行入口） | `qwenwork/host_bridge.go`、`qwenwork/main.go`、`qwenwork/stream.go`、`qwenwork/failover_retry.go` | 单测：信封含 `host_callback_id`；两个入口都把 `req.HostCallbackID` 传下去 |
| 3.2 共享 HTTP 客户端补 Dial/TLS/ResponseHeader 三段超时 + 禁 h2 | `qwenwork/host_bridge.go` | 单测：三段超时常量与禁 h2 生效 |

## 8. 任务停止 / 结束条件

- 任一 CYCLE 的真实测试无法全绿 → **停在该 CYCLE**，不进入下一 CYCLE，不发版；
- 哨兵反证无法命中（说明断言是弱测试）→ 视为该修复点未验证，先补断言再继续；
- 生产热重载未出现 `hot reloaded` → 不判定成功，按项目 skill 走失败恢复流程；
- 用户当轮给出明确结束指令 → 立即停止扩散性输出，只给最小收口结论。
