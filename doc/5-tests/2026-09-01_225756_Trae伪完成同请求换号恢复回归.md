## 样本与断言

1. 长输入加 599 字节正文和 `done`：判为 pseudo，emitter 调用 0 次。
2. 长输入正文累计达到 600 字节：缓存按原顺序释放，后续分片实时发送。
3. 账号 A 返回带唯一哨兵的短正文和 `done`，账号 B 返回健康长正文和 `done`：客户端只能看到 B 哨兵。
4. A、B 都伪完成：返回 `account pool exhausted after 2 attempt(s)`，不发送 stop。
5. 选号器返回 A 至 B 至 A：实际只调用 A、B 各一次。
6. 异步 attempt panic：上游关闭一次，客户端关闭一次，只发送一个协调器错误。
7. emitter 失败：不再打开备用账号，客户端只关闭一次。

## 生产验收（TASK-006，2026-09-01 23:54-23:57 CST）

0.1.27 生产热加载后第一批真实 `qwen3.8-max` 流量在两次请求上完整走通同请求换号闭环：

- `stream_id=1607`（request `df45ea3f`）：attempt=1（auth_hash=19ca85be）伪完成 → attempt=2（auth_hash=e1987432）伪完成 → 池耗尽显式失败，未把短答当成功下发。
- `stream_id=1609`（request `4d1fcf6f`）：attempt=1（auth_hash=e1987432）伪完成（150 chunks）→ attempt=2（auth_hash=19ca85be）伪完成（79 chunks）→ 池耗尽显式失败。
- 失败核算落盘：203343 fail_count=2、225774 fail_count=2 且冷却生效（cooling=True）。

部署前（0.1.26）同生产流量的伪完成行为对比（部署时间 23:48:33，此前为 0.1.26）：

- `stream_id=1261`（21:36，qwen3.8-max，auth=203343）：`stream pump done ... termination=done chunks=13` 后紧跟 `stream pump pseudo-done`，**无任何 retry / 切号日志**——0.1.26 只记录伪完成，不进行同请求恢复。
- `stream_id=1366`（22:24，DeepSeek-V4-Flash，auth=225774）：`pseudo-done chunks=10`，同样**无同请求恢复**。

结论：0.1.27 在真实生产流量上验证了「同一逻辑请求内 A→B 换号重试、全部账号伪完成时显式失败、失败核算与冷却正确」；不再是 0.1.26 的「把伪完成短答当成功下发、只能影响下一请求」。部署前/后日志构成同一缺陷的 before/after 行为对照：0.1.26 伪完成后无 retry，0.1.27 伪完成后出现 `pseudo retry attempt=N` 与 `pool exhausted`。当前窗口两个账号均被上游瞬时限流，未观察到「一账号伪完成 → 另一账号健康成功」的完整成功恢复，记为 `NOT_OBSERVED`，需要后续自然流量继续观察，但不影响伪完成不再静默当成功这一核心修复的验收。

## 生产直连复现补充（2026-09-02 00:29-00:33 CST，用户授权直连正式环境）

用户提供生产 API key（`https://cpa.luode.vip/v1`，qwen3.8-max）并授权直接请求调试。关键发现：**异步流式路径在上游打开阶段挂死，非流式聚合路径正常**。

- 非流式 `/v1/responses`（无 `stream`）：一次成功，13.3s 返回完整 8 节正文（chars=1860，termination=done，finish=stop）。对应生产日志 `stream aggregate done`，走 `handleExecExecute` 聚合路径（`aggregateTraeCompletion`），**不带伪完成换号**。
- 流式 `/v1/responses`（`stream:true` 超长输入 12 章节/3000 字）：240s 无任何字节后超时。生产日志仅一条 `exec stream async scheduled: ... stream_id=1664`，**此后没有任何 open/pump/pseudo/done/pool exhausted 日志，也无失败核算落盘**；宿主在 4m0s 返回 499（`POST /v1/responses` 4f0560db）。
- 对比 23:54 的 1607/1609：那两次 open 成功、pump 后伪完成换号；1664 是**在 `hostHTTPDoStream`（`MethodHostHTTPDoStream` RPC）打开阶段同步阻塞不返回**，协调器 goroutine 悬挂在第一次 `deps.Open`，客户端 4 分钟收不到任何字节。

根因判断：`hostCall` 是同步 cgo 调用（`C.wb_call_host`），`callLLMStream → hostHTTPDoStream` 无超时保护；宿主流桥在长推理/某些账号下打开上游不返回，异步协调器无法前进 → 客户端 499/无正文/无核算。这与「积分够却一直失败（HTTP 200 0/12 tokens）」的 feed 现象一致，也与「非流式能成功、流式失败」的分流一致。该路径的修复（打开超时/失败回退到同步聚合）属后续闭环，本记录仍为 0.1.27 伪完成换号验收结果。
