# 2026-11-29_003000 glm-provider 模型目录动态化与档位核实

## 一、问题

用户提问：「好像模型获取得也不对, 我们现在是通过接口动态获取模型的吗?」

排查结论分两层。

### 1.1 当时不是动态的

`/models` 只是回放 `glm/models.go` 里的硬编码数组，从不回源上游：

```go
var defaultModels = []string{
	"glm/glm-5.1", "glm/glm-4.7", "glm/glm-4-plus",
	"glm/glm-think", "glm/glm-deepresearch",
}
```

workbuddy 才是动态的（`workbuddyCandidateModels` → `callModelsAPI` 回源 → `storeDynamicModels` 落缓存）。

### 1.2 更严重：五个名字实际只有三档

`resolveAssistantID` 对非 ID 的模型名一律返回 `defaultAssistantID`：

```go
assistantID := defaultAssistantID
if agentIDPattern.MatchString(trimmed) { assistantID = trimmed }  // 只有裸 24+ 位 ID 才换
```

于是 `glm-5.1`、`glm-4.7`、`glm-4-plus` 打到**同一个智能体、同一个 `chat_mode`**，行为完全一致；只有 `think`（`chat_mode=zero`）与 `deepresearch`（`chat_mode=deep_research`）有真实差异。

## 二、上游能力探测

### 2.1 模型/智能体列表接口

对 18 个候选路径探测，只有两条有效：

| 方法 | 路径 | 结果 |
|---|---|---|
| POST | `/chatglm/backend-api/assistant/list` | `200`，返回 `assistant_list`（**用户自建**智能体，当前账号为空） |
| GET | `/chatglm/backend-api/assistant/info?assistant_id=...` | `200`，返回该智能体的 `name` / `chat_mode` / `description` |

其余全部 404：`/user/credit`、`/user/quota`、`/user/point`、`/user/vip`、`/user/member`、`/user/resource`、`/models`、`/model/list`、`/assistant/official`、`/assistant/square`、`/assistant/market`、`/assistant/recommend`、`/assistant/mine`、`/v1/assistant/list` 等。

结论：**GLM 没有「官方模型列表」接口**，官方模型由预置智能体承载，只能靠 `assistant/info` 校验；能动态拿到的只有用户自建智能体。

### 2.2 维度核实

对 `(if_plus_model, chat_mode)` 做六组组合实验：

| 组合 | HTTP | 帧类型 |
|---|---|---|
| `plus + normal` | 200 | `text` |
| `no-plus + normal` | 200 | `text` |
| `plus + zero` | 200 | `think` |
| `no-plus + zero` | 200 | `think` |
| `plus + deep_research` | 200 | `text` |
| `plus + normal(字面)` | 200 | `text` |

**`if_plus_model` 取 true/false 对响应形态没有影响**；真正区分档位的只有 `chat_mode`。因此不把该布尔当作模型维度，也不据此虚构「Plus 版」与「普通版」两个模型。

## 三、实现

### 3.1 目录改为带档位说明的结构

`glm/models.go` 新增 `modelEntry` 与 `modelCatalog`：

| ID | DisplayName | 说明 |
|---|---|---|
| `glm/glm-4-plus` | GLM 标准 | `chat_mode=normal`，网页版默认档 |
| `glm/glm-think` | GLM 思考 | `chat_mode=zero`，返回 think 段 |
| `glm/glm-deepresearch` | GLM 深度研究 | `chat_mode=deep_research` |
| `glm/glm-5.1` | GLM 标准（glm-4-plus 同档） | 兼容别名，上游等价 |
| `glm/glm-4.7` | GLM 标准（glm-4-plus 同档） | 兼容别名，上游等价 |

`defaultModels` 由 catalog 派生，保留既有顺序与兼容性；`allModelInfos()` 输出 `DisplayName` 与 `Description`。

### 3.2 新增 `glm/assistants.go`

- `listUpstreamAssistants(accessToken, cfg)`：POST `assistant/list`，body 带必填的 `page` / `page_size`（缺省上游返回 400 校验错误），头沿用 `refreshHeaders` 且 `X-Device-Id` 取自令牌载荷。
- `dynamicModelInfos(accessToken, cfg)`：预置 catalog + 自建智能体（`glm/<assistant_id>`，DisplayName 后缀「（自建智能体）」）；回源失败降级为纯预置目录并返回 warning。
- `firstUsableAuth()`：取第一个未停用账号供目录回源。
- `handleMgmtModels(query)`：`auth_id` 可选，缺省用首个可用账号。

`Config` 新增 `assistant_list_endpoint` 可覆盖端点。

### 3.3 `resolveAssistantID` 支持 `glm/<id>`

先剥离最后一个 `/` 之前的前缀再匹配 ID 正则，使动态智能体可直接作为模型名使用：

```
glm/65940acff94777010aa6b796 → assistant_id=65940acff94777010aa6b796, chat_mode=""
glm/glm-think                → assistant_id=默认, chat_mode=zero
```

### 3.4 面板

`loadModels` 改为保留 `{id, label, note}`，下拉 `value` 用 ID、显示文本用 DisplayName、`title` 挂档位说明；提交仍走 `model` 字段。

## 五、结论

模型目录已改为接口动态获取：预置档位来自真实维度核实，自建智能体来自上游 `assistant/list`。五个模型名不再伪装成五个不同模型，面板直接标明哪两个是同档别名。

四层版本一致：代码 = `VERSION` = registry = 生产 `0.2.11`。

## 六、遗留

1. 官方模型版本（`glm-4` / `glm-4-plus` 等）由上游后端按账号决定，插件侧无法选择，只能通过 `assistant_id` 换智能体。若日后上游开放模型列表接口，只需替换 `listUpstreamAssistants` 的实现。
2. 当前账号自建智能体为空，动态链路虽已打通但未在真实数据上体现；有自建智能体的账号会自动多出对应条目。
