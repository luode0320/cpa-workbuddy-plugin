### 9.2 文案校正的取证依据（真实客户端，决定性）

在**真实豆包桌面端客户端 2.35.12 进程内**（`Doubao.exe --remote-debugging-port=9226`）对平台自己的「立即签到」按钮做 CDP `Input.dispatchMouseEvent` 可信点击（`Network.enable` 抓包）：

- 请求：`POST /alice/ug/campaign/landing/checkin?version_code=20800&...&aid=497858&real_aid=497858&...&msToken=<平台真实生成>&a_bogus=<平台真实生成>`，body `{"scene":"pc_incentive_task_mvp_v3"}`。
- 响应：`{"data":null,"code":710010702,"msg":"系统错误","message":"system error",...}`。
- 点击后 `document.body.innerText` 仍为「立即签到 / 累计获得额度：0 点」；回查 `v3/detail` 的 `checked_in_today` 仍 `false`、`progress.total_amount` 仍 `0`。

结论：**710010702 是平台按账号投放策略的拒绝，不是请求构造、签名、渠道或设备指纹问题**——平台自身前端 + 真实签名 + 真人可信点击同样失败。故原「需桌面端领取」文案会误导用户去桌面端做无效操作，改为「平台限桌面端」。

同一轮对照：真实客户端内用 `aid=1044603 + doubao_device_platform=desktop` 查询可拿到 `chosen_type=1` 且 `complete_page_info.title = "签到成功，获得 200 额度"`，但随后 checkin 仍 710010702，且回查状态零变化 —— 说明该 complete page 是服务端下发的静态页，与实际签到状态无关。

| `doubao/completion.go` | `newUpstreamClient` | `return &http.Client{Jar: jar, Timeout: timeout}, jar` |

### 26.9 为什么 `-1` 只换号、不冷却

这是本轮唯一一个在实现过程中被自己的回归用例推翻的设计：

第一版把 `-1` 同时加进 `isAccountFailure` 与 `shouldRotate`，两个哨兵都通过。但 `isAccountFailure` 的语义是「计入账号冷却」，而 `-1` 的证据链明确显示**同一账号的技能模式完全可用**（26.4 表第 4 行，6.33 s 正常出字）。把整号冷却 60 秒起，等于用一个只影响工作模式的局部故障毒化整个账号 —— 用户切到技能模式也会被 `pickAccount` 跳过。

因此最终拆成两套判据：

- `shouldRotate(200, -1) == true` —— 当次请求换号，工作模式立刻落到已投放账号；
- `isAccountFailure(200, -1) == false` —— 不记账、不冷却，技能模式继续可用。

### 27.7 决定性坑：`/im/*` 的 Content-Type 与 `/chat/completion` 相反

### 28.2 根因判定

`F:\cpa-plugin\doubao\video_chain.go` 的 `ensureVideoAsset` 四条短路条件里，没有任何一条能排除首轮：

1. `mode.Kind != "video"` —— 首轮同样是 video，不短路；
2. `len(res.Assets) > 0` —— 首轮没有资产，不短路；
3. `res.ConversationID == ""` —— 首轮 `SSE_ACK` 就把 `conversation_id` 给了，不短路；
4. `res == nil` —— 不成立。

真正该用的信号是「这一次请求有没有带续接点」：只有确认轮才可能产生产物。插件内部早就有这个信号（`resumePoint`，0.1.26 的 TASK-009 引入并在三条执行路径上贯通），但回灌入口没有用它。测试也没拦住——`TestEnsureVideoAssetSkipsNonVideoModes` 只验了「生图 / 已有产物 / 无会话 id」三条，**恰好缺「视频模式 + 有会话 id + 无续接点」这个首轮组合**。

| 4 | 5 / 1080p / 不传 | 4.0s | **拒答**「无法直接生成短视频文件」 | 6m0s | 超时，无产物 |
| 5 | 5 / 720p / 不传 | 4.5s | **拒答**「当前无法直接生成短视频」 | 6m0s | 超时，无产物 |
| 6 | 10 / 1080p / 不传 | 0.5s | HTTP 503 `auth_unavailable` | — | 账号处于阶梯冷却 |

第 6 组不是链路问题：前一次超时把账号打进冷却，宿主在预算内没有第二个可用账号，于是直接 503 并回带 `last upstream error`。

### 29.2 `AC-001` 首轮参数同源：成立

第 1、3 组的首轮文本是决定性证据，调用方传的三项被逐字写进上游的参数确认：

```text
第 1 组（5 / 1080p / 16:9）
- 模型： Seedance 2.0 Mini
- 时长： 5 秒
- 比例： 16:9 横屏
- 清晰度： 1080p 观感

第 3 组（5 / 缺省 / 缺省）
- 模型： Seedance 2.0 Mini
- 时长： 5 秒
- 清晰度： 720p
- 比例： auto（将按模型支持的自动比例处理）
```

第 3 组还额外说明缺省回落是对的：只传 `video_duration=5` 时，清晰度按 `defaultVideoResolution` 写成 `720p`、比例按 `defaultVideoRatio` 写成 `auto`，与 `normalizeVideoParams` 的缺省一致。

**第 2 组暴露一个上游侧事实，必须写清楚**：完全不传参数时，插件提交的仍是缺省 `10 秒 / 720p / auto`（确认轮 `chat_ability` 里就是这三个值，产物 `duration=10.08` 可反证），但上游首轮文本自己写了「时长：15 秒」。也就是说**首轮文本是模型生成的，不是插件拼的**，参数没传时它会自行编一个值。这正好是 `DEC-001` 拒绝「解析上游确认文本回填参数」的直接理由——文本不可作为参数真相源。

### 29.3 `AC-002` `media[].duration` 回填：成立

两次真正出片的响应里 `media[0]` 都带 `duration`，且是产物真实时长而不是请求的目标值：

```json
第 3 组（请求 5 秒）  {"duration": 5.057, "height": 682, "width": 384, "type": "video"}
第 2 组（缺省 10 秒） {"duration": 10.08, "height": 216, "width": 384, "type": "video"}
```

`5.057` 与 `10.08` 都是上游 `video.duration` 的浮点原值，未做取整，与 `creation_parse.go` 里 `Duration: video.Duration` 的实现一致。同时可看到宽高仍取产物帧上的字符串字段（`384×682`、`384×216`），说明 `assetFromVideo` 的既有解析路径未被本轮改动影响。

### 29.4 上游拒答路径：本轮新发现的真实缺陷

第 4、5 组的首轮**没有进入视频参数确认流程**，模型直接回了一段拒答：

```text
第 4 组：很抱歉，我目前**无法直接生成短视频文件**，不能按照你指定的 5 秒、1080p、auto 比例来输出…
第 5 组：很抱歉，我当前无法直接生成短视频。你指定的参数：时长5秒、720p、画面比例auto…我已经记录下来，但暂时不支持直接输出该视频文件。
```

关键在于**这两种拒答同样带着 `conversation_id` / `section_id` / `message_index` 返回**（第 4 组 `conv=38454307071027458`，第 5 组 `conv=38454428941576706`）。插件侧 `ensureVideoAsset` 的判据是「视频模式 + 续接点非空 + 无现成产物 + 有会话 id」，这四个条件在拒答场景全部成立，于是确认轮照常发出，随后进入消息链轮询，白等满 `videoPollTimeout=6m0` 才报：

```json
{"error": {"message": "等待视频超时（6m0s）：上游仍未产出成品，稍后可用同一 conversation_id 重试", "type": "server_error", "code": "internal_server_error"}}
```

用户看到的是一条「等 6 分钟再说过一会儿重试」的提示，而真实原因是**会话根本没有视频任务**，重试同一个 `conversation_id` 永远不会成功。这条文案在这一态下是误导的。

**为什么会拒答，本轮无法完全定性**：第 3 组与第 5 组的请求参数、提示词、追加的 `视频参数要求` 段落**完全一致**（都是 `5 秒 / 720p / auto`），一次正常出片、一次拒答。同一输入两种走向说明它不是参数组合硬约束，而是上游模型的采样/风控行为。可以确认的只有一个趋势：连续多次视频请求之后，拒答出现得更频繁（第 4、5 组连续拒答，第 6 组直接进冷却）。

**本轮不改代码，理由**：改判据需要先知道「什么样的首轮文本算进入视频流程」，而第 2 组证明了上游文本会自行编造参数，靠文本匹配做判据会引入新的误判面。这一条登记为待办，等能稳定复现拒答后再设计判据（可选项包括：把超时文案补上「也可能是上游没有进入视频生成流程」、或把 `videoPollTimeout` 在无 `block_type=2074` 占位帧时提前收敛）。

## 30. 0.1.29：面板「测试」假阴性修复与流式续接点补全（2026-11-17 23:00 - 23:20）

0.1.28 把面板「测试」的成功判据收紧到「必须解析到 `block_type=2074` 创作块」，上线后点验
发现它从**假阳性**直接翻成了**假阴性**：同一个账号、同一类提示词，正式链路 12.2 秒真的
出图，面板 2.2 秒就判「没能出图」。本节记录定性与修复。

### 30.1 生产点验（0.1.28，`Authorization: Bearer Ld@588588`）

| 请求 | 耗时 | 响应 |
| --- | --- | --- |
| `POST /v0/management/plugins/doubao-provider/test-active` body `{"auth_index":"doubao-adcd31d29873b4c8","model":"doubao/image"}` | 2.2s | `{"error":"测试失败（模型: doubao/image）：账号能正常出字，但没能出图（可能未投放该能力或额度已用尽）"}` |

两条都是**假阴性**，但成因不同。

### 30.2 根因一：见文本即停

`runActiveTest` 的回调里写着：

```go
		// 创作块才算产物证据；文字与思考只能证明「账号能聊天」。
		text, ok := activeTestOutput(ev)
		if !ok && !activeTestSawCreation(ev) {
			return true
		}
		if text != "" {
			sawText = true
			preview = text
		}
		if activeTestSawCreation(ev) {
			sawOutput = true
		}
		return false
```

只要一帧带文本就 `return false` 关流。而生图与生视频都是**先说后出**：上游先回一段
「好的，我来画」，产物帧在 10 秒之后才到。2.2 秒关流 ⇒ 永远等不到产物帧 ⇒ 必然判失败。

视频更彻底：首轮本来就是两段式的第一段，只回参数确认文本，**任何情况下都不会有产物帧**，
用创作块判它等于要求它必然失败。

### 30.3 根因二（曾误判，已撤回）

排查过程中曾把 `$env:TEMP\zz_stream_raw.txt` 里第 82/83/84 帧的
`choices[0].delta.media` 当成上游产物形态，据此给 `activeTestSawCreation` 加了
`streamDeltaMedia` 判据与两个用例。

**这是一次误判**：那些帧带 `"object":"chat.completion.chunk"`，是**插件自己输出给客户端的
OpenAI 格式帧**（由 `convert.go` 的 `streamChunk` 生成）；`runActiveTest` 接收的是**上游豆包
帧**（`event: STREAM_CHUNK` + `content.content_block` / `patch_op`），里面没有 `delta.media`。
该判据在上游帧上永远命中不了，属凭空增加代码。已完整撤回，并补回被连带删掉的
「文本帧不得终止读取」用例——否则哨兵失去覆盖。

### 30.4 修复

`doubao/active_ping.go` 的 `runActiveTest` 重写为按能力分开的判据：

| 能力 | 判据 | 依据 |
| --- | --- | --- |
| `image` | 必须解析到创作块（`block_type=2074` → `collectCreationAssets` 非空） | 图片是同步产物，同一 SSE 内到齐 |
| `video` | 必须拿到 `SSE_ACK` 里的 `ack_client_meta.conversation_id` | 首轮不产生产物，会话建起来是首轮唯一可得的通路证据 |

两处共同的前提：**文本帧只作记录，不终止读取**。文本仍在失败文案里用得上——「账号能正常
出字，但没能出图」正是靠它区分「能聊天」与「能出图」。

视频成功文案明写这只是首轮通路：

```

```

因为上游确实会**先建会话、再用一段文本拒答**（同节 30.7 记录），会话 id 无法区分这两种态。

另修一处文案瑕疵：上游常在产物前先发一个句号或换行，看着像有文本却不含信息，直接拼进
结果会得到「…耗时 15.1s）：。」。新增 `meaningfulPreview` 去掉只有标点的预览。

### 30.5 流式续接点补全（同一轮发现）

视频两段式要求客户端在首轮之后带 `conversation_id` / `section_id` /
`last_message_index` 再发一次，而流式响应里这三项一直缺失：增量帧在文本到达时就发出去了，
那时聚合还没完成。修复：

- `streamStopFrame(model string, resume resumePoint)` 取代原来只传 `conversationID` 的写法，
  终止帧（`finish_reason=stop`）统一带全套续接点；两条流式路径
  （`collectStreamResponse` / `pumpCompletionStream`）都传 `res.resumePointOf()`。
- `attachResumePoint` 从硬写三字段改成逐字段判空写：上游只给会话 id、不给分节 id 时不再
  写空串，缺哪个字段一眼能看出。

## 33. 0.1.31 多账号会话粘性与回灌账号归属验证（2026-11-21）

### 33.1 缺陷来源与授权

用户 2026-11-21 提出：「如果我们有很多账号之后, 会出现问题吗? 因为要回复2次都会生成视频, 如果第二次被路由到其他账号了呢?」——这是对已上线能力的真实质疑，经代码核对确认成立，用户当轮指令「把这三层一起改掉发 0.1.31」。

缺陷的代码证据（改前）：

- `doubao/scheduler.go:106-109` 的选号是纯轮转：`idx := schedulerIndex % len(candidates)` + `schedulerIndex++`，没有任何 `conversation_id` 感知。
- `doubao/executor_failover.go:47` 的 `if !shouldRotate(status, code) { break }` 在续接请求里同样生效：429 一到就换号，把首轮的 `resume` 原样带到新账号。
- `doubao/executor.go:209`、`doubao/executor_stream.go:82`、`doubao/executor_stream.go:117` 三处 `ensureVideoAsset` 一律传外层首选账号 `sa`；一旦 failover 换过号，回灌就拿 A 的 Cookie 去拉 B 的会话。

后果：池里有两个以上账号时，首轮落 A、确认轮必落 B，上游认不出上下文，确认轮白等满 `videoPollTimeout`（6 分钟）后报「等待视频超时」，并把这次追问的额度烧在一个健康账号上（429 会触发冷却记账）。

### 33.2 三层改动的落点

| 层 | 落点 | 关键行为 |
| --- | --- | --- |
| 1 会话粘性 | 新增 `doubao/session_sticky.go` | `conversation_id → auth_id` 内存表，`sessionStickyTTL = 30 * time.Minute`；首轮成功后 `rememberSessionAuth` 登记，续接请求在 `decodeExecutorRequest` 末尾由 `applySessionSticky` 回钉 |
| 2 续接禁换号 | `doubao/executor_failover.go` | `runWithFailover` 在 `noteAccountFailure` 之后加 `if !resume.isZero() { break }`，早于 `pickAccount` |
| 3 回灌用实际账号 | `doubao/executor_failover.go` + 三个调用点 | `runWithFailover` 返回值由 `(*completionResult, error)` 改为 `(*completionResult, *StoredAuth, error)`；`executor.go:209`、`executor_stream.go:82`、`executor_stream.go:117` 改用 `used` |

第 1 层的三条设计约束（都在代码注释里写明理由）：

- **不做静默回落**：绑定账号被删除或停用时 `applySessionSticky` 返回错误「会话 %s 绑定的账号 %s 已不存在或已停用：请重新发起首轮，不要续接旧会话」。回落到当前账号只会把一次注定失败的续接记成健康账号的失败。
- **命中即复用宿主快照**：`sa.AuthID == boundAuthID` 时直接返回宿主给的 `*StoredAuth`，不去读盘 —— 宿主快照比本地文件新。
- **写时顺带回收**：表只在请求路径上写，没有独立清理协程，`rememberSessionAuth` 每次写前扫一遍过期条目。

### 33.7 未覆盖

- **两个以上真实账号的端到端验证没做**：生产只有一个账号（`doubao-adcd31d29873b4c8`），粘性只在单测层面被钉死，没有「首轮 A + 确认轮 B」的真实双账号复演。要复演需要再导入一个豆包账号。
- **热重载清空表的行为未实测**：这是设计取舍（内存表），代码层面明确，但没有在生产上做「热重载后拿旧 conversation_id 续接」的观测。
- **拒答态白等 6 分钟未修**：与本轮三层改动正交，仍属已知限制。

### 33.8 本节结论

0.1.31 把「多账号下确认轮被路由到其他账号」这条链路从三处一起堵住：请求入口按粘性回钉账号、failover 层拒绝在续接请求上换号、回灌层用实际执行账号。三层各有独立用例与哨兵，本地门禁全绿。真实双账号复演留作后续（生产当前只有单账号）。
