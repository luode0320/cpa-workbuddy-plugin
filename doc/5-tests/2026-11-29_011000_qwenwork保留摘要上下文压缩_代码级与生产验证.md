### 1.4 过程中修掉的三处工程缺陷（非哨兵，但同样影响判定可信度）

| 缺陷 | 现象 | 修法 |
|---|---|---|
| **S1 在全量跑中判 NO-HIT** | 单跑命中、全量跑不命中 | 根因：**宿主编译器被 OOM 杀掉**（Windows 分页文件仅 26MB ⇒ 提交额度打满），门禁失败输出里没有目标测试名 ⇒ 被误判。修法：门禁失败先识别环境类错误（`paging file is too small` / `out of memory` / `cannot allocate memory` / `fork/exec`）⇒ 降编译器内存参数（`GOMAXPROCS=1` / `GOGC=20` / `GOFLAGS=-p=1`）⇒ 等 20s 重试 ⇒ 仍失败判 **ENV-FAILED 并终止**（退出码 2），不再伪装成 NO-HIT |
| **哨兵脚本打印诊断时崩溃** | `UnicodeEncodeError: 'gbk' codec can't encode character` ⇒ 脚本整体中断、后续哨兵全部未执行 | `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |
| **异常时源码不还原** | 脚本崩溃后变异可能留在工作树 | 变异循环包 `try/finally`：无论正常结束还是抛异常都还原源文件并清理备份目录 |

逐段读：

1. **登记**（`pending_summary=true`）：请求按预算裁剪（1167 条历史被裁，输入 341 万字符 → 预算 46 万字符）⇒ 未覆盖区段登记为待摘要。
2. **后台生成**（`context summary ready`）：后台摘要完成，覆盖 1169 条、8960 字符。
3. **注回**（`summary_injected=true pending_summary=false`）：**下一轮同会话请求命中缓存** ⇒ `<conversation-checkpoint>` 消息注回请求 ⇒ 被裁掉的语义还回模型。

⇒ **「裁剪省 token + 摘要保语义」的完整闭环在生产成立**，且摘要在后台完成、未出现在主请求的关键路径上。

### 3.2 生产暴露的新缺陷 → 0.2.32 修复

`01:35:52` 与 `01:35:55` 两条 `context summary ready` **属于同一会话、覆盖同样的 1169 条** ⇒ 同一会话的待摘要区段被**重复生成**。

⇒ **完整回看 0.2.31 窗口（同会话 `msg:050d2fe47ee7903a`）**：

```
01:47:52 context summary ready: covered=1185 chars=8966
01:48:21 context summary ready: covered=1187 chars=9052
01:48:24 context summary ready: covered=1186 chars=8934
01:49:09 context summary ready: covered=1190 chars=8874
01:49:16 context summary ready: covered=1195 chars=8844
01:49:52 context summary ready: covered=1199 chars=8954
01:50:09 context summary ready: covered=1199 chars=8982
```

⇒ **2 分 17 秒内 7 份摘要**，每次都带整段待摘要历史（约 46 万字符 / 13 万 token）。

- 根因：`enqueueContextSummary` **没有会话级去重**——摘要未就绪期间到达的每个请求都会再登记一个任务（全局并发上限 2 ⇒ 最多两份同时在跑，其余被上限丢弃）。
- 代价：① 重复烧上游额度；② 每个任务 `accountLoadAcquire` 占住一个**账号在跑槽位**，与主请求抢同一账号 ⇒ 直接抵消「摘要不阻塞首字」的设计目标。
- 修复（**0.2.32**）：`claimContextSummarySlot` / `releaseContextSummarySlot` 成对管理 `contextSummaryRunning`；同会话同时只允许一个在跑任务，其余请求跳过（下一轮命中缓存后自然不再登记）；失败语义不变（摘要失败不传导给客户端，下一轮重新登记）。
  ⚠️ **注意区分**：全局并发上限（2）是**限流**，会话级在跑标记才是**去重**；只有限流时，同会话仍会反复排队重算。

## 四、结论与遗留

**结论**：0.2.31 把「被裁掉的语义」以官方同款锚定摘要还回模型，且**不占用首字**——生产日志给出完整闭环（登记 → 后台摘要 → 下一轮注入 checkpoint）。0.2.32 修掉生产暴露的「同会话重复摘要」（重复烧额度 + 多占账号槽位）。

**遗留（诚实登记）**：

1. **摘要质量未做人工评读**——本轮只验证机制成立（checkpoint 注入、头部逐字保留、签名失配作废），未评估摘要文本本身对模型回答质量的实际增益。⇒ 需要一个「同会话开/关摘要对照」的语义 A/B 才能定量。
2. **摘要请求本身的上游成本**——每次摘要带约 46 万字符历史；去重后每会话每次覆盖只 1 次，但仍是一笔可观开销；`context_summary_model`（用更便宜的模型做摘要）已接线但**生产未配置、未验证**。
3. **部署后 TTFT 样本量不足**（n=31）⇒ 「无回归」只是方向性结论；建议按既定巡检阈值继续累积。
4. **首字 >10s 的主因仍在 0.2.30 结论里（上游侧）**，本轮不改变该判断；0.2.31/0.2.32 的目标是**语义保真**，不是首字。
