## 4. STYLE-03 注释分层与定义位置（Owner：comment-rules）

### 4.1 函数头元信息

`statusCodeHint`、`isAccountFailure`、`shouldRotate` 三个函数头的 `[参数]` / `[返回]` / `最近修改时间：…；改动原因：…` 均已补齐：

- `statusCodeHint`：`最近修改时间：2026-11-16 21:26:00；改动原因：-1 的成因改回「该账号未投放工作模式」，附三步取证。`
- `isAccountFailure`：`最近修改时间：2026-11-16 21:32:00；改动原因：-1 不纳入账号冷却，避免连带封死同账号可用的技能模式。`
- `shouldRotate`：`最近修改时间：2026-11-16 21:32:00；改动原因：-1 纳入同请求换号，使工作模式请求能自动落到已投放账号。`

### 4.2 判定依据写在注释里，不写在文案里

`statusCodeHint` 的 `-1` 分支保留了完整三步取证（真实浏览器同请求同结果 → 原样 body 重放 → `launch` 端点 `ug_campaign_info` 差异），这段属于「论证式块注释」，符合本项目对争议结论必须留证的要求。

函数头另补了一段 `-1` 的两次误判史（0.1.23 前记成「未投放」、0.1.23 推翻成「请求体缺字段」），与既有的 `710022004` 三次误判史并列，形成同类问题的可追溯链。

### 4.3 已清理的过时注释

`completion.go` 里三处把「省略字段 → 回 -1」当作既定事实的注释已改写，避免与新结论冲突：

- `clientMeta` 注释：改为「这两项不用 omitempty 是为了与浏览器抓到的请求逐字节对齐」，并显式写明「早期曾把省略它们当成 -1 的成因，2026-11-16 21:20 已证伪」。
- `completionOption` 的 22 个默认值字段注释：改为「逐字节对齐真实请求，避免任何形状差异成为排查噪音」。
- `buildSkillOption` / `buildWorkOption` 步骤 3 注释：改为「网页端每次都会显式发送这些默认值段，逐字节对齐真实请求」。

保留这些字段本身不动 —— 它们让请求与浏览器抓包完全一致，是有价值的，只是不再是 `-1` 的解释。

## 5. STYLE-04 函数签名与参数结构（Owner：code-quality-rules）

**未改任何函数签名**。三个函数都保持原参数列表：

```go
func statusCodeHint(code int, desc string) string
func isAccountFailure(status, code int) bool
func shouldRotate(status, code int) bool
```

`isAccountFailure` 与 `shouldRotate` 的判定集合出现分化（前者不含 `-1`、后者含），仍由两个独立函数分别表达，没有合并成「带标志位的单一函数」：两者的调用点不同（`noteAccountFailure` 只用前者，`executor_failover` 只用后者），合并会强迫每个调用点传入它不关心的参数。
