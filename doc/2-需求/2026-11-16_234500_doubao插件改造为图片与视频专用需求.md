## 1. 结论先行

这一轮侦察推翻了一个此前一直默认的前提：**图片和视频在上游是两条完全不同的链路，不是同一个「创作」能力**。

| 维度 | 图片 | 视频 |
|---|---|---|
| 产物到达方式 | **同步**，同一次 `/chat/completion` 的 SSE 里带 `block_type=2074` 的 `creation_block` | **异步**，先只回文本「参数确认」，产物由 `/im/chain/single` 回灌 |
| 需要会话续接 | 不需要，单轮即可拿到 `image.key` 与缩略图 URL | **必需**，确认轮必须带 `conversation_id` + `last_section_id` + `last_message_index` |
| 实测出片耗时 | 17.0s（非流式，生产 `/v1/chat/completions` 实测成功） | 首轮确认 ~14s → 用户确认 → 约 **2.5 分钟**后页面出现「你的视频生成好了。」 |
| 当前插件状态 | ✅ 可用（已出图，`media[0].type=image`） | ❌ 拿不到视频文件（只回确认文本） |

三条决定性事实（全部来自本轮真实取证，不是推测）：

1. **图片是同步产物**。网页发「画一只在窗台上晒太阳的橘猫」，`/chat/completion` 的 SSE 里直接出现 `{"block_type":2074,"content":{"creation_block":{"creations":[{"type":1,...,"image":{"key":"tos-cn-i-a9rns2rl98/rc_gen_image/a26b91dcc4134f549710407b79607c68.jpeg",...}}]}}}`，与现有 `creation_parse.go` 的 `assetFromImage` 完全对得上。
2. **视频首轮只回参数确认**。网页和插件表现一致：`我将为你生成一段…请先确认参数：视频生成参数确认 / 模型：Seedance 2.0 Mini / 时长：15 秒 / 比例：16:9 横屏 … 确认后我再开始生成视频。` 75 秒内 965 个请求里 **零** `creativity` / `creation` 端点调用，也没有任何视频下载地址。
3. **视频必须续接会话才有产物**。在同一个会话里再发「确认，开始生成」，页面发出的 `/chat/completion` 带 `client_meta.conversation_id="38454121040780034"`、`last_section_id="38454121040780290"`、`last_message_index=5`，且 `option.agent_mode` / `conversation_mode` / `model_item_key` **全部为空**（不复用首轮的技能与模型参数，纯靠会话续接）。随后 SSE 回「本次使用 Seedance 2.0 Mini 生成，预计等待 5 分钟」，约 150 秒后页面文本变成「你的视频生成好了。」，产物由 `/im/chain/single` 拉回。

## 2. 视频产物的真实结构（与现有代码不匹配，属确凿缺陷）

从 `/im/chain/single` 抓到的真实回包（`$env:TEMP\zz_chain_CH1.json`，34294 B）里，`creations[]` 的形状：

```json
{"type":2,
 "id":"62082127376376066",
 "gen_detail":{"task_type":6,"ref_images":[]},
 "can_publish":true,
 "video":{"vid":"v0269cg10004dbti12i7dldbulb4k8a0",
          "cover":{"key":"tos-cn-p-9ecd54/o8k...",
                   "image_thumb":{"url":"https://aka.doubaocdn.com/s/Js7YhbSWti","width":384,"height":216},
                   "image_preview":{"url":"https://aka.doubaocdn.com/s/8VzBqp4l6r","width":1280,"height":720}},
          "status":3,
          "width":"384","height":"216",
          "duration":10.08,
          "video_type":"mp4",
          "download_url":"https://v26-vdl.doubao.com/.../mime_type=video_mp4&...",
          "video_model":"{\"status\":10,\"message\":\"success\",\"video_list\":{\"video_2\":{\"definition\":\"720p\",\"vwidth\":1280,\"vheight\":720,\"fps\":24,\"main_url\":\"<base64>\"}}}"}}
```

对照 `F:\cpa-plugin\doubao\creation.go` 的现有定义：

```go
type creationVideo struct {
	Status    int              `json:"status"`
	Key       string           `json:"key"`
	URL       string           `json:"url"`
	Cover     *creationVariant `json:"cover"`
	VideoInfo *creationVariant `json:"video_info"`
	Duration  float64          `json:"duration"`
}
type creationVariant struct {
	URL        string            `json:"url"`
	URI        string            `json:"uri"`
	Width      int               `json:"width"`
	Height     int               `json:"height"`
	URLFormats map[string]string `json:"url_formats"`
}
```

四处硬性不匹配：

| 现有字段 | 真实字段 | 后果 |
|---|---|---|
| `URL json:"url"` | **`download_url`** | 视频地址永远解析为空 |
| `VideoInfo json:"video_info"` | **`video_model`（JSON 字符串）** | 多清晰度列表永远拿不到 |
| `Cover` 期待 `creationVariant` | `cover` 是 `{key, image_thumb, image_preview}`，没有 `url` 字段 | 封面兜底也永远为空 |
| `width`/`height` 期待 int | 真实是字符串 `"384"` / `"216"` | 若加进去必须用 `json.Number` 或字符串再转换 |

`creation_parse.go:122` 的 `assetFromVideo` 取 `video.URL` → `Cover.URL` → `VideoInfo.URL`，三者在真实响应里**全部为空** ⇒ 即使视频链路打通，现有解析器也抽不出地址。这一条与「会话不续接」是两个互相独立的缺陷，必须一起修。

## 3. 目标能力集（「只做图片和视频」的边界）

## 4. 关键缺口（会改变实现方向，必须先定）

### 缺口一：视频做到什么程度

现状是「首轮确认文本 + 无产物」。要真正出片，必须新增三件事：

1. **会话续接**：`runWithFailover` → `collectCompletion` 目前 `conversationID` 恒空串、`needCreate` 恒 `true`（`executor_failover.go:36`）。视频需要首轮拿到 `conversation_id` / `section_id` / `last_message_index`，第二轮原样带回去。
2. **自动二次确认**：视频首轮不会出片，必须由插件自己判断「这是参数确认，需要再发一次确认」。这里有三种取舍 —— 自动发「确认，开始生成」（省一次往返，但用户失去改参数的机会）、暴露给调用方显式两段式、或者首轮提示词里就要求「不要询问，直接生成」（实测无效，模型仍会确认）。
3. **`/im/chain/single` 轮询**：新增端点调用（`cmd=3100`、`ext.sync_scenario="BatchSend|flow.agent.creation"`），按 `last_message_index` 增量拉，直到 `creations[].type==2` 且 `video.download_url` 非空。实测等待约 150 秒，远超现有 `TimeoutSeconds=120`。

这三件的工作量远大于「裁剪」。需要用户确认是「一次做到出片」还是「先做图片，视频保留现状」。

### 缺口二：视频产物的返回形态

视频是 URL（有时效，`url_expire` 字段），不是可内联的二进制。可选：

- `media[]` 里给 `{type:"video", url, cover, duration, definition}`，`content` 里给 `[视频] <url>` 文本 —— 与现有 `creation_render.go` 的约定一致，改动最小。
- 或走 OpenAI 的 `videos` 独立接口 —— 与现有 `chat/completions` 兼容层冲突，不建议。

### 缺口三：裁剪的破坏性

删掉工作模式与签到是**破坏性变更**，会导致：

- 面板上「测试模型」只能测 `doubao/video`，其余模型名从 `/v1/models` 消失。
- 已部署的调用方若在调 `doubao/default` / `doubao/deepseek-v4-flash`，会直接 404。
- `checkin` 相关路由（`/checkin/status`、`/checkin/run`）从管理面板移除。

版本号是否需要大版本跳跃（0.1.25 → 1.0.0 语义化标记破坏性），也需要确认。

## 5. 风险

- **视频额度**：网页明确提示「本次生成将消耗每日免费额度」。自动二次确认会**未经用户逐次同意**消耗额度，这是产品语义变化，不是纯技术改动。
- **等待时长**：单次视频可能 2~5 分钟，现有 `TimeoutSeconds=120` / `StreamTimeoutSeconds=600` 都需要为视频单独放宽或改为异步任务模型。
- **产物时效**：`download_url` 带 `url_expire`，过期即失效，插件不能长期缓存 URL。
- **上游结构漂移**：`video_model` 是一个 JSON 字符串套 JSON 的结构，字段名（`download_url` / `video_model`）都在本轮才第一次被观测到，稳定性未知。
