# workbuddy 禁用状态经 CPA 管理接口同步到宿主

- 日期：2026-10-28
- 状态：需求已确认，待实施
- 来源：用户当轮指令「插件禁用，cpa 没有禁用……给插件加上一个 cpa 的密钥配置，通过直接调用 cpa 的接口来禁用的」
- 影响插件：`workbuddy-provider`（本轮只做这一个，其余插件另立需求）

## 1. 现象与实测证据

用户在面板看到「插件禁用、宿主 CPA 未禁用」的分叉。2026-10-28 生产只读侦察复现：

| 数据源 | 禁用账号数 | 明细 |
|---|---|---|
| 插件 sidecar `workbuddy-failover.json` | **6** | 135ac906 / 1c7e16a0 / 1d7eca06 / 2ca400e3 / 4c979370 / 7ee5e596 |
| 宿主 `GET /v0/management/auth-files`（provider=workbuddy-provider，共 39 个账号） | **3** | 135ac906(97f9d104) / 7ee5e596(ffa38ace) / 8c1f5e2a(51190df6) |

两个方向都对不上：sidecar 有 3 个宿主看不到（1c7e16a0 / 1d7eca06 / 2ca400e3 / 4c979370），宿主有 1 个 sidecar 没记（8c1f5e2a）。这不是「延迟生效」，是双源结构性问题。

## 2. 根因

### 2.1 插件写的是 disk mirror，不是宿主路由真相源

三类禁用（`failover_disable` / `low_credit_disable` / `exhausted_disable`）全部走 `persistAuthDirect` → `writeAuthFileDirect`，直写物理文件的 `disabled: true`。

生产宿主是 MySQL 存储（`MYSQL_DSN`），物理文件是镜像（`/CLIProxyAPI/mysqlstore/mysqlstore/auths/`）。宿主路由读的是 **MySQL DB**，不是这个镜像。镜像会被宿主下次 persist 覆盖回 `disabled:false`，插件写的三个归属标记也会被丢弃——`failover_state.go` 头部注释已经记录了这个实证（宿主重建只保留白名单键 `type/provider/logo/note/disabled/auth/account`）。

### 2.2 sidecar 只能挡住插件自己的路由

`workbuddy-failover.json` 是唯一在宿主覆盖后仍存活的状态记录，但它只参与插件内的 `scheduler.pick` / `pickNextAuth` 排除，**宿主选择器看不见它**。于是：插件不选它，宿主还会把请求发过来。

### 2.3 探活在坏账号上做无效循环

`failoverProbeTargets()` 认 sidecar 记禁用的账号，所以宿主侧其实仍可路由的账号（如 67460db7 / auth_index `1fc81c0d44c9e62d`，宿主 `disabled:false status:active`）也会被每轮探活回放、每次都 429，且因为探活失败不写盘，sidecar 记录永远清不掉。

## 3. 宿主提供的权威通道（已实测）

`PATCH /v0/management/auth-files/status`

- body：`{"name": "<auth 文件名>", "disabled": true|false}`，可选 `auth_index`
- 实测契约：缺 `name` → `400 {"error":"name is required"}`；缺 `disabled` → `400 {"error":"disabled is required"}`；name 不存在 → `404 {"error":"auth file not found"}`
- 宿主实现（`internal/api/handlers/management/auth_files_fields.go:24` `PatchAuthFileStatus`）走 `applyAuthDisabledState` + `h.authManager.Update(ctx, targetAuth)`：
  - `applyAuthDisabledState` 同时设置 `auth.Disabled`、`auth.Status`、`auth.StatusMessage`、`auth.Metadata["disabled"]` —— **这才是插件读到的 `AuthData.Disabled` 的来源**
  - `authManager.Update` 内部 `m.persist(ctx, auth)` 会写 MySQL（`store.Save`），因此**宿主路由真相源被真正改写**
- 这是宿主认证文件管理页 toggle 的同一入口，语义与人工操作完全一致

## 4. 需求

### 4.1 功能

1. 新增插件配置项 `cpa_management_key`（config_yaml 键），用于调用宿主管理 API 的 Bearer 令牌。
2. 三种禁用动作在写盘之外（或替代写盘）调用 `PATCH /v0/management/auth-files/status`，使宿主真正禁用该账号。
3. 三种恢复动作同样调用该接口把 `disabled` 置回 false。
4. 接口调用失败时保留现有写盘兜底，并打日志标记降级路径。

### 4.2 用户已裁定的边界（2026-10-28）

| 议题 | 裁定 |
|---|---|
| 覆盖范围 | **三类全部改造**：failover_disable / low_credit_disable / exhausted_disable |
| 密钥来源 | **新建 `cpa_management_key` 配置项**，不复用已有的 `management_key`（后者是插件自身对外的鉴权口令，语义不同） |
| 调用失败处理 | **保留现有写盘兜底**：API 成功即权威，失败回落直写物理文件并记日志 |

### 4.3 非范围

- 其他插件（coze / qoderwork / qoder-ai / traework / zcode / workbuddy-ai / cursor / qwenwork / copilot）本轮不改
- 不改宿主管控端口、不改宿主任何配置
- 不修本轮另发现的「热重载不杀 goroutine 导致探活 8 倍累积」问题（已单独记入记忆）
- 不改探活周期与冷却阶梯

## 5. 待实施阶段确认的关键点

1. **宿主管理端点地址**：插件拿不到宿主管控端口（SDK 只暴露 `BasePath` 与 `BaseURL`，无监听端口）。默认 `http://127.0.0.1:8317`，需允许 config_yaml 覆盖（如 `cpa_management_url`），否则非默认端口部署不可用。
2. **归属标记的承载位置**：API 只写 `disabled`，不认插件的三个顶层标记。归属判断（谁的禁用谁负责恢复）必须继续依赖 sidecar + 物理文件标记，或扩展为该接口可写的自定义字段（`PATCH /v0/management/auth-files/fields` 可写任意 Metadata 字段，已确认存在）。选哪条需在实施规划中定稿。
3. **auth 文件名**：接口要 `name`（如 `workbuddy-67460db7-f8b6-4be6-86de-d05f7dc53bf9.json`），插件侧已有 `hostAuthPhysical.Name` 可取。
4. **密钥注入方式**：config_yaml 是唯一来源，还是同样支持 env / secret 文件（与既有 `usage_report_key` 的三级解析保持一致）？建议对齐既有解析顺序。

## 7. 与既有结论的关系

- 修正 `failover_state.go` 头部「写盘禁用无法到达宿主路由判据」的结论：写盘确实到不了，但现在有 API 这条通道能到
- 复用 `doc/4-bugs/2026-10-25_144500_coze低额自动禁用未同步宿主认证文件状态根因诊断.md` 的根因分类（宿主判状态只认 `AuthData.Disabled`），但修复路径不同：coze 是靠补顶层字段让宿主读镜像，workbuddy 生产走 MySQL 存储，补字段同样会被 persist 覆盖，必须走 API
- 2026-08-22 记录「管理 API `PATCH /v0/management/auth-files/status` 是 host UI toggle 入口，但插件拿不到认证（`localMgmtPassword` 只注入 TUI 客户端）→ 不可用」——本需求正是通过新增 `cpa_management_key` 配置解决这个前置阻塞
