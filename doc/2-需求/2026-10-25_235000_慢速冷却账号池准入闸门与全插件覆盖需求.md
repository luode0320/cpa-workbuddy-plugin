# 慢速冷却账号池准入闸门与全插件覆盖需求

- 时间：2026-10-25 23:50 (GMT+8)
- 提出人：luode
- 状态：实施中

## 1. 用户原话与诉求

> 所以这个慢速冷却机制，我们改成只有插件的这个账号大于20（启用+停用），才触发。
> 这样就不会因为账号不够出现问题了，把所有慢速冷却机制都加上这个逻辑，
> 把其他插件也补上慢速冷却机制并账号大于20（启用+停用），才触发。

拆成三条硬要求：

1. **准入闸门**：已有慢速冷却的插件，账号总数 **> 20（启用 + 停用都算）** 才触发判定。
2. **闸门铺开**：所有慢速冷却实现都必须带这道闸门，不能只有个别插件有。
3. **机制铺开**：其他还没有慢速冷却的插件也要补上，同样受 > 20 闸门约束。

## 2. 为什么必须加这道闸门

判据是「各账号 TTFT 中位数的**下四分位（P25）**」。这个统计量在样本池太小时不成立：

| 池子规模 | P25 的退化形态 | 后果 |
| --- | --- | --- |
| 1 个 | 等于该账号自己的中位数 | 自己和自己比，永远 1.0 倍，不判慢（无害但无意义） |
| 2 个 | 取两个中位数里较小的那个 | 任一次网络抖动就会让其中一个被判慢，两号互相顶替 |
| 3~5 个 | 取排序后靠前的值 | 单个毛刺账号即可拉低基准，误判率显著上升 |
| < 20 | 仍易被单点波动主导 | 制造噪音，收益低于风险 |

这正是 2026-10-25 生产实测的教训：事故排查期临时留存的激进参数（1.2 倍 / 2 样本 / 500ms 下限）
下，池内 TTFT 仅 1.26 倍差却持续判慢，冷却主体在两个账号之间反复跳变。
**账号数不足时，任何相对判据都只是在放大噪声。**

| qoderwork-provider | 18 | 0 | 18 | 休眠 |
| coze-provider | 17 | 0 | 17 | 休眠 |

**这条闸门的直接效果：现有生产里只有 workbuddy 真正运行慢速冷却，其余插件全部自动休眠。**
这正是用户「不会因为账号不够出现问题」的意图——机制在位、按池子规模自动上下线。

## 4. 闸门的判定口径

- **计数范围**：**启用 + 停用** 全部账号。用户明确要求把停用账号也计入。
  理由：停用往往是临时的（额度耗尽、探活中），池子的真实规模应按账号归属算，
  而不是按当前可路由数算；否则一次批量临时禁用就会让机制忽开忽关。
- **阈值**：`> 20`（严格大于，即 21 个及以上）。默认值定为 20，可通过配置项覆盖。
- **判定时机**：在**判定入口**（`evaluateSlowAccount` / `noteSlowObservation`）前置检查，
  不是每次路由判定都查。理由见第 5 节。
- **不满足时的行为**：完全不记录样本、不判慢、不冷却。**不是「记样本但不冷却」**——
  无意义的样本只会在池子长大后立刻触发一轮基于陈旧数据的误判。

## 5. 账号总数从哪来（关键工程约束）

账号枚举的唯一可靠来源是宿主 RPC `host.auth.list`（`hostAuthList()`），
它返回全部账号（含 `Disabled` 字段），足以统计「启用 + 停用」总数。

**但它是跨进程 RPC，绝不能放在每请求热路径上。** 慢速冷却的判定入口
`noteSlowObservation` 挂在每次成功请求的成功路径上，如果这里同步调 RPC：

- 每个成功请求多一次跨进程往返，直接抬高整体延迟；
- 宿主侧 RPC 若有排队，会把插件侧成功路径也拖慢。

**设计：账号总数用独立的周期缓存，判定入口只读内存变量。**

- 缓存字段：`slowPoolSize`（int）+ 读写锁；零值表示「尚未探测」。
- 刷新时机：独立 ticker（与现有 watchdog / prune 周期任务同风格），周期 10 分钟。
- 刷新失败：保留上一次已知值，不清零——宿主 RPC 偶发失败不应该让机制忽开忽关。
- 首次探测：插件加载后立即探测一次，避免上线后 10 分钟内处于「未知」状态。

**「尚未探测」如何处理**：保守关闭（`slowPoolSize == 0` 视为不满足闸门）。
宁可晚 1 次刷新周期生效，也不能在未知状态下误判。

## 6. 覆盖范围

### 6.1 已有慢速冷却的插件（加闸门）

`workbuddy` / `traework` / `qoderwork` / `zcode` 四个。逐个加：
状态字段、周期刷新、判定入口前置检查、配置项 `slow_min_pool_size`、用例、变异验证。

### 6.2 需要新补慢速冷却的插件（补机制 + 闸门）

**具备全部前置条件的三个（本轮实现）**：

| 插件 | TTFT 采集 | 账号枚举 | 路由拦截点 |
| --- | --- | --- | --- |
| workbuddy-ai | `usage.go:225` `sseUsageCollector.ttftNS` | `hostAuthList()` | `active_auth.go:189` `accountRoutable(authID)` |
| qoder-ai | `usage.go:288` 同上 | `hostAuthList()` | `active_auth.go:191` `accountRoutable(authID)` |
| qwenwork | `usage.go:288` 同上 | `hostAuthList()` | `active_auth.go:182` `accountRoutable(authID)` |

三者与 workbuddy 高度同构（同一个骨架演化而来），移植路径与 traework/qoderwork 一致，
但**仍需先补 per-attempt TTFT 计时隔离**（阻断项，见 6.3）。

**前置条件不全的三个（用户裁定：本轮不做，仅记录现状）**：

| 插件 | 缺失项 | 说明 |
| --- | --- | --- |
| coze | 无 TTFT 采集、无 `accountRoutable` | 执行链没有首字节打点，也没有统一路由判定函数；属独立工程 |
| copilot | 无 TTFT 采集 | 有 `accountRoutable`，但执行链不记首字节延迟 |
| cursor | 架构不同（`internal/` 分层，非单包） | `cursorapi` 有内部 TTFT 统计但未上抛到使用链 |

**用户裁定（2026-10-26）**：「三者都不做」。理由：补齐前置条件的工作量远大于移植状态机本身，
且生产均未启用或无池子。本轮只在本文档记录缺口，代码不动。

### 6.4 本轮的实现范围（最终）

| 插件 | 本轮动作 | 含闸门 |
| --- | --- | --- |
| workbuddy / traework / qoderwork / zcode | 加账号池准入闸门 | ✅ |
| workbuddy-ai / qoder-ai / qwenwork | 补 per-attempt TTFT + 非流式 TTFT + 完整状态机 + 路由过滤 + 7 配置键 | ✅ |
| coze / copilot / cursor | 不动（用户裁定本轮不做） | — |

### 6.3 阻断项：per-attempt TTFT 计时隔离

所有移植必须先检查 `ttftNS(started)` 是否用**请求级**时间戳跨 attempt 复用。
若是，则「A 号失败耗时 10s → 换到 B、B 首帧 2s」会被记成 12s，
**A 的失败耗时算到健康号 B 头上**。喂给慢速判据会误禁健康账号，比不加机制更糟。

## 7. 验收标准

1. 四个已有插件：账号数 ≤ 20 时 `noteSlowObservation` 不记样本、`evaluateSlowAccount` 返回 false；
   账号数 ≥ 21 时行为与现在完全一致。
2. 三个新移植插件：per-attempt 计时用例通过 + 状态机用例通过 + 闸门用例通过。
3. 全部插件：变异验证覆盖「删掉闸门条件」「闸门恒假」「闸门恒真」三种形态，全部 KILLED。
4. 配置项 `slow_min_pool_size` 在管理端可见、可改，默认 20。
5. cgo-shim build + vet + test 全绿。

## 8. 非目标

- 不改判定算法（P25 基线、倍数阈值、绝对下限、防抽干）——只加准入闸门。
- 不把慢速冷却变成写盘禁用——慢是性能问题不是故障。
- 不为 coze / copilot / cursor 补 TTFT 采集或路由判定函数（超出本轮）。
- 不改动其它冷却机制（失败冷却、轮换冷却）。
