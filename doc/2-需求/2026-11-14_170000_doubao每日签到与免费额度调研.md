# 豆包每日签到与免费额度调研（含开源反代对照与生产实测）

- 日期：2026-11-14
- 状态：调研完成，方案待定（未实施）
- 来源：用户当轮指令「豆包工作是有每日签到的, 查一下怎么做? 好像是有免费和额度的, 看看github的其他开源的反代是怎么处理的?」
- 影响插件：`doubao-provider`（当前 0.1.11，**无任何签到能力**）
- 参考实现：`yyydsz/doubao2api` ★5、`L0NE-6/DoubaoWork-Daily` ★7、`hiclaw168-163/auto-signin-kit` ★5、`bluechonk/doubao-auto-checkin` ★6、`tututashu/doubao-auto-checkin` ★5、`meliissy/doubao-daily-checkin` ★1

## 1. 结论先行

豆包签到**可以做，但不能无条件自动签**。关键判据是 `POST /alice/ug/campaign/landing/get` 返回的 `chosen_type`：

| `chosen_type` | 落地页形态 | 网页 checkin 结果 |
|---|---|---|
| `0` | 无引导卡片，正常签到入口 | **200 + `code:0`**（已签则 `idempotent:true`） |
| `3` | `landing_cards[0].card_code = web_pc_download_banner`，文案「前往豆包桌面端即可领取」 | **200 + `code:710010702` 系统错误** |

生产两个真实账号实测（同一份代码、同一份 Cookie 通道、同样裸 HTTP）：

- 账号 `doubao-adcd31d29873b4c8`（欧皇小德子）：`chosen_type=0`，今日已签（`task_status=3`、`reward_status=3`、`progress.total_amount=200`），补打 checkin 返回 `{"checked_in":true,"checkin_date":"2026-11-14","continuous_days":1,"idempotent":true,"reward_amount":200,"reward_code":"quota_grant","reward_status":3}`。
- 账号 `doubao-c754e5d56ed62480`（用户158477）：`chosen_type=3`，落地页卡片文案「前往豆包桌面端即可领取」；checkin 在 **8 种变体**下全部 `710010702`（网页 query / 客户端 query / 加 `biz_params` / 加 `AgwCommonParam` / 加 `task_id` / 换 `version_code` 20800·23001·23010 / 加 `agw-js-conv` + `last-event-id` 头）。

**因此 `710010702` 在本场景不是参数错误，也不是 session 被风控污染，而是平台按账号渠道下的产品拒绝**：该账号的网页签到入口被替换成「下载桌面端」引导，网页通道不发放这个签到。

另一条决定性证据来自 `POST /alice/ug/campaign/v3/detail/` 的任务清单：

| 账号 | web 形态 `tasks` | 客户端形态 `tasks` |
|---|---|---|
| 账号1（已签） | 含 `daily_signin`（`task_status=3`） | **不含 `daily_signin`** |
| 账号2（未签） | 含 `daily_signin`（`task_status=1`） | **不含 `daily_signin`** |

`daily_signin` 只在 **web 形态**（`device_platform=web` + `doubao_device_platform=web` + `aid=497858`）的详情里下发；一旦把 query 换成桌面端形态（`aid=582478` + `doubao_device_platform=desktop` + `client_platform=pc_client`），平台直接不下发该任务，`chosen_type` 也随之变 `0` 且 `landing_cards` 为空。

## 2. 接口契约（五仓库一致，已交叉验证）

| 用途 | 方法 | 路径 | body |
|---|---|---|---|
| 签到 | POST | `/alice/ug/campaign/landing/checkin/` | `{"scene":"pc_incentive_task_mvp_v3"}` |
| 活动详情 | POST | `/alice/ug/campaign/v3/detail/` | `{"campaign_group_code":"pc_incentive_task_mvp_v3"}` |
| 落地页形态 | POST | `/alice/ug/campaign/landing/get` | `{"scene":"pc_incentive_task_mvp_v3"}` |
| 任务奖励 | POST | `/alice/ug/campaign/item/reward/claim/` | `{"task_id":"","campaign_group_code":"...","campaign_item_code":"<code>","AgwCommonParam":{}}` |
| 额度汇总 | POST | `/alice/commerce/sale/subscription/quota/summary/` | `{}` |

公共 query 必带：`version_code`、`language=zh`、`device_platform=web`、`doubao_device_platform=web`、`aid=497858`、`real_aid=497858`、`pkg_type=release_version`；`device_id` / `web_id` / `tea_uuid` / `web_tab_id` 可选但建议带。请求头：`Cookie` + `Content-Type: application/json` + `Origin: https://www.doubao.com` + `Referer: https://www.doubao.com/pc/agent-explore` + UA 含 `SamanthaDoubao/<version>`。

签到回执字段：`data{checked_in, checkin_date, continuous_days, idempotent, reward_amount, reward_code, reward_status, reward_type}`。**成功判据只能是 `data.checked_in == true`，不能只看 `code == 0`。**

业务码：`710012001` 登录过期、`710022004` 限流、`710010702` 系统错误（本场景=渠道不支持下发）、`code=2` 活动不存在（换季）。

活动规则：每日 200 活动额度、周一翻倍 400、30 天累计上限 8800；漏签不补、赠额 30 天有效。

## 3. 免费额度怎么读

`quota/summary` 是真实存在的接口（`yyydsz/doubao2api` 的 `internal/server/quota.go` 用的就是它），生产实测两个账号的响应差异可直接反映签到结果：

- 账号1（已签）：`data.incentive_quota_section.window_limit_groups[0]` → `feature_group_name = "活动赠送额度"`、`feature_group = "doubao_activity_reward_quota"`、`window_limits[0] = {total_amount:200, used_amount:200, used_percent:100, end_time:1797237901995}`。
- 账号2（未签）：响应仅 810 字节，`data` 里无 `window_limit_groups`。

读法：递归找所有 `window_limits` 数组，累加 `total_amount` / `used_amount`；兼容数字与数字字符串（去 `,` 空格 `¥` `$`）。这是 `quota.go:116-166` 的既有实现，可直接照搬。

注意两个口径差异：
- `quota/summary` 给的是**还剩下多少**（含总量与已用）。
- `v3/detail` 的 `progress.total_amount` 给的是**本活动周期已获得多少**（账号1=200，账号2=0）。
- 两者不冲突，展示时应分开呈现。

## 4. 风控红线（开源实现踩坑记录）

`hiclaw168-163/auto-signin-kit` 的 `NOTE-04` 记录了一次真实事故：活动页前端 SDK 会带 `a_bogus`、`msToken`、`web_id`、`tea_uuid`、`pc_version`；**裸 HTTP 反复请求会让该 session 被判受限，此后连官方客户端手工点「立即签到」也回 `710010702`，只有卸载重装客户端才恢复**。该仓库因此把 `auto` 通道改成「客户端 CDP 不可达就 skip，绝不发裸请求」。

`L0NE-6/DoubaoWork-Daily` README:85-86 给出同向警告，并明确「脚本不会伪造 `biz_params` 与 `AgwCommonParam`」。

本轮生产实测对这一风险给出了**更精确的边界**：账号1 用裸 HTTP 打 checkin 得到的是正常幂等回执（不是 `710010702`），说明裸请求本身不会必然污染——**真正决定成败的是账号的 `chosen_type` 渠道形态**。但「反复打必然失败的 checkin」仍然没有收益且增加风控面，因此仍应做成一次性、失败即停。

## 5. 六个开源实现的做法对照

| 仓库 | 通道 | 是否自动领取 | 定时 | 幂等策略 |
|---|---|---|---|---|
| `yyydsz/doubao2api` | 裸 HTTP | 是 | 每天 9 点整点 | 只看回执 `checked_in` / `idempotent` |
| `L0NE-6/DoubaoWork-Daily` | 裸 HTTP | 是（默认只读 query） | 青龙 `15 9 * * *` | pending 台账 + 18 秒确认预算 + 0/2/4 秒回查 + 10 分钟间隔 / 30 分钟窗口 / 4 轮；只认 `checked_in_today=true` |
| `hiclaw168-163/auto-signin-kit` | CDP 界面优先，裸 HTTP 已禁用 | 是（仅界面通道） | 系统级 schtasks/launchd/cron | 详情态 `checked_in_today` 为唯一事实源 |
| `bluechonk/doubao-auto-checkin` | CDP + 客户端 | 是 | Windows 计划任务 09:10 | 点击前先 `check_success()` |
| `tututashu/doubao-auto-checkin` | Playwright 点击 | 是 | 09:20 + 每 4 小时兜底 + 开机补跑 | 点击前先判已签 |
| `meliissy/doubao-daily-checkin` | URL/method/body 全配置化 | 是 | Actions 北京时间 00:05 | 从响应文本正则抠数字 |

共识：**多账号一律串行**（账号间 `sleep(1)`），**定时集中在上午 9 点档**，**成功后必须回查详情**，**不把单个 `code=0` 当成功**。

## 6. 方案（按代价排序，可单选）

### 档 1：只读状态（零风险，推荐先落）

只打 `v3/detail`（web 形态）读 `data.tasks[].daily_checkin.checked_in_today`，在面板显示「今日已签 / 待签 / 需桌面端」，未签时给出手动链接。

- 稳定性：生产两账号实测 `code=0`，无风控面。
- 数据来源唯一可信：`checked_in_today`。
- 需要新增：管理路由（如 `/checkin/status`）+ 面板卡片 + 定时只读刷新。

### 档 2：条件自动签（推荐，收益/风险最优）

在档 1 基础上加一次 `landing/get` 前置判据：

```
读 landing/get → chosen_type == 0 且 landing_cards 无 web_pc_download_banner
  → 读 v3/detail，checked_in_today == true 则直接返回 already（不发写请求）
  → 否则 POST landing/checkin {"scene": group}，最多 1 次
  → 0/2/4 秒回查 detail，仅 checked_in_today == true 记 claimed
  → 收到 710010702 / 710012001 / 710022004 → 记 blocked，当天不再重试
chosen_type != 0（有桌面端引导）
  → 直接记 needs_desktop，不发任何写请求
```

- `chosen_type` 闸门是关键：它把「必然失败的写请求」挡在前面，既省流量又避免风控面。
- 每日最多 1 次写请求，失败即停，绝不做多轮重试。
- 与开源实现的差异：它们都没做这一步前置判据，因此会在 `chosen_type=3` 的账号上反复吃 `710010702`。

### 档 3：桌面端 CDP（不推荐插件内实现）

`chosen_type=3` 的账号只能在桌面端领取。要在插件内自动做，需要本机安装豆包客户端并开 9222 调试端口，用 `Input.dispatchMouseEvent` 做受信任点击（`element.click()` 会被 `isTrusted` 校验丢弃）。插件是 c-shared `.so` 跑在 Linux 容器里，无桌面环境，**不适合内嵌**；可做的只是「检测到外部 CLI 已跑过，把结果读回来展示」。
