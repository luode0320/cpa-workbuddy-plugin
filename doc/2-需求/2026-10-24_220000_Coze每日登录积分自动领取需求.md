# Coze 每日登录积分自动领取需求

- 时间：2026-10-24 22:00 (GMT+8)
- 提出人：luode
- 状态：已实现并待发布

## 1. 背景与问题

用户反馈「扣子的插件不能每日签到领积分」，要求找办法（含反代、GitHub 方案）。

排查后确认两件事：

1. **插件确实完全没有签到/领取链路**：`git grep` 全仓 `coze/` 目录，
   `签到|checkin|check-in|daily|sign_in|signin` **零命中**；插件只有
   `credit/balance` 与 `credit/balance/detail` 两个只读端点。
2. **账号池长期 0 分**：生产 9 个扣子账号，实验开始时 8 个 `remain=0`。

## 2. 关键事实（生产九账号对照实验实证）

### 2.1 每日积分真实存在

来源 `src=24`「活动积分」，条目名「每日登录」，每条 **1500 分**，
**有效期仅 1 天**（到期时间戳均落在当天 23:59:59）。

历史记录（探测前）：

| 账号 | 每日登录发放日期 | 当时 remain |
|---|---|---|
| 1185dd | 10-19 | 0 |
| 2a143e | 10-21 | 0 |
| 75c744 | 10-19 | 0 |
| a2d9fc | 10-20 | 0 |
| b161bd | 10-21 | 0 |
| b3f25e | 10-20 | 0 |
| d74585 | 10-19 / 10-20 / 10-21 | 0 |
| f18297 | 10-21 | 0 |
| ff6ae4 | 10-21 | 0 |

结论：**这些积分当天不领即归零**，不是被推理消耗掉。

### 2.2 唯一触发器是 `credit/balance/check`

官方文档口径是「登录后发放」，但实测**网页登录动作本身不触发**。
逐项对照（每个账号只打一个端点，60 秒后观察是否到账）：

| 动作 | 结果 |
|---|---|
| `GET /api/marketplace/trade/credit/balance/check` | **✅ 发放 1500** |
| `GET /api/coze_space/activity/info` | ❌ |
| `GET /api/marketplace/commerce/get_user_benefit` | ❌ |
| `GET /api/marketplace/incentive/user_task/list` | ❌ |
| 不请求（对照组） | ❌ |
| `POST /passport/token/beat/v2/`（插件现有续期） | ❌ |
| `GET /home`（模拟网页登录） | ❌ |

复现性：另取 3 个「当日未发」账号只打 check，**3/3 全部 0 → 1500**。

### 2.3 幂等

同一账号同日连打 3 次 check，当日条目始终 **1 条、总额 1500**，不重复发放。

### 2.4 响应语义（初版假设已被推翻，重要）

check 响应为 HTTP 200 + `code=0`，`data` 里有 `pass` / `deny_reason`。

**初版误以为 `pass` 表示「本次是否发放」**，据此实现了一版；随后**全账号复核推翻**：

| 账号 | check 响应 | 当日到账 | remain |
|---|---|---|---|
| 1185dd | `pass:true` | 1 条 | 1500 |
| 2a143e | `pass:true` | 1 条 | 1500 |
| 75c744 | `pass:true` | 1 条 | 1500 |
| a2d9fc | `pass:true` | 1 条 | 1500 |
| b161bd | `pass:true` | 1 条 | 1500 |
| **b3f25e** | **`pass:false, deny_reason:1`** | **1 条** | **1500** |
| d74585 | `pass:true` | 1 条 | 1500 |
| **f18297** | **`pass:false, deny_reason:1`** | **1 条** | **1500** |
| ff6ae4 | `pass:true` | 1 条 | 1500 |

结论：**`pass` / `deny_reason` 描述的是「余额是否够用」，与本次是否发放无关**。
`pass=false` 的账号照样拿到当天 1500 分。

最终判据改为「**明细里存在当天且仍有余额的每日登录条目**」：
只能先调 check、再从明细确认，不能凭 check 响应判定。
`pass` 仅作排查线索保留，不参与领取判定。

### 2.5 明细状态值口径

`display_status` 实测取值：

| 值 | 含义 | 示例 |
|---|---|---|
| 2 | 当天可用（即将过期） | 今日 1500 分 |
| 3 | 未来到期 | 新用户注册奖励 |
| 4 | 已过期 | 历史每日登录 |
| 0 | 查全部 | 全量条目 |

## 3. 方案裁定

用户裁定「方案 A」，即**在插件内置**，不采用外部 GitHub Actions 或独立 cron。

弃用理由：

- GitHub 现成项目 `andrew-new/coze-daily-credit-action` 用 Playwright 打开首页
  **盲点「领取/签到/免费积分」等按钮**，脚本自带兜底文案
  「No claim-like control found; page visit is treated as the daily action」
  —— 找不到按钮就把访问当作完成，属弱实现；且需另维护一套 Cookie 快照。
- 外部 cron 需独立维护 Cookie 旋转，与插件已有的滚动续期重复。

插件即反代，内置让领取天然跟随既有的 5 分钟积分刷新周期，
且复用同一份已滚动续期的 Cookie。

## 4. 需求项

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R1 | 后台自动领取 | 每个刷新周期内，启用账号自动调用 check；当日可达 1500 分 |
| R2 | 先领后查 | 同一轮内领取必须先于余额查询，否则闸门读到旧余额 |
| R3 | 跨日正确 | 按北京时间（UTC+8）切日，凌晨领取不得算到前一天 |
| R4 | 不重复发放 | 同日多次调用只产生 1 条记录（依赖上游幂等，插件不额外去重） |
| R4b | 到账判据正确 | 不得用 `pass` 判发放；必须由明细中「当天 + 有余额」的每日登录条目确认 |
| R5 | 失败隔离 | 领取失败不影响本轮余额刷新 |
| R6 | 面板可见 | 每账号显示「今日已领 / 未领 / 领取失败」三态 |
| R7 | 手动补领 | 面板按钮可单账号立即补领，并回传最新余额 |
| R8 | 禁用账号不领 | 禁用账号不触发领取，避免无意义上游调用 |

## 5. 非范围

- 不实现「邀请奖励」「首次注册奖励」「成就系统任务」等其他积分获取方式
  （`incentive/user_task/list` 实测返回空列表，当前账号无可做任务）。
- 不改动既有积分红线、换号、冷却语义。
- 不引入任何新配置项（领取跟随既有刷新周期，默认恒开）。

## 6. 部署要求

用户同时要求「把号都导入到生产」。查证后明确其含义为
**启用 `coze-provider` 插件，让已在位的 9 个账号回归路由**：

- 9 个账号文件已在生产容器 `/root/.antigravity_cockpit/coze_accounts/`；
- 但生效配置中 `coze-provider` 为 `"enabled": false`，
  所有账号 `last_renew_at` 冻结在 2026-10-23T01:32:50；
- 不需要导入新凭据。

## 7. 风险与边界

| 风险 | 处置 |
|---|---|
| 上游 check 端点改版或下线 | 领取失败只记日志，不阻断余额刷新；面板显示领取失败原因 |
| 上游风控（高频调用） | 跟随 5 分钟刷新周期（每日每账号约 288 次），与网页端加载积分页同频；实测无异常 |
| `pass=false` 被误判成「未发放」 | **已实测推翻**：pass 与发放无关。改为明细确认，pass 仅作排查线索 |
| 请求失败时用旧明细误判今日已领 | 请求失败即不做确认，保留原状态 |
| 跨日判定用时区库 | 用固定 UTC+8 偏移，不依赖 tzdata |
