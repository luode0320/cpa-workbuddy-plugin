# workbuddy 高峰期拥堵识别与失败分类修正

- 日期：2026-10-31
- 状态：需求已确认，已实施（待发布）
- 来源：用户当轮指令「workbuddy客户端有一个模型拥堵的状态, 我们插件现在时看不到的, 这个可以拿到吗? 因为我们发现到了高峰期的时候, 拥堵几乎导致无法使用? 分析一下。」
- 影响插件：`workbuddy-provider`（用户裁定只做这一个，其余同族插件另立需求）
- 参考实现：`https://github.com/linguo2625469/workbuddy2api-panel`（用户指定借鉴对象）

## 1. 现象

每天高峰期（北京时间 15:00–17:00）workbuddy 渠道几乎无法使用：请求大面积失败，且失败后账号池迅速萎缩，越到高峰后期越难恢复。用户的原话是「拥堵几乎导致无法使用」。

用户同时提出一个观察：WorkBuddy 客户端自身会显示「模型拥堵」状态，而我们的插件完全看不到这个状态。

## 2. 根因（静态证据链）

问题不是「看不到拥堵状态」这一件事，而是**拥堵被系统性误判成账号故障，形成雪崩**。四条缺陷串成一条放大链：

| 编号 | 缺陷 | 位置（修复前） | 后果 |
|---|---|---|---|
| D1 | SSE 错误帧只认 `{"error":...}` 包裹，顶层业务码帧 `{"code":6004,...}` 被当正常正文透传 | `workbuddy/stream.go` `sseErrorFrame` | 拥堵帧既不记账也不换号，客户端收到一段无意义 JSON |
| D2 | 5xx 不在同请求内换号，直接向用户报错 | `workbuddy/stream.go` 换号判据 | 高峰期上游过载通常只影响部分后端，用户承担了第一次必然失败 |
| D3 | 任何一次失败即写盘禁用（无门限） | `workbuddy/accountFailover.go` `recordFailureScoped` | 一次抖动把健康号从宿主路由摘掉，恢复只能等 10 分钟探活 |
| D4 | 探活标记缺失时永久跳过 | `workbuddy/failover_disable.go` `failoverProbeTargets` | 被禁号可能「禁用且永远探不了」，直到人工介入 |

放大链：拥堵 → 6004/6021/5xx 按账号级记账 → 一次即写盘禁用 → 可用池缩小 + 会话亲和被打散 → 剩余账号压力上升 → 更多拥堵 → 全池 `auth_unavailable`。

D4 不是推测：`doc/4-bugs/2026-10-29_160000_deepseek-v4.1-flash推理变慢主力快号禁用与会话亲和打散根因诊断.md` 已记录主力快号单次 429 后被禁 8 小时、零探活的生产实证。

## 3. 上游拥堵的两种语义（参考实现依据）

参考仓库在 2026-10-15 实案后固化了两种拥堵的区分，本需求沿用同一口径：

| 业务码 / 文案 | 语义 | 正确处置 |
|---|---|---|
| `6021` 或 `queue.full` / `queue full` | **渠道级容量满载**：推理集群排队队列打满 | 不罚号、不换号（换任何账号都会撞同一堵墙，换号只放大请求量），向客户端透传可读提示 |
| `6004` | **模型级限流**：账号整体健康，只是该模型当下被限 | 只隔离「该账号 × 该模型」，换模型即可用；不得禁用账号 |
| 其余 5xx / 传输错误 / 限流文案 | 瞬时抖动 | 同请求换号 + 内存阶梯冷却；连续多次才写盘禁用 |

`6004`/`6021` 在我方生产日志中尚无取证（拥堵窗口未覆盖本轮工作时间），判据来自参考仓库代码注释记录的实案，属**外部证据**，需在下一个拥堵窗口用生产日志补齐（见第 6 节）。

## 4. 目标

1. 流式路径能识别顶层业务码帧，拥堵帧不再被当正文透传。
2. `6021` / `queue.full` 归为「上游拥堵」维度：不冷却、不禁用、不换号，透传可读原因。
3. `6004` 归为「模型级限流」维度：只冷却该账号×模型，不禁用账号。
4. 写盘禁用加连续失败门限（默认 3 次），且门限只作用于瞬时类失败——确定性失败（401/403/404/405、402 额度、11128 拦截）不等门限。
5. 5xx 纳入同请求换号，让用户不必承受上游过载的第一跳失败。
6. 探活标记缺失时回落兜底模型，消除「禁用且永远探不了」的死角。

## 5. 范围

### 做

- `workbuddy/stream.go`：顶层业务码帧识别、6021 分支、5xx 换号。
- `workbuddy/failure_class.go`：新增 `failureScopeModelRateLimit` / `failureScopeUpstreamBusy` 两个维度、业务码识别纯函数、瞬时/确定性判据。
- `workbuddy/accountFailover.go`：按维度决定是否记账/是否写盘禁用、连续失败门限、`shouldRotateOnStatus`。
- `workbuddy/failover_disable.go`：探活兜底模型。
- `workbuddy/policy.go`：拥堵提示文案常量。
- `workbuddy/usage_config.go` + `workbuddy/main.go`：新增配置项 `failover_disable_min_count`（默认 3，填 1 恢复旧行为）。
- 单测与变异验证。

### 不做

- 其他插件（qoderwork / workbuddy-ai / traework / qoder-ai / zcode 等）
- 宿主 CPA 侧任何改动
- 「模型拥堵」状态的**展示**（面板 UI 显示拥堵状态）——本轮只修失败处置，不做可视化
- 会话亲和打散问题（`doc/4-bugs/2026-10-29` 缺陷 B，另立需求）
- 慢速冷却阈值调整

E1 不阻塞本轮修复：本轮修的是「拥堵被误判为账号故障」这一确定根因，静态证据链完整（D1–D4 均可从代码直接读出），且 D4 已有生产实证。若上游实际不使用 6004/6021，最坏情况是退化为「按普通限流处理」——仍受新的门限保护，不会重回「一次失败即禁用」。

## 7. 验收标准

1. cgo-shim `build` / `vet` / `test` 全绿。
2. 变异测试：对 5 个关键判据分别注入反向改动，全部应被测试杀死。
3. 顶层业务码帧、6021、6004、门限、探活兜底各有独立用例。
4. 生产热重载后 `.so` sha256 与本地 release zip 逐字节一致，日志出现 `hot reloaded`。
