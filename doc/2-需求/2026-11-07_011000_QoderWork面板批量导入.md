# QoderWork 面板批量导入

- 日期：2026-11-07
- 状态：已实施（待发布）
- 来源：用户当轮指令「我们希望 QoderWork 改成支持批量 JSON 导入」（附生产面板截图：导入弹窗只有单个 PAT 输入框 + 备份恢复文本框）
- 影响插件：`qoderwork-provider`（0.12.7 → 0.13.0）
- 参考实现：`workbuddy` / `traework` 面板已有的多文件批量导入（同族插件能力对齐）

## 1. 现状与缺口

用户需要的「批量」在旧实现里只有三条不完整的路径：

| 入口 | 旧行为 | 缺口 |
|---|---|---|
| `导入 QoderWork 凭证` 弹窗上层 | 单个 `pt-` PAT 输入框，一次一个 | 批量铺号必须逐个粘贴 |
| 同弹窗「从备份恢复」 | 一个 textarea，`expandCredentials` 支持导出包装 / 裸数组 / 单条 | 无文件选择器；不认 PAT 列表；无法混排；入口文案与「批量」无关 |
| `导出备份` / `导出 ZIP` | 导出侧能力完整 | 导入侧不能直接吃 ZIP 里的多文件 |

对比同族的 `workbuddy` 与 `traework`：两者都已具备「一次多选 .json 文件 + 统一 textarea + 逐条串行 + 失败明细」，qoderwork 是唯一缺这一层的插件。这是能力差距，不是新设计。

## 2. 需求口径

「批量 JSON 导入」按最宽容解释落地，覆盖用户手上可能存在的全部数据形态，避免二次返工：

1. **多文件**：一次选择多个 `.json` / `.jsonl` / `.txt`（单文件 ≤ 2MB），选中即展开为逐条待导入项
2. **PAT 列表**：每行一个 `pt-`，一行内用逗号/空格分隔多个也认
3. **凭据 JSON**：单个嵌套 `{auth,account}`、flat `{accessToken,uid}`、凭据数组
4. **导出备份包装**：`{accounts:[{credential:{...}}]}`
5. **PAT 容器**：`{pats:[]}` / `{tokens:[]}`（外部批量工具常见形态）
6. **JSONL**：每行一个 JSON 对象
7. **混排**：以上任意组合出现在同一份输入里（整体 JSON 解析失败后退化为逐行解析）

## 3. 方案

### 3.1 判定顺序（关键）

解析必须**先判断「是不是完整凭据」再判断「是不是 PAT」**：

```
有 accessToken（nested 或 flat） → cred（离线回灌）
accounts[] 包装               → 逐条展开为 cred
pats[] / tokens[] 容器        → 逐条当 PAT
有 personalToken / pat 字段   → pat（需上游换 token）
有 auth / account / uid 字段  → cred（结构待后端校验）
其他对象                      → bad（不硬当凭据）
```

顺序反了的后果：带 `personalToken` 的完整凭据被当成 PAT，丢掉已有的 `accessToken` 会话令牌并白打一次上游换 token。该缺陷已用专项用例锁定。

### 3.2 端点分流

| 项类型 | 端点 | 语义 |
|---|---|---|
| PAT | `POST /import` | 上游换 jobToken（jt-/jrt-），再落盘 |
| 凭据 | `POST /import-cred` | 不换 token，原始物理文件按 `parseStored` 结构校验后直接落盘 |

后端零改动。不新增批量端点，理由：逐条调用已有端点失败隔离最好、进度可逐项呈现、与 workbuddy/traework 架构一致；PAT 换 token 本身串行，批量端点的收益仅是少数 HTTP 往返。

### 3.3 执行与容错

- 逐条串行，项间 150ms 间隔（PAT 会打上游，避免突发）
- 单项失败不中断后续项；业务失败（`success:false`）与网络异常（throw）都记入失败明细
- **批内去重**：同一 PAT 字符串 / 同一凭据 JSON 只导一次。重复粘贴在「全量重贴重试」时是常态，不去重会重复换 token
- **失败收敛**：部分成功时把输入框自动改写为「仅失败项」，用户点重试不会重复导入已成功的账号（服务端按 uid 覆盖写本身幂等，但重复导入会拖慢批量并让成功计数失真）
- 全部成功才关闭弹窗并清空输入；有失败则保留弹窗与失败明细

## 5. 边界

- 只做前端批量，不新增 `/import-batch` 后端端点
- 不做跨批次去重：已成功账号重复导入是覆盖写（幂等），不做服务端查重
- ZIP 不能直接拖入：需先解压（浏览器无法在没有 zip 库的前提下解包；导出侧已提供 ZIP 供人工分发）
- 未做导入并发：PAT 换 token 是上游写操作，串行是刻意的
- 失败项明细不做持久化：关闭弹窗即丢失，但输入框已收敛为失败项，可在关闭前重试
- 逐条写盘会逐条触发宿主 auth watcher 事件（N 个账号 = N 次文件写入），属既有架构行为（workbuddy / traework 同构），本轮不做批量合并写入
