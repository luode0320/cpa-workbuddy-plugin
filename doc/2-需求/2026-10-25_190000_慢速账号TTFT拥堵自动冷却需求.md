# 慢速账号 TTFT 拥堵自动冷却需求

- 时间：2026-10-25 19:00 (GMT+8)
- 提出人：luode
- 状态：已实现

## 1. 背景与问题

用户从生产 Token 用量面板观察到：同一模型 `deepseek-v4.1-flash` 的请求里，
**首字延迟（TTFT）在 13s ~ 21s 之间明显分层**，且慢的那一批集中在固定来源账号。
用户诉求原话：

> 生产的有些账号其实有问题的，可能比较拥堵，我们有方案可以对这些拥堵的账号进行监控到，
> 然后进入冷却吗？因为这些慢速的账号会拉低请求的响应速度。

即：**慢请求不是失败，现有失败冷却完全抓不到**。一个上游拥堵但每次都能返回 200 的账号，
会一直留在路由池里持续拉低整体响应速度。

## 2. 现状侦察结论（本轮真实读取）

| 环节 | 现状 | 证据 |
| --- | --- | --- |
| TTFT 采集 | 已有，8 个 provider 插件齐全 | `workbuddy/usage.go:266` `sseUsageCollector.firstByteAt`；`:291` `ttftNS()` |
| 上报链路 | 已有，`ttft_ns` 进 NDJSON feed | `workbuddy/usage_feed.go:157` |
| 面板聚合 | 已有，`Source` 即账号，可按 `average_ttft_ns` 排序 | `token-usage-tracker/usage_stats/aggregate.go:194`、`api.go:516` |
| 路由消费延迟 | **完全没有** | `accountFailover.go` / `scheduler.go` / `failover_retry.go` 零引用 `ttft` |

结论：**观测面已存在，缺的只是「观测 → 冷却」这一根线。**

## 3. 两个必须先纠正的判读

### 3.1 绝对阈值不可用

生产同一批请求 **input 全部在 33~34 万 tokens**（830 次请求总输入 1.76 亿）。
这么大的上下文，prefill 本身就落在十几秒量级，13~21s 的 TTFT **不必然代表账号拥堵**。

若按「TTFT > 10s 就冷却」这类绝对阈值上线，会把整池健康账号全部禁掉。
**判据必须是同模型横向相对对比。**

### 3.2 现有 TTFT 数据带计时污染

`started` 在 executor 入口只取一次（`workbuddy/main.go:728`、`:901`），跨 attempt 复用；
而 `collector` 每轮新建（`workbuddy/stream.go:218`）。

后果：A 号失败耗时 10s → 换到 B 号、B 首帧 2s，记录下来的 `ttft_ns` 是 **12s**，
**A 号的失败耗时被算到健康的 B 号头上**。慢速判据直接吃这个数会误禁健康账号。
本需求必须在启用判据前先修这一处。

## 4. 需求目标

1. 能在**账号 × 模型**维度识别「显著慢于同池同模型水平」的账号；
2. 识别后该账号在该模型上**进入冷却**，后续请求不再路由给它；
3. 冷却**到期自动恢复**，无需人工介入，也无需探活；
4. 全池都慢时**不误伤**（上游整体拥堵不是账号问题）；
5. 全池都被判慢时**有兜底**，不会把调度饿死；
6. 面板可观测：能看出某账号当前是否慢、慢多少倍。

## 5. 需求边界

### 5.1 范围内

- `workbuddy-provider` 插件（当前生产主力，截图数据来源）；
- 账号 × 模型级冷却状态机（新增，状态独立）；
- 四处路由过滤接入（调度 / 换号 / 两处前置拦截）；
- per-attempt TTFT 计时修复；
- 非流式路径 TTFT 采集补齐（当前恒为 0）；
- 5 个配置键 + ConfigFields 登记；
- 面板暴露慢速冷却状态与相对倍数。

### 5.2 范围外

- 其它 provider 插件（qoderwork / traework / qoder-ai / workbuddy-ai 等）——
  机制先在 workbuddy 验证成立，再按需横向复制；
- 写盘禁用（`disabled: true`）——慢是性能问题不是故障，写盘禁用会要求探活才能恢复，
  对慢账号过重；
- 自动调整上游模型选择、自动切换 provider；
- 基于 TPS / 总耗时（`latency_ms`）的判定——总耗时受输出长度影响，不可比；
- 历史 TTFT 数据回灌。

## 6. 验收条件

| ID | 条件 | 验证方式 |
| --- | --- | --- |
| AC-001 | 同模型下某账号 TTFT 中位数超过全池基准 N 倍且超过绝对下限时，进入冷却 | 单测：构造 1 慢 2 快三账号，慢号被冷却，快号不被冷却 |
| AC-002 | 冷却中的账号在该模型上被调度 / 换号 / 两处前置拦截跳过 | 单测：`slowCoolingDown` 返回 true 时四处过滤均命中 |
| AC-003 | 冷却到期自动放行，无需任何外部动作 | 单测：注入时间推进越过 `cooldownUntil` 后判定为 false |
| AC-004 | 全池同模型都慢时无人被冷却（基准随之抬高） | 单测：三账号 TTFT 同为 20s，全部不冷却 |
| AC-005 | 样本数不足时不判定 | 单测：样本数 1 < minSamples 时返回 false |
| AC-006 | 全池同模型都被判冷却时放开一半，不饿死调度 | 单测：三账号全部达阈值，冷却后至少一个可路由 |
| AC-007 | 失败请求不计入慢速样本 | 单测：`failed=true` 时样本数不增长 |
| AC-008 | 换号后 TTFT 只统计当前 attempt 的耗时 | 单测：模拟 attempt 0 慢失败 + attempt 1 快成功，记录值不叠加 |
| AC-009 | 配置键全部登记进 ConfigFields | 单测：遍历 `wbRegistration().Metadata.ConfigFields` 断言 5 个键存在 |
| AC-010 | 默认值下不会误禁生产账号 | 生产观察：上线后 `slow_cooling` 计数与禁用数不出现异常批量增长 |

## 7. 关键判据定义

**基准（baseline）**：同模型下所有「样本数达标账号」的 TTFT 中位数的中位数。

**判定为慢**（三个条件同时成立）：

1. 该账号该模型的窗口内 TTFT 中位数 ≥ baseline × `slow_ttft_ratio_x10 / 10`；
2. 该账号中位数 ≥ `slow_min_ttft_ms`（绝对下限，防止低延迟场景下的相对放大误判）；
3. 该账号窗口内样本数 ≥ `slow_min_samples`（防止单条毛刺误判）。

**为什么用相对判据而不是绝对判据**：见 §3.1。全池一起变慢时 baseline 同步抬高，
没有人被判慢——这正确表达了「上游整体拥堵，不是某个账号的问题」。

## 8. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 快账号被误判为慢（基准被单个极快账号拉低） | 用中位数而非最小值作基准；加绝对下限 `slow_min_ttft_ms`；样本数门槛 |
| 慢账号被冷却后全池无号可用 | 全冷检查 + 放开一半（复用轮换的防抽干语义） |
| 计时污染导致归因错位 | 先修 per-attempt 计时（§3.2），并有 AC-008 锁定 |
| 缓存命中率差异被误读为慢 | 判据按 `账号 × 模型` 维度，不跨模型比较 |
| 默认参数不适合生产 | 全部可配置；`slow_account_enabled: false` 可整体关闭 |
