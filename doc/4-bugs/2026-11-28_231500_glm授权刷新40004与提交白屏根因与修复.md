# 2026-11-28_231500 glm 授权刷新 40004 与提交后白屏根因与修复

## 一、现象

用户在生产 `https://cpa.luode.vip` 完成 `glm-provider` 授权时遇到两个串联故障：

1. **授权页提交后整页白屏**：地址栏停在 `/v0/resource/plugins/glm-provider/login?state=glm-17958729883435297`，主内容区完全空白，无任何文字。
2. **令牌校验失败**：白屏之前的表单提交返回
   ```
   refresh_token 校验失败: refresh status 400: {"status":40004,"message":"bad request(40004)","result":null,"rid":"17958777673209997001795877767320999"}
   ```
   即上游 `POST https://chatglm.cn/chatglm/user-api/user/refresh` 直接拒绝。

用户提供的凭据经 JWT 载荷解读为：`sub=用户_BodEoe`、`exp=1811407521`（2027-05-25）、`iat=1795855521`（2026-11-28 22:45）、`device_id=12b4933d6acd4dcdaf0b1e828fad00f2`、`type=refresh`。令牌**当时刚签发且未过期**，排除凭据本身失效。

## 二、复现

两个问题可独立复现，互不依赖：

| 编号 | 复现动作 | 观测结果 |
|---|---|---|
| BUG-1 | `POST /v0/resource/plugins/glm-provider/login/callback?state=...` | `HTTP 404`，`size_download=0` |
| BUG-2 | `POST /v0/resource/plugins/glm-provider/login/callback` 携带真实 `X-GLM-RefreshToken` | `HTTP 200` 但页面内容为「令牌校验失败 / refresh status 400 / 40004」 |

对照：同一 callback 用 `GET` 请求 → `HTTP 200`，`446` 字节正常错误页。说明路由本身只接受 GET。

## 三、根因

### 3.1 BUG-1 白屏：POST 打到了只接受 GET 的 resource 路由

`glm/login.go` 的授权页脚本原为：

```js
fetch(CALLBACK,{method:"POST",headers:h,credentials:"omit"})
  .then(function(r){return r.text()})
  .then(function(t){document.open();document.write(t);document.close()})
```

而插件 resource 路由（`/v0/resource/plugins/<id>/...`）在宿主侧只注册了 GET，POST 直接 404 且响应体为空。前端无条件执行 `document.open(); document.write(""); document.close()`，把已经渲染好的表单整页替换成空文档 —— **白屏不是没渲染，而是被空响应体覆盖**。

之所以命令行走 `GET` 能看到正常页面、而浏览器走 `POST` 一定白屏，差异只在这一点。

### 3.2 BUG-2 40004：`X-Device-Id` 发了随机串

`glm/token.go` 的 `requestToken` 原实现：

```go
sign := generateSign(cfg.SignSecret, time.Now().UnixMilli(), newNonce())
...
req.Header = refreshHeaders(refreshToken, sign, newNonce())   // ← 随机设备标识
```

`X-Device-Id` 被填入 `newNonce()` 的随机串。上游对该头做**与 `refresh_token` 载荷内 `device_id` 的一致性校验**，随机值必被判参数非法，返回 `40004 bad request`。

用真实令牌做的六组探针矩阵给出了决定性证据（同一令牌、同一分钟、仅改请求参数）：

| 探针 | `X-Device-Id` | 其它差异 | HTTP | 结果 |
|---|---|---|---|---|
| P1 | **随机串**（原实现） | — | 400 | `40004` 失败 |
| P2 | **令牌内 `device_id`** | — | 200 | `access_token` 成功返回 |
| P3 | 令牌内 `device_id` | `Accept: application/json` | 200 | 成功 |
| P4 | 令牌内 `device_id` | 去掉签名头 | 400 | `40011`（签名必需） |
| P5 | 令牌内 `device_id` | 空 body | 200 | 成功 |
| P6 | 令牌内 `device_id` | json + 空 body | 200 | 成功 |

结论收敛到单变量：**只要 `X-Device-Id` 与载荷一致就成功，与之无关的 `Accept` 和 body 形态都不影响结果；签名头是另一条独立必需项（缺失报 40011）**。

### 3.3 追问：对话链路同源失效

修完 3.2 后授权成功（账号 `glm Ji4HOg` 导入），但真实对话仍返回 500：

```json
{"error":{"message":"upstream status 400: {\"status\":40004,...}","code":"internal_server_error"}}
```

追踪 `glm/completion.go:163`：

```go
h := refreshHeaders("", sign, newNonce())   // ← 又是随机设备标识
```

即对话端点 `/chatglm/backend-api/assistant/stream` 存在与刷新端点**完全同源**的缺陷。用同一 access_token 做两组对照：

| 探针 | `X-Device-Id` | HTTP | 结果 |
|---|---|---|---|
| C1 | 随机串（原实现） | 400 | `40004` |
| C2 | 令牌内 `device_id` | 200 | SSE 正常，首帧 `status:"init"` 并带 `conversation_id` |

结论：`device_id` 一致性校验是**整站级**要求，刷新与对话两条链路都必须满足。

## 四、修复

### 4.1 `glm/token.go`

新增 `deviceIDFromRefreshToken`，从 JWT 第二段 base64url 载荷解析 `device_id`：

```go
func deviceIDFromRefreshToken(refreshToken string) string {
	parts := strings.Split(refreshToken, ".")
	if len(parts) != 3 {
		return ""
	}
	payload, err := base64.RawURLEncoding.DecodeString(parts[1])
	if err != nil {
		return ""
	}
	var claims struct {
		DeviceID string `json:"device_id"`
	}
	if err := json.Unmarshal(payload, &claims); err != nil {
		return ""
	}
	return strings.TrimSpace(claims.DeviceID)
}
```

`requestToken` 改为用解析值，并在解析失败时**在请求上游之前**就给出可行动提示：

```go
deviceID := deviceIDFromRefreshToken(refreshToken)
if deviceID == "" {
	return nil, fmt.Errorf("refresh_token 缺少 device_id，请从 chatglm.cn 重新复制")
}
...
req.Header = refreshHeaders(refreshToken, sign, deviceID)
```

### 4.2 `glm/login.go`

表单提交改为 `GET` + 请求头回传令牌（同源请求不触发 CORS 预检，令牌不进 URL、不进浏览器历史与访问日志）：

```js
fetch(CALLBACK,{method:"GET",headers:h,credentials:"omit",cache:"no-store"})
  .then(function(r){return r.text().then(function(t){return {ok:r.ok,status:r.status,body:t}})})
  .then(function(res){
    if(!res.ok||!res.body){btn.disabled=false;msg.className="msg err";msg.textContent="回调失败 HTTP "+res.status;return}
    document.open();document.write(res.body);document.close();
  })
```

新增状态码与响应体判空：失败时就地报错，不再把页面清空。

### 4.3 测试夹具

原三个测试用 `"test-refresh"` 这类非 JWT 字符串，新校验会拒绝。引入 JWT 形夹具：

并新增：
- `TestDeviceIDFromRefreshToken`：合法载荷 / 非三段式 / 载荷无 `device_id` / 载荷非法 JSON 四种边界。
- `TestRequestTokenRejectsMissingDeviceID`：无 `device_id` 时在发请求前即报错。
- `TestRequestTokenMock` 追加断言 `X-Device-Id` 必须等于载荷值，防止回退。

	return nil, fmt.Errorf("access_token 缺少 device_id，请重新授权")

## 六、教训

1. **「页面白屏」先查响应体，不要先怀疑渲染**。本次白屏是 `document.write("")` 的结果：上游 404 给空体，前端无条件覆盖文档。凡「提交后」白屏，第一嫌疑是回调响应为空而非 HTML 有误。
2. **resource 路由的 GET-only 约束在建前端调用时就是硬约束**。同一个 URL 用 curl GET 能返回完整页面，会让人误判「接口是通的」，但前端用的是 POST —— 通道方法本身必须核对，不能只核对内容。
3. **上游"伪装头"里凡是能对上实物的一律不要伪造**。`X-Device-Id` 看起来像随手可造的指纹头，实际是与令牌载荷绑定的强校验字段；这类头应优先从凭据自身派生，造不出来就必须查协议，不能拿随机值顶上。
4. **错误码要能区分"我的参数错"与"用户的令牌错"**。修复后 `缺少 device_id` 直接给可行动提示，不再把上游 `40004` 原样抛给用户。
