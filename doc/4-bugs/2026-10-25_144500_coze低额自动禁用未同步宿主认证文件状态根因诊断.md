# coze 低额自动禁用未同步宿主认证文件状态根因诊断

- 日期：2026-10-25
- 状态：根因已定位（未修复）
- 影响版本：coze-provider 0.6.1 及以前（自低额自动禁用机制引入起）
- 环境：生产 cpa（45.207.222.65 / 容器 `cli-proxy-api`）

## 1. 现象

生产 coze 插件面板中，4 个账号带有「低额自动禁用」徽标（用户 174655 / 800509 / 650744 / 一个 0 分号），
卡片底部按钮显示「启用」（即插件认为该号已禁用）。

但同一宿主的「认证文件管理」页：
- 选择 `coze-provider` 标签 + 「停用」筛选，结果为 **「没有匹配的配置文件」**；
- 页面汇总仍是「69 个启用 · 1 个异常」，coze 的 14 个账号全部按**启用**统计。

两侧状态互相矛盾：插件说禁用，宿主说启用。

## 3. 根因

### 3.1 直接根因

coze 的 `authDataForLogin`（[coze/login.go:303](file:///f:/cpa-plugin/coze/login.go#L303)）只把 `disabled`
放进了 `Metadata` 映射，**从未设置 `pluginapi.AuthData` 的顶层 `Disabled` 字段**：

```go
return pluginapi.AuthData{
    Provider:    providerName,
    ID:          fileName,
    FileName:    fileName,
    Label:       sa.Label,
    StorageJSON: storage,
    Metadata: map[string]any{
        "type":  ...,
        "disabled": sa.Disabled,   // 只有这一处
        ...
    },
}
```

宿主的 `pluginAuthDataToCoreAuth`（[auth_provider.go:636](/tmp/cpahost/cpa/internal/pluginhost/auth_provider.go#L636)）
判定状态时**只读 `data.Disabled`**：

```go
status := coreauth.StatusActive
if data.Disabled {
    status = coreauth.StatusDisabled
}
...
Disabled: data.Disabled,
```

Metadata 里的 `"disabled"` 在这条路径上完全不参与 `Status` 计算，随后被
`coreauth.NormalizeCredentialMetadata` 当作普通凭据元数据处理。
结果：`auth.parse` 每次返回的都是 `Disabled=false / Status=active`。

### 3.2 为什么「Metadata 回传」这条路对 coze 失效

0.6.1 的修复思路是「让 `auth.parse` 的 Metadata 带上 `disabled`，宿主重建文件时原样写回」。
该结论对**文件重建路径**成立（`internal/watcher/synthesizer/file.go:107` 会读 `metadata["disabled"]`），
但对**状态判定路径**不成立 —— 后者只认 `AuthData.Disabled` 顶层字段。两条路径读的不是同一个来源。

### 3.3 MySQL 中 `disabled=false` 与 `low_credit_disable=true` 的来源

`MySQLStore.Save`（[mysqlstore.go:240](/tmp/cpahost/cpa/internal/store/mysqlstore.go#L240)）在写盘前执行：

```go
auth.Metadata["disabled"] = auth.Disabled   // 用宿主内存态覆盖插件元数据
```

而 `auth.Disabled` 来自 `pluginAuthDataToCoreAuth` 的 `data.Disabled`（恒 false）。
`mergedStorageJSON` 再把这份 Metadata 合并进 StorageJSON 一起落盘/入库 —— 于是
`disabled:false` 覆盖掉插件的 `disabled:true`，`low_credit_disable:true` 因宿主不认识而原样保留。
这精确解释了 2.3 节观察到的矛盾组合。

> 注：磁盘当前仍是 `disabled:true`，说明本轮的插件直写发生在宿主 persist 之后（写入未被覆盖）；
> 一旦下一次宿主 persist 落在插件写盘之后，磁盘上的 `true` 也会被抹成 `false` ——
> 这正是 workbuddy 0.20.x 系列曾踩过的同一类竞态。

## 4. 影响面

| 维度 | 影响 | 严重度 |
|---|---|---|
| 真实流量路由 | **无影响**。`publishCreditPool` 以 `!acc.Disabled` 计算 `usable`，闸门在宿主选中前已排除低额号；6 小时日志中「转由宿主换号」0 次即为证据 | 无 |
| 宿主面板可见性 | 4 个已禁用账号在「认证文件管理」页显示为启用；按「停用」筛选查不到任何 coze 账号 | 中 |
| 宿主调度器候选池 | 低额号仍是宿主候选（宿主只看 `Status`），理论上可被宿主优先选中后再由插件闸门踢回 → 每次多一次插件内失败路径。当前未观测到成因浪费（0 次换号日志），属**潜在**开销 | 低 |
| 状态持久化可靠性 | 一旦宿主 persist 晚于插件写盘，磁盘 `disabled:true` 会被抹为 false，同时 `low_credit_disable` 保留 → 巡检仍能识别归属并重新禁用（自愈），但会形成反复抖动 | 中 |
| 人工运维 | 无法从宿主界面确认哪些号被自动禁用，也无法用宿主「停用」筛选定位 | 中 |

## 5. 修复方案（建议）

### 5.1 核心改动（1 行 + 测试）

在 `authDataForLogin` 中补设顶层字段：

```go
return pluginapi.AuthData{
    Provider:    providerName,
    ID:          fileName,
    FileName:    fileName,
    Label:       sa.Label,
    Disabled:    sa.Disabled,   // 新增：宿主只认这个字段判 Status
    StorageJSON: storage,
    Metadata:    ...,
}
```

覆盖全部三个调用点，因为都走同一个函数：
- `handleParseAuth`（宿主扫描/重建时）→ [login.go:362](file:///f:/cpa-plugin/coze/login.go#L362)
- 登录成功返回 → [login.go:178](file:///f:/cpa-plugin/coze/login.go#L178)
- `auth.refresh` 返回 → [login.go:402](file:///f:/cpa-plugin/coze/login.go#L402)

### 5.2 配套测试

1. `TestAuthDataForLogin_CarriesDisabledField`：`Disabled:true` 的账号必须产出 `data.Disabled == true`；
   健康账号必须 `false`（锁死正负两侧）。
2. 端到端：`handleParseAuth` 对 `disabled:true` 的 raw JSON 必须返回 `Auth.Disabled == true`
   —— 这是本次根因的直接回归锚点（现有 `TestAuthParse_RoundTripsDisableState` 只断言 Metadata，覆盖不到）。

### 5.3 不采用的方案

- **改走 `PATCH /v0/management/auth-files/status`**：需要管理密钥注入插件、且会与巡检节奏耦合；
  插件已持有物理路径直写能力，补字段即可，不需要引入新通道。
- **仅靠 Metadata**：已证明无效（3.2 节）。

## 7. 现有测试为何没拦住

`coze/disable_metadata_test.go` 的三个用例全部只断言 `Metadata["disabled"]` 与
`Metadata["low_credit_disable"]`，从未断言 `AuthData.Disabled` 顶层字段。
0.6.1 的「Metadata 回传闭环」结论本身正确但不完整 —— 它只覆盖了宿主重建文件的路径，
漏掉了宿主判定账状态的路径，测试也就按这个不完整结论写了断言。

## 8. 结论

- 这是**实现缺陷**，不是设计问题：禁用状态的真实来源（物理文件）正确，缺的是向宿主传递状态的字段。
- 与 0.6.1 修复同源但不同层：0.6.1 解决「宿主 persist 抹掉顶层键」，本次暴露「宿主从不读 Metadata 判状态」。
- 流量侧自愈机制（巡检闸门 + 归属标记）完好，用户无感知故障；但宿主监控面失真，人工无法据此运维。
- 修复成本极低（1 行 + 测试），建议随下一个 coze 补丁版本发布。
