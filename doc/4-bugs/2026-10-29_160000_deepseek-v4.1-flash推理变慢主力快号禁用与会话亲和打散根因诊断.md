# deepseek-v4.1-flash 16 点后推理变慢：主力快号被禁用 + 会话亲和被打散（根因诊断）

- 编号：BUG-WORKBUDDY-DEEPSEEK-FLASH-SLOWDOWN-20261029
- 侦察时间：2026-10-29 23:00 — 2026-10-30 00:05
- 状态：**根因已确证（双因叠加），非上游故障、非主机资源、非 CPA 并发**
- 生产目标：155.103.157.254（`cpa-server-new`），容器 `cli-proxy-api`，workbuddy-provider **0.21.6**（容器 2026-10-28 18:45 启动后未重启，全程热更新）

## 1. 现象

用户报「下午 16 点左右大量会话请求进来后，deepseek-v4.1-flash 推理很慢」。

用量 feed 实测（`token-usage-feed.ndjson`，TTFT 中位，10 分钟粒度）：

| --- | --- | --- |

| 21:40-23:00 | 2335-2799ms | 恢复 |

即 TTFT 从 ~1.7s 抬到 ~3.0-3.5s，**约 1.8-2 倍**。

**用户说的「16 点开始大量会话请求进来」确有实测依据**——10 分钟请求量在 16:10 前后跳增约 64%：

## 2. 根因（双因叠加，按贡献排序）

### 2.1 主因：主力快号 15:48:53 被一次 429 禁用，8 小时未恢复

**这是变慢的起点，早于 16 点整。**

`1d7eca06` 是当天绝对的主力账号：

| 指标 | 值 |
| --- | --- |
| 请求量 | 1699 条（14:30-15:48，占该窗口 deepseek 请求 58%-100%） |
| TTFT 中位 | **1825ms**（全池最快） |
| 吞吐中位 | 61-87k tok/s |
| 生命周期 | 02:58:28 起 → **15:48:53 末条** |

**末条请求就是致命一击**：15:48:53 一条请求 `failed=True, status=429, latency=261ms, ttft=0`，随即：

```
2026/10/29 15:48:53 [workbuddy] failover disabled account via cpa api:
    auth=1d7eca06-f515-4420-acc6-20da4951ea67 model=deepseek-v4.1-flash
```

**至今（10-30 00:01）仍 `disabled=true`，`failed_count=1 / success_count=131`，`note="CN · 已禁用 · 积分未知"`，且 15:48 之后再无任何 `failover probe` 记录**——探活从未尝试恢复它。

关键代码事实（`workbuddy/failover_disable.go:700-713`）：探活只对「记录了失败模型」的账号执行，`model == ""` 时直接 `failover probe skipped: no failed model recorded` 并跳过。该账号的失败模型记录丢失（账号文件顶层只有 `account/auth/disabled/failed_count/logo/note/provider/success_count/type`，**无 `failover_disable` / `failover_model` 标记**），因此被永久排除在探活之外。

### 2.2 次因：16:42:28 一次配置重载清空会话亲和缓存

```

[2026-10-29 16:42:28] [config_reload.go:141] config successfully reloaded, triggering client reload
```

## 3. 输入长度是放大因素，但不是主因

输入中位随用户会话推进自然增长：

| 时段 | 输入中位 |
| --- | --- |
| 15:00-16:00 | ~93k |
| 16:00-16:42 | ~163k |
| 17:00-21:00 | 177-198k |

TTFT = a + k·input 分段回归折算，「仅输入变长」可解释约 **1.10x**，实测 **1.25-1.28x**——差出的部分由冷账号 prefill 无缓存承担。

双因素控制（间隔<15s 热门 + 同输入档）仍显示劣化：

| 输入档 | 时段 | n | TTFT | 吞吐 |
| --- | --- | --- | --- | --- |
| 150-200k | 15:00-16:00 | 264 | 2067ms | 79123 |
| 150-200k | 16:00-16:42 | 473 | 2643ms | 64587 |
| 150-200k | 21:00-23:30 | 89 | 2616ms | 68648 |

即使同输入档、同为热号，16:00 后仍慢 28%。这部分是**池内账号结构变化**（快号被禁、换入更多慢号）而非单纯冷热。

## 5. 需要修复的两个缺陷

### 缺陷 A：单次 429 即永久禁用主力账号，且探活无法覆盖（严重）

- **现象**：`1d7eca06` 一条 429（261ms）→ `failed_count=1` → 永久 `disabled=true`，8 小时无流量、无探活、无恢复。
- **直接后果**：全池最快账号（1825ms）退出，池内 TTFT 基线整体上移。
- **机理**：探活只针对「记录了失败模型」的账号（`failover_disable.go:700-706`），而该账号文件顶层**无 `failover_disable` / `failover_model` 标记**，探活一律 `skipped: no failed model recorded`。与 0.20.2 修复的「宿主每请求重建 auth 文件抹掉 failover 三键」是同一类问题，但该修复只覆盖 `persistCounterDelta` 的写盘路径，未覆盖「插件被热重载 / 账号被外部改写」后的重建场景。
- **建议**：① 禁用时把失败模型无条件写入账号文件顶层，且在被抹除后由 `carryFailoverKeysIntoMetadata` 以外的路径补回（如 `auth.parse` 出口统一注入）；② 对「已禁用但无失败模型记录」的账号，探活时退化为用其最近成功模型或默认模型探测，而不是永久跳过；③ 单次 429（频率限制，非额度耗尽）不应触发永久禁用，应与 6004/14018 区分处理。
- **影响面**：全天共 10 次 `failover disabled account`，其中 `1d7eca06` 是最严重的一次（唯一的主力快号）。

### 缺陷 B：配置重载清空会话亲和，且用户无感知

- **现象**：`PATCH /v8/management/config` 即使内容是空操作（`0 -> 0` 变更），也会 `triggering client reload` → 重建 101 个 client → 清空亲和缓存。
- **直接后果**：16:42 后亲和命中率 0%，持续 4.5 小时，直到 21 点流量下降后才自然重建。
- **放大效应**：亲和打散使流量铺满 34 个账号，热号优势归零。
- **建议**：① 管理面板上的配置保存（即使是空保存）应跳过 reload（`config changes detected` 为空时直接返回）；② 重载类操作避开业务高峰；③ 重载后如可接受，主动预热亲和或保留既有 session 绑定。

## 6. 证据边界

- **冷账号为何更慢**：feed 中 workbuddy 的缓存字段（`cache_read` / `cached` / `cache_creation`）恒为 0，无法直接观测上游 prefix cache。结论依据是「同账号请求间隔 → TTFT/吞吐」的强相关（2.4 节）与同账号前后对比，属**相关性证据**，非上游缓存命中率的直接实证。
- **16:00-16:42 区间已变慢但亲和仍高**：此段 TTFT 已从 1.7s 到 2.6s，主因是 15:48:53 快号被禁 + 输入从 93k 涨到 163k，而不是亲和。亲和打散是 16:42 之后进一步恶化的原因。二者时间上前后接力，共同构成「16 点开始变慢、17-21 点最差」的完整曲线。
- 16:20:11 慢速冷却触发属机制正常工作的旁证（当时 3516985d median=6005ms），10 分钟后到期恢复，**不是**持续变慢的原因。

## 7. 排查方法沉淀

- **TTFT 必须按输入长度归一化**：绝对毫秒在这个场景会误导（input 33 万 tokens 时 prefill 本身就十几秒）。用 `input_tokens / TTFT秒`（tok/s）才可横比。
- **同账号请求间隔（gap）是账号冷热的可用代理指标**：在缓存字段缺失时，gap → TTFT 的相关性足以支撑判断，但需用「同一批账号前后对比」交叉验证以剥离账号质量差异。
- **会话亲和命中率是配置重载影响面的直接度量**：`grep -c "session-affinity: cache hit"` 除以请求数，逐小时对比即可精确定位清空时刻。
- **单条失败请求足以让主力账号退出池子**：查账号生命周期时，末条请求的 `failed/status_code` 必须单独看，不能只看聚合失败率（当天失败率 0.0%，但就是这一条毁掉了 8 小时）。
