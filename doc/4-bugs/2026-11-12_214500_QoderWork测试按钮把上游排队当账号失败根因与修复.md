# QoderWork 面板「测试」把上游容量排队当账号故障：10605 排队帧的误呈现根因与修复

结论：**报错本身不是故障，是上游容量排队。** 生产原帧 `upstream 200: 403: 10605: {"errorCode":0,"isQueued":true,"modelKey":"qmodel_latest","queueCount":1,"queueType":"p4","retryAfterSeconds":60,"serviceAvailable":true,"subCode":"RESOURCE_LIMIT","waitTime":60}` 里 `serviceAvailable:true` 与 `errorCode:0` 已明确表示服务可用、无业务错误，`isQueued/subCode=RESOURCE_LIMIT` 表示请求被排进 p4 容量队列、前方 1 个请求、建议 60 秒后重试。真正的缺陷在插件侧：`sendActivePingQoder` 把排队帧与账号故障合并成同一个 `error`，`handleTestActiveWithAuth` 再把它包成「活跃测试失败」并把**截断 200 字符的转义 JSON** 直接怼到面板，`panel.html` 只有 ok/err 两态 → 用户看到红色「测试失败」+ 一坨乱码，据此怀疑账号或凭据损坏。影响：面板「测试」按钮与失败探活共用该原语，所有 Qwen 系模型在高峰期都会呈现同一误读；范围：只修呈现语义与错误成型，不改排队判定、不改 failover 计数与冷却；非范围：不改上游排队策略，不引入自动等待重试；完成标准：排队帧在面板呈现为「排队中」+ 可读中文提示 + 结构化重试秒数，非排队失败文案与行为完全不变；术语：`10605` 为上游业务码（`queueBusinessCode`）、`queueFrameError` 为本轮新增的排队错误类型、`upstream_queued` 为结果 map 上的排队标记键。

## 问题现象

- 触发路径：QoderWork 面板 → 账号卡片「测试」→ 模型列表选中 `Qwen4-Max-Preview`。
- 面板表现：红色「测试失败」，详情为 `活跃测试失败 (模型: Qwen4-Max-Preview): upstream 200: 403: 10605: {&#34;errorCode&#34;:0,&#34;isQueued&#34;:true,...}`（截图见本轮会话首条消息）。
- 用户判断：以为账号或凭据坏了，实际账号健康。

## 影响范围

- 受影响入口：`POST /test-active`（面板测试按钮），以及复用同一原语的失败探活（`failover_disable.go` 的 `failoverPingFn = sendActivePingQoder`）。
- 受影响模型：所有映射到 `qmodel_latest` / `qmodel` 等拥挤队列的模型，实测 `Qwen4-Max-Preview`。
- 不受影响：排队判定本身（`isQueueFrame` / `recordAccountFailure` 的「排队帧不计数不冷却」自 0.13.x 起已正确），账号冷却与禁用逻辑（本轮零改动）。

## 出现环境

- 插件：qoderwork-provider 0.13.16（生产，插件面板 `/management.html#/plugin-pages/qoderwork-provider`）。
- 链路：面板 → `/test-active` → `sendActivePingQoder` → COSY 签名 → gateway.qoder.com.cn SSE。
- 时间：2026-11-12 21:07（截图为证），所处时段为上游晚高峰。

## 触发条件

1. 目标模型当前处于容量排队状态（上游返回 HTTP 200 + SSE 错误帧，顶层 `code=403`，内嵌 `10605` + `isQueued:true`）。
2. 面板点「测试」，走 `sendActivePingQoder` 的 SSE 错误帧分支。

两者同时成立即复现；账号与凭据本身健康时同样复现——这正是误读的根源。

## 期望结果

- 排队必须与失败分开呈现：面板应显示「排队中」而非「测试失败」，提示里说清「账号与凭据正常」。
- 提示必须是可读中文，不回显截断转义 JSON；原始帧仍需保留，供排障时取证。
- 结构化字段（建议重试秒数、队列分档、前方请求数、子码、上游模型键）应随结果返回，面板可据此提示「N 秒后可重试」。
- 非排队失败（401 凭据失效、112 权益缺失、断流等）文案与行为必须一字不变。

## 实际结果（修复前）

- 排队帧 → `fmt.Errorf("upstream %d: %s", statusCode, truncateRedacted(msg, 200))` → `handleTestActiveWithAuth` 包成「活跃测试失败」→ 面板 `const ok=!(d&&d.error)` 判定失败 → 红字 + 原始 JSON 截断串。
- 无任何结构化字段，用户无法判断这是排队。
- SSE 层的 `sseErrorFrame` + `unwrapNestedMessage` 已把 4 层嵌套展开成 `403: 10605: {...}`，信息其实齐全，只是在最后一跳被压成了字符串。

## 当前证据

### 证据 1：上游原帧语义自证（截图逐字转录）

```text
活跃测试失败 (模型: Qwen4-Max-Preview): upstream 200: 403: 10605:
{"errorCode":0,"isQueued":true,"modelKey":"qmodel_latest","queueCount":1,
 "queueType":"p4","retryAfterSeconds":60,"serviceAvailable":true,
 "subCode":"RESOURCE_LIMIT","waitTime":60}
```

- `errorCode:0` + `serviceAvailable:true`：服务可用、无业务错误码。
- `isQueued:true` + `queueType:p4` + `queueCount:1`：被排进 p4 队列，前方仅 1 个请求。
- `retryAfterSeconds:60` / `waitTime:60`：上游明确建议 60 秒后重试。
- `modelKey:qmodel_latest`：`Qwen4-Max-Preview` 经运行时映射（`registerUpstreamModelNames` + `lookupUpstreamKey`）落到内部代号 `qmodel_latest`；仓库内无 `Qwen4-Max-Preview` 静态映射，证实该名字来自上游官方 display_name。

### 证据 2：分类与本轮改动前的行为（代码定位）

| 位置 | 修复前行为 |
|---|---|
| `qoderwork/policy.go:515-522` `isQueueFrame` | 已能识别 `isQueued` / `queueCount` / `10605` |
| `qoderwork/accountFailover.go:274` | 排队帧 `return false`（不计数不冷却）——已正确 |
| `qoderwork/active_ping.go:155`（旧行号） | 排队帧被截断成 `upstream 200: 403: 10605: {...}` 普通 error |
| `qoderwork/active_ping.go` `handleTestActiveWithAuth` | 无条件包成「活跃测试失败」，无排队字段 |
| `panel.html` `runTestModel` | 只有 `ok`/`err` 两态，排队必然落进 err |

结论：缺陷不在「识别排队」，而在「识别之后没有把排队语义传到用户态」。

## 根因

**错误成型层丢语义。** `sendActivePingQoder` 把两类性质完全不同的失败压成同一个 `error` 接口值：

1. 账号/凭据真故障（401、112 权益缺失、断流）——需要用户处理。
2. 上游容量排队（200 + 10605 排队帧）——用户只需稍后重试，账号完全健康。

压平后，上层只有 `err != nil` 一个判据，面板只有 `d.error` 一个判据，语义在 `fmt.Errorf` 那一行就永久丢失了；截断 200 字符又把仅剩的线索（`isQueued`/`serviceAvailable`）切成半截转义 JSON，最终呈现为「乱码式失败」。这也是本仓库 `project-cpa-workbuddy-plugin-sse-and-ping-optimization-rules` 规则二早就写明的要求——探活必须如实解析首包错误帧——只在「不误判成功」这一侧落实了，没有在「失败分类」这一侧落实。

## 修复方案

保留一切既有的排队判定与 failover 行为，只补三段语义传递：

1. `policy.go` 新增 `queueFrameInfo` 结构 + `parseQueueFrameInfo(body string) (queueFrameInfo, bool)`：从带任意前缀的错误文本里，对每个 `'{'` 起点用 `json.NewDecoder` 解码第一个完整 JSON 值（Decoder 允许尾随内容，规避 `upstream 200: 403: 10605: ` 前缀无法整体 Unmarshal）；命中 `isQueued || queueCount>0 || subCode!=""` 即返回。
2. `active_ping.go` 新增 `queueFrameError`（`status/info/raw`），**`Error()` 文本与改造前逐字一致**——失败探活日志与历史日志按该文本落盘，换文案会让新旧日志无法对照。`sendActivePingQoder` 的两个失败返回点先判排队，命中则返回 `*queueFrameError`。
3. `handleTestActiveWithAuth` 失败分支改走 `buildActivePingFailure(model, err)`：`errors.As` 命中排队则返回可读中文提示 + `upstream_queued:true` + `detail`（原始错误）+ 按存在性追加 `retry_after_seconds`/`queue_type`/`queue_count`/`sub_code`/`upstream_model`；未命中保持原文案。
4. `panel.html` `runTestModel` 改三态（成功 / 排队 / 失败）：排队用 `warn` 配色、标题「排队中」、toast「上游排队中」，颜色取既有 `--warn`；仅新增 `.import-result .r-hd.warn` 与 `.r-warn` 两条 CSS。

刻意不做的事：

- **不做自动等待 60 秒重试**：`defaultActivePingTimeout` 只有 20 秒装不下，且上游 110 日调用次数上限让自动重试有成本；排队是请求级 + 时段性，规则要求「立即以错误收尾、不在号池内换号消耗」。
- **修改 failover 侧**：排队帧在 `recordAccountFailure` 里本就 `return false`；探活侧 `runFailoverProbeTick` 仍按 `err != nil` 记一次「这次探不通」（不解禁账号），语义与行为均不变。
- **键名不用 `queued`**：`credits_handler.go` 与 `management.go` 的 `queued` 是「后台刷新排队数」，同名会混淆，故用 `upstream_queued`。

## 同族同步范围

`qoder-ai/active_ping.go` 的 `sendActivePingQoder` 与 qoderwork 逐字同构（同 `applyCosyHeaders`、同 20s 超时、同 scanner、同 `truncateRedacted(msg, 200)`），`qwenwork/active_ping.go` 走 maas 路径但错误成型结构同形——两者按「逐函数适配」原则后续同步；`workbuddy`/`workbuddy-ai` 的探活只读首个 512 字节即判成功（不看错误帧），属另一类问题，不在本缺陷范围。

## 修复结果

- 面板对同一排队帧呈现：标题「排队中」、内容「上游排队中 (模型: Qwen4-Max-Preview，队列 p4，前方 1 个请求)，约 60 秒后可重试；账号与凭据正常，属上游容量排队而非测试失败」，黄色 `warn` 配色。
- 原始帧保留在结果 map 的 `detail` 字段，排障时照旧可取。
- 非排队失败文案与行为一字未变（有测试锁定）。
