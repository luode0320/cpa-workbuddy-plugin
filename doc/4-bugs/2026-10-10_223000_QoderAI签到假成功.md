# Qoder AI 国际版签到假成功（生产账号 u8e6a5348 / ua554edc3）

结论：

1. 面板/接口显示「签到成功」但账号积分不变，根因是**宿主 HTTP 桥状态码解码错误**：插件用 `json:"status_code"` 解码宿主响应，而宿主（v7.2.x）实际输出未加 tag 的 PascalCase `{"StatusCode":404,...}`，`status_code` 因下划线既不匹配键名也不匹配大小写不敏感匹配，导致 `StatusCode` 恒为 0；`if resp.StatusCode >= 400` 永不触发，所有 404/4xx/5xx 被当作 200 成功。
2. 修复解码后进一步用生产真实 token 实测确认：国际版 OpenAPI `openapi.qoder.sh` **不存在每日签到端点**——`/sash/api/v1/me/daily-check-in/status` 与 `/claim` 均返回 404 `{"errorCode":"NotFound"}`；官方桌面客户端（`app.asar`）无任何签到代码，其奖励体系是 `campaign`（活动），且三个国际账号 `campaigns` 均 `claimable:false, campaigns:[]`。即：**修好解码只能把「假成功」变成「诚实的失败」，国际版当前仍没有可用签到端点** → 需产品确认（GAP-001）。

影响：受影响的是 qoder-ai-provider 的每日签到（面板「签到」/「全部签到」/ 定时自动签到）。同一解码缺陷还影响所有依赖 `StatusCode` 判定的链路（动态模型获取、额度查询、计划查询、探活），在 Linux 生产上都会把 4xx/5xx 误判为成功；Windows 不受影响（`hostHTTPDo` 在 Windows 走直连分支）。

范围：`qoder-ai/host_bridge.go`（状态码解码）、`qoder-ai/billing.go`（签到响应归一化收紧）、新增 `qoder-ai/host_bridge_test.go`。非范围：不改推理链路、模型映射、账号调度与生命周期、宿主 ABI；本轮不改 qoderwork（同源缺陷，另案跟踪）。

完成标准：

1. 宿主桥非流式响应状态码按真实线协议解码，4xx/5xx 不再被当作成功。
2. `performCheckinCall` 在响应缺 `success` 字段时不再默认成功。
3. 本地 `python scripts/cgo-shim-build.py qoder-ai` 的 build / vet / test 全绿，新增回归测试在修复前必失败。
4. 用生产账号 `u8e6a5348` / `ua554edc3` 真实复验：签到接口返回真实上游结果（不再假成功）。
5. 发布并热重载，行为验收通过。

验证状态：本地修复与反证已完成；生产复验与发布待执行。

## 问题现象

用户原话：「签到是无效的, 签到是不成功的, 我们现在生产的 u8e6a5348、ua554edc3 都可以签到, 得到 100 积分, 但是都不能成功签到, u8e6a5348 现在 393, ua554edc3 是 0, 他们签到成功一个分别加 100 积分。」

已知事实：

- 目标插件：qoder-ai-provider（仓库 `qoder-ai/`），生产已装 0.1.1。
- 目标账号：`u8e6a5348`（auth_index `074014975b590c79`，total_remain 393）、`ua554edc3`（auth_index `0e7c37aded465763`，total_remain 0）。
- 生产调用 `POST /v0/management/plugins/qoder-ai-provider/checkin` 对两账号均返回 `{"success":true,"message":"签到成功"}`，但 `credits.total_remain` 与调用前完全一致（393 / 0）。

## 复现

生产环境对单账号调用签到接口，观察返回与积分快照：

1. `POST .../qoder-ai-provider/checkin` body `{"auth_index":"074014975b590c79"}` → 返回 `success:true, message:"签到成功", credits.total_remain:393`。
2. 直接对上游 `GET https://openapi.qoder.sh/sash/api/v1/me/daily-check-in/status`（同一 Bearer token）→ 实际返回 `404 {"errorCode":"NotFound"}`。
3. 二者矛盾：上游 404 但插件报成功，证明状态码未生效。

## 根因

**根因（缺陷 A，铁证）**：宿主桥状态码解码错误。

- `qoder-ai/host_bridge.go` 的 `hostHTTPDo` 用
  `var resp struct { StatusCode int `json:"status_code"` ... }`
  解码宿主 `host.http.do` 返回的 Result 载荷。
- 宿主侧真源 `F:\CLIProxyAPI\sdk\pluginapi\types.go` 的 `HTTPResponse` **无 json tag**；宿主经 `marshalRPCResult`（`json.Marshal`）序列化后键名是 PascalCase `{"StatusCode":404,"Headers":...,"Body":...}`。
- Go 的 `json` 解码：标签名与键名做「大小写不敏感」匹配，但 `status_code` 含下划线，与 `StatusCode` 既不精确相等、也不构成大小写不敏感匹配 → `StatusCode` 恒为 0。
- 结果：`billing.go` 的 `if resp.StatusCode >= 400` 永不触发，404 被当作成功；`performCheckinCall` 再对无 `success` 字段的响应做 `m["success"] = true` 盲归一化，最终对外输出「签到成功」。

**同类已修先例**：workbuddy 0.14.30 修复过完全相同的缺陷（提交 `1f26e0c`，`workbuddy/host_bridge.go` 的 `parseHostHTTPDoResult` + `workbuddy/host_bridge_test.go` 回归测试）。`qoder-ai/host_bridge.go` 与 `qoderwork/host_bridge.go` 逐字节相同，两插件都带此缺陷。

**缺陷 B（产品级，GAP）**：国际版 `openapi.qoder.sh` 没有每日签到端点。

| 端点 | 结果 |
| --- | --- |
| `openapi.qoder.sh/sash/api/v1/me/daily-check-in/status` | 404 `NotFound` |
| `openapi.qoder.sh/sash/api/v1/me/daily-check-in/claim` | 404 `NotFound` |
| `openapi.qoder.sh/api/v2/quota/usage` | 200（账号额度真值） |
| `openapi.qoder.sh/sash/api/v1/me/campaigns` | 200 `{"showCampaign":false,"claimable":false,"campaigns":[]}` |
| `openapi.qoder.sh/sash/api/v1/me/achievements` | 200 |
| `openapi.qoder.com.cn/sash/api/v1/me/daily-check-in/status`（CN 域） | 200（CN 端点是真实的） |
| `qoder.com/sash/.../daily-check-in/status` | 401 `missing cookie header`（走 web session，非 Bearer） |

证据：

- 穷举 140 个候选路径（`checkin / check-in / daily / reward / sign / claim / activity / benefit / task / quest / campaign / streak / bonus / gift / meter / billing / coupon / point` 等 × `me / me/{w} / me/{w}/status / me/{w}/claim`），非 404 命中只有 `/sash/api/v1/me/campaigns`。
- 反解官方客户端 `D:\Qoder\resources\app.asar`（v0.4.3）：无任何 daily-check-in / 签到 / rewardCredits 代码；奖励体系是 `campaigns`（`campaignKey` 常量 `client_launch_26`，`campaignUrl` 内嵌 surface + machineIdentity/clientType 头）。
- 三个国际账号 `campaigns` 均 `claimable:false, campaigns:[]`。

## 修复边界

- 只改宿主桥状态码解码（缺陷 A）与签到响应归一化收紧；不改推理、模型、调度、宿主 ABI。
- 缺陷 B 属产品事实，先如实透传上游真实结果，不伪造成功；具体签到入口由 GAP-001 待产品确认后再决定实现或下线 UI。

## 修复与验证结论

主方案：把 workbuddy 已验证的 `parseHostHTTPDoResult` 方案移植到 `qoder-ai/host_bridge.go`，并收紧 `performCheckinCall`。

1. `host_bridge.go`：抽出纯函数 `parseHostHTTPDoResult`，同时兼容宿主未加 tag 的 PascalCase 键与未来可能的下划线键；`hostHTTPDo` 改为调用它。
2. `billing.go`：`performCheckinCall` 在响应缺 `success` 布尔字段时返回 `success:false`（契约异常），不再默认成功。

本地验证：`python scripts/cgo-shim-build.py qoder-ai` 的 build / vet / test 全绿；新增 3 个回归测试（PascalCase 主用例、下划线兼容、非法载荷）。反证：临时把解码字段改回 `json:"status_code"`，`TestParseHostHTTPDoResult_HostUntaggedPascalCase` 必失败（`StatusCode = 0, want 200`）；必失败哨兵证明测试真实进编译。

生产复验与发布：待执行。
