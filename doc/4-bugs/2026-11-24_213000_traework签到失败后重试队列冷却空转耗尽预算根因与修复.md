# traework 签到一次失败后下次定时不再重试，部分账号当天签到失败

- 时间：2026-11-24 21:00 用户反馈 / 2026-11-24 21:30 根因锁定并确定修复方案
- 版本：traework-provider 0.5.58（故障版本）→ 0.5.59（修复版本）
- 环境：生产 45.207.222.65（`cpa-server`），容器 `cli-proxy-api`
- 发现渠道：用户反馈「trea 插件有些账号尝试一次签到失败后下次定时的时候就没有继续尝试了，导致我们有些号其实没有签到成功」

## 1. 现象

部分账号一次签到失败后，后续每 4 小时一轮的定时签到（00/04/08/12/16/20）不再真正重试，当天签到积分丢失。失败账号的补签完全依赖纯内存重试队列；一旦队列条目被丢弃，当天不再有补签路径。

## 2. 根因

失败账号的补签队列（`traework/checkin_retry.go`）和签到冷却（`traework/checkin.go`）三处叠加，把有限的重试预算消耗在无效空转上：

### 2.1 冷却期重试空转，白吃掉 60 次额度（主因）

- `checkinAccount`（`checkin.go:340-346`）遇到 9074「当前参与用户太多」时记账号级冷却，平时 55 分钟、早窗 12 分钟（`checkin.go:28-31` `checkinNormalCooldown` / `checkinPeakCooldown`）。
- 同一次失败被 `scheduleCheckinRetry` 入队，1 分钟一次、上限 60 次（`checkin_retry.go:31-35`）。
- 但 `checkinAccount` 开头就检查冷却，冷却期内直接返回「限流冷却中，约 N 分钟后重试」、根本不打上游（`checkin.go:283-286`）。
- 该消息被 `checkinRetryable` 判为可重试（`checkin_retry.go:68-74` 仅排除 no credential / 凭据加载失败），每拍 `requeueCheckinRetry` 都 `Attempts++`（`checkin_retry.go:238`）。
- 结果：55 分钟冷却吃掉约 55 次 attempt，冷却结束时只剩约 5 次真实机会；上游若未恢复，60 次耗尽后 `requeueCheckinRetry` 的 `if e.Attempts >= checkinRetryMax { return }`（`checkin_retry.go:240-245`）直接丢弃条目，当天不再重试。

### 2.2 跨定时槽位的 attempt 粘滞

`scheduleCheckinRetry` 对已在队账号只刷新 `LastMessage` / `UID`，不重置 `Attempts` / `NextAt`（`checkin_retry.go:88-94`）。若某条目在下次 4 小时槽位时既没成功也没被丢弃，新一轮失败只是刷新消息，attempt 保持高位，下一拍即被丢弃。

### 2.3 丢弃后无当天补签路径

条目一旦被丢弃，只能等下一个 4 小时槽位；若恰好在 20:00 那轮丢弃，当天彻底没有机会。三点叠加精确对应用户现象。

## 3. 修复方案

主方案（F1 + F2），均为根因修复，改动集中在 `traework/checkin.go` 与 `traework/checkin_retry.go`。

### F1 冷却空转不扣预算

给 `checkinResult` 增加内部字段 `Cooldown time.Duration`（`json:"-"`，大于 0 表示本次因账号级冷却跳过、未请求上游，值为剩余冷却）。`checkinAccount` 的冷却返回路径置位。`processCheckinRetry` 在成功分支之后优先判断该标志：命中时走新增的 `requeueCheckinRetryWaiting`，把条目 `NextAt` 顺延到冷却结束再留一个重试间隔，`Attempts` 不自增，让 60 次预算全部留给真正会打上游的尝试。冷却消息本身仍是可重试消息，仅消费路径不同。

### F2 每轮定时重置预算

`runFleetCheckin` 在循环内、对每个凭据加载成功的账号执行 `checkinAccount` 之前，先 `cancelCheckinRetry(f.AuthIndex)` 清掉上一轮遗留条目。这样本轮若失败，`scheduleCheckinRetry` 会新建条目、`Attempts=1`，保证每个 4 小时槽位都有完整 60 次机会，消除跨槽粘滞。不改动 `scheduleCheckinRetry` 的幂等语义（并发全量签到同时入队时仍不重置 attempt），避免扩大改动面。

### 备选方案（未采用）

- 把重试截止从固定 60 分钟改为动态延续到下一槽位、并为队列做跨重启持久化：能进一步覆盖热重载与超长冷却，但改动大、需新状态文件，超出本次止血范围，列为后续增强。
- 仅加长 `checkinRetryMax`：治标不治本，冷却期仍会空转并拉长无效请求窗口，放弃。

## 4. 风险与影响面

- `checkinResult` 新增字段仅内部使用、不参与序列化，既有多处字面量构造不受影响（Go 结构体字面量按字段名赋值）。
- F2 的 `cancelCheckinRetry` 只在全量签到轮次对本轮参与账号调用；手动点「测试签到」走 `runFleetCheckin("manual")`，同样受益于预算重置，符合预期。
- 冷却条目顺延后 `NextAt` 可能落在下一个 4 小时槽位之后，届时本轮全量签到会先 cancel 再重建，不会出现条目永久滞留。
- 并发全量签到与重试循环同时处理同一账号时，`requeueCheckinRetryWaiting` 与 `requeueCheckinRetry` 均沿用「仅当 key 不存在才写回」的既有保护，不引入新竞态。

## 5. 验证方式

- 定向回归用例（`traework/checkin_retry_test.go`）：冷却顺延不扣 attempt、跨轮 cancel 后重建得到完整预算、永久失败不入队。
- 全量本地验证：`python scripts/cgo-shim-build.py traework`（build + vet + test 全绿）。
- 发布后生产热重载生效核验（默认授权范围）：`docker logs cli-proxy-api | grep "hot reloaded"` 见目标版本，落盘 `.so` sha256 与 release zip 一致。

## 6. 确认结论

根因明确、方案针对根因、影响面收敛在两个文件、可本地真实测试，用户已明确回复「执行」，直接进入编码实施。
