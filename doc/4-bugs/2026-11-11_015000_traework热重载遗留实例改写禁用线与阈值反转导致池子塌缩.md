# traework 热重载遗留实例反复改写禁用线 + 禁用线高于保活线导致池子塌缩

- 时间：2026-11-11 01:50:00
- 插件：traework-provider 0.5.44 → 0.5.45
- 生产：45.207.222.65，容器 `cli-proxy-api`
- 现象（用户口径）：「首字延迟和生成时间都很高（首字 10s 以上，生成时间 100s 以上）」；
  对比 workbuddy 与 trae 后确认 trae 明显更慢；「输入输出 token 不多但首字延迟很高
  （20w 输入 / 500 输出，首字 20s+ 明显异常）」。

## 一、缺陷 A：热重载遗留实例持续改写禁用线

`main.go:141` 的 `cliproxyPluginShutdown` 是**有意的空实现**（写注释说明不在此处
收尾资源），因此宿主热重载只把旧 `.so` 记入 retired 列表，旧实例的 goroutine
会一直跑到进程结束。

`instance_guard.go` 早在 2026-11-08 就已存在，但只有 2 个循环接入守卫。
0.5.41 → 0.5.42 → 0.5.44 三次热重载后，生产进程内同时 mmap 着**三个** `.so`：

- 0.5.41 实例的 `watchdogLoop` 按自己编译期的禁用线常量 `100` 每 10 分钟重写
  「`disabled:true` + `low_credit_disable_below:100`」，把 `remain=97` 的号也禁掉；
  新实例按生效线 10 判它「余额够用」又不解禁（归属键被宿主白名单丢弃），
  两边来回拉锯。
- 同一批旧实例的 `keepaliveLoop` / `autoCheckinLoop` / `authFlagGuardLoop` /
  `slowPoolSizeLoop` 也各自打上游，探活与签到请求随热重载次数**线性放大**，
  在配额已耗尽时仍在持续请求。

后果是候选池被反复削薄，并发堆到少数幸存账号上，首字延迟尾部同步抬升。
trae 上游每账号只给 **2** 个并行槽位，溢出部分在上游静默排队，正是
「输入 20w / 输出 500 但首字 20s+」的形态。

## 二、缺陷 B：禁用线高于保活线使保活档不可达

`creditTierFor` 的判定顺序是先禁用线、后保活线：

```go
if disableBelow > 0 && remain < disableBelow { return creditTierDisabled }
if preserveBelow > 0 && remain < preserveBelow { return creditTierPreserve }
```

`low_credit_disable_below` 在 0.5.30 起默认 100，而 `min_routable_credits` 默认 20。
禁用线更高时，任何满足保活档的余额（`< 20`）必然先满足禁用档，**保活档在数学上
不可达**——`creditTierPreserve` 成了死档位。0.5.30 的 CHANGELOG 自己就记下了
这个反模式（21 → 7），0.5.42 把默认值回滚成 10，但配置项仍接受任意整数。

## 三、修复

### A：统一实例守卫闸门

新增 `retireIfSuperseded(loop string) bool`，已被取代时打停止日志并返回 true。
接线覆盖 8 个循环：`failoverReconcileLoop` / `failoverProbeLoop` /
`watchdogLoop`（入口 + 每轮）/ `slowPoolSizeLoop`（入口 + 每轮）/
`keepaliveLoop` / `autoCheckinLoop`（入口 + 定时器唤醒后）/ `checkinRetryLoop` /
`authFlagGuardLoop`。`failover_disable.go:893` 的第三个调用点保持原始
`pluginInstanceSuperseded()` 形态，因为那里需要区分「过期」与「探活失败」。

### B：在读路径夹取生效禁用线

新增 `effectiveLowCreditDisableBelow()`：禁用线不得超过保活线；`<= 0` 的
kill switch 原样透传。所有读点统一走它（`cache.go` / `credit_disable.go` /
`management.go` 两处 / `scheduler.go`）。

夹取放在**读路径**而不是 `config.go` 的解析处，理由有二：
1. 保住 `<= 0` 关闭本机制的语义，配置解析处看不到保活线；
2. 不改写生产配置，避免触发配置存储红线。

历史被宽松阈值禁掉的号会自动自愈：这些号盘上只有本机制的三键
（`manual_disable` 只由面板 toggle 写入），`ours` 成立，下一轮分级按当前
生效线判为 normal 后走既有解禁路径。

## 五、遗留

- `account_load.go` 的 `sessionAccountInflightSoftCap = 2` 仍只用于粘性会话重绑，
  `pickLeastLoaded` / `pickLessLoadedThan` 只排序不拒绝。真正的硬并发上限是
  独立的一条缺陷，且 `accountLoad` 是包级全局，每次热重载会把计数清零。
- `[keepalive] retry traework-<uid>.json: failed (refresh rejected: ExchangeToken
  returned no token)` 覆盖约 29 个账号，属上游 refresh 通道问题，与本轮改动无关。
