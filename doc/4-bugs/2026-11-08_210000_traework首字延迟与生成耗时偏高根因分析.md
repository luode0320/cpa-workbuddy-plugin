- 请求：判断首字延迟与生成时间偏高是否为插件缺陷，并参考同类开源反代实现

## 二、归因（三项证据）

### 1. 超长 input 是主因
按 input 规模分桶后 TTFT 中位数：

| input 区间 | traework minimax TTFT p50 | workbuddy deepseek TTFT p50 |
| --- | --- | --- |
| 50k-100k | 3364ms | 2448ms |
| 100k-200k | 3433ms | 2598ms |
| 200k-300k | 4393ms | 2853ms |
| >300k | 7809ms | —（样本不足） |

大 input（≥50k）归一化 prefill：traework **29.3 ms / 1k tokens**，workbuddy **22.4 ms / 1k tokens**。中位数仅差 31%，属同一量级 —— 平均值不是问题所在。

### 2. 长尾才是异常点
traework 在 100k-200k 区间的 TTFT p50 是 3433ms 但 p90 达 16349ms（**4.8 倍**），workbuddy 同区间 p90 仅 3240ms（1.25 倍）。说明 traework 的问题集中在长尾而非平均。

慢请求（TTFT>15s，占 14.6%）特征：
- input 中位 **361,136 tokens**，快请求为 251,214 tokens
- 集中在高峰时段：17 点 57 次、18 点 49 次、19 点 49 次（其余时段 4~34 次）
- 按账号分布集中：38586387(60)、23105196(52)、28207018(41)、44919566(37)、24336702(36)、39297886(34)；当前活跃账号 12022422 仅 6 次
- 慢请求集中的账号正是随后因配额耗尽被禁用的那批

### 3. 慢速账号机制工作正常
traework 的 `slow_account` 以「同模型全池中位数」为基准。全池同时变慢时基准同步抬高，不会误判 —— 这正是上游整体拥堵而非个别账号故障的正确表达，因此未触发降权是预期行为。

## 三、结论

**不是插件缺陷。** 延迟由三项上游特性共同决定：大 input prefill（25~36 万 tokens）、Trae 上游高峰时段性能衰减、以及慢账号路由到更慢的上游节点。插件侧转发链路未引入可观延迟（对照 workbuddy 同量级 input 的 p50 仅低 31%，与模型 prefill 效率差异相符）。

## 四、参考同类开源反代实现

`connectedgraph/trae2api-web`（Go，50 stars，2026-10-27 更新）`internal/upstream/client.go`：

- `ResponseHeaderTimeout: 120 * time.Second` —— 注释说明「首字节兜底，给上游预留足够推理时间」
- `StreamHTTP: &http.Client{Transport: tr}` —— **流式客户端不设 `http.Client.Timeout`**，注释为「单测专用客户端，不能超时，否则超长 SSE 会被 HTTP.Timeout 切断」；其单测显式断言 `if c.StreamHTTP.Timeout != 0 { t.Errorf(...) }`
- 流式透传使用 `http.Flusher` + `X-Accel-Buffering: no-cache`

## 五、据此落地的改动

| 项 | 改动前 | 改动后 | 依据 |

## 六、未覆盖与后续

- 生产主路径走宿主桥 `host.http.do_stream`，插件侧超时配置仅在桥不可用时生效；占位提示 —— 真正影响长流的宿主 HTTP 客户端超时属跨项目范围，本仓库不改。
- 流式路径未单独创建「不设整体 Timeout」的客户端：当前流式已走宿主桥，插件侧 client 不参与生产流式。
- 建议后续观测：若 Trae 上游在高峰时段持续衰减，可考虑在插件侧引入「首字延迟超阈值即主动换号重试」（需先确认换号能改善，本批数据中慢请求跨多个账号，暂不具备该前提）。

### 结论细化

1. **首字长尾才是用户可感的主要痛点**：TTFT p50 仅 3.9~8.4s，但 p90 达 32~70s。中位数正常、尾部分位异常，符合上游排队特征。
2. **生成速度是模型固有差异**：Doubao 35.3 tok/s 明显低于 workbuddy 的 165.4 tok/s；但该请求 input 中位 166894 tokens，KV cache 极大，decode 阶段每 token 需扫全量 KV，速度下降属预期。
3. **对照 workbuddy 首字≥10s 仅 0.2%（vs traework 15.2%~29.9%，差 76~150 倍）**是最强异常信号。但两者 upstream 与服务商不同，且 workbuddy 的样本几乎都是 deepseek-v4.1-flash（推理模型、输出短）。
4. 插件侧已排除的项：`buildTraePayload` 不注入固定 system prompt（不额外放大 input）；流式读取无固定轮询延迟（`time.After` 仅作超时守卫）；`hostHTTPStream.Read` 直接透传 payload 不缓冲整帧。

## 十一、长尾根因最终定性：上游 Trae 侧突发排队（非插件缺陷）

### 决定性证据一：并发量与 TTFT 长尾完全无关

按「同账号同分钟内的第几个请求」与「全池同分钟并发量」两个维度切片（traework，12h 样本 5080 条）：

| 同账号并发序 | n | TTFT p50 | TTFT p90 | 慢请求(≥10s)占比 |
| --- | --- | --- | --- | --- |
| 第1个 | 2174 | 5592ms | 33125ms | 25.2% |
| 第2个 | 759 | 4838ms | 33233ms | 21.9% |
| 第3-4个 | 558 | 5149ms | 33612ms | 26.3% |
| 第5+个 | 1589 | 5044ms | 35088ms | 23.4% |

| 全池并发量 | n | TTFT p50 | TTFT p90 | 慢请求占比 |
| --- | --- | --- | --- | --- |
| 1 | 673 | 5711ms | 33660ms | 26.0% |
| 3 | 551 | 5505ms | 33798ms | 26.5% |
| 5 | 394 | 5435ms | 33873ms | 26.4% |
| 10 | 160 | 4802ms | 34599ms | 20.6% |

并发从 1 升到 10+，慢请求占比稳定在 20~26% —— **排队假设被彻底否定**（插件侧并发不构成原因）。

### 决定性证据二：同一账号、同一 input 量级下 TTFT 随机跳变

账号 `0312977305`（deepseek-v4.1-flash，input≥15 万）连续 9 次请求的 TTFT：

```
3587, 3319, 3347, 2867, 2791, 4063, 34001, 6359, 3470
```

前 5 次都在 2.8~4.1 秒，第 6 次突然 34 秒，第 7 次 6.4 秒，第 8 次又回到 3.5 秒。
同账号、同模型、同 input 量级，**TTFT 在 2.8 秒与 52 秒之间无规律跳变** —— 这是上游 Trae 侧的
突发排队（后端实例冷启动 / 调度抖动），与账号健康度、插件链路、并发量都无关。

### 决定性证据三：慢请求的 input 只略大，不是主因

| 类别 | n | input 中位 |
| --- | --- | --- |
| 慢请求（TTFT≥15s） | 218 | 257,486 |
| 快请求（TTFT≤5s） | 924 | 187,523 |

input 仅差 37%，不足以解释 5~10 倍的 TTFT 差距。

### 附带发现：客户端上下文管理差异（属 DSH 侧，非插件）

同一 `header:1` 会话内：

| provider | input 走势 | TTFT 走势 |
| --- | --- | --- |
| workbuddy | 稳定在 21 万左右 | 4309 / 5323 / 5228 / 5265 / 5154ms（稳定） |
| traework | 涨到 44 万、65 万 | 9239 / 8594 / 6709ms（波动大） |

workbuddy 的 input 被稳定截断在约 21 万，traework 则持续增长到 65 万。两插件代码中**都没有**
上下文截断逻辑（grep `truncat|maxContext|contextWindow|context_limit` 无实现），差异来自
**上游侧或客户端侧**的上下文管理，不是插件缺陷。

### 与用户「trae 比 workbuddy 慢很多」观感的对应

| 维度 | workbuddy | traework |
| --- | --- | --- |
| 同 input 区间 TTFT p50 | 2711ms | 3809ms（1.4×） |
| 同 input 区间 TTFT p90 | 4482ms | **31181ms（7.0×）** |
| input 是否被截断 | 是（~21 万） | 否（涨到 65 万） |
| 上游突发排队表现 | 无（p90≈p50×2） | 有（p90≈p50×8） |

用户感受到的「慢很多」由**长尾**主导，而非平均值。

### 最终结论

**不是插件缺陷。** 首字延迟偏高来自三项上游/客户端因素，按影响排序：

1. **Trae 上游突发排队**（主因）：同账号同 input 下 TTFT 随机在 2.8s~52s 跳变，插件侧无任何可干预点；
2. **上下文未被上游截断**（次因）：input 涨到 65 万，prefill 工作量是 workbuddy 的 3 倍；
3. **模型差异**（次因）：Doubao 生成速度 35.3 tok/s vs workbuddy 165.4 tok/s。

插件侧可做的优化已全部完成：分阶段超时（10s/10s/120s）、禁 h2、请求级错误分类、实例守卫、
避免双重换号放大。**若要继续改善首字延迟，需要 Trae 上游侧配合**（或改用上下文更短的模型）。

**没有超过 100 万的请求** —— 说明客户端（DSH）已按上下文上限截断到约 80 万，
但 80 万 token 的 prefill 在任何模型上都是数十秒级成本。

### 已排除的优化路径

| 路径 | 结论 |
| --- | --- |
| prompt caching | 上游 `cached_tokens`/`cache_read_tokens`/`cache_creation_tokens` **全部为 0**（24h、12023 条），上游不提供 |
| 插件侧截断 | `buildTraePayload` 原样透传 messages，无截断逻辑；主动截断会破坏对话完整性 |
| 首字闸门 | 已封顶 1200ms（0.5.32/0.5.33），实测 p90=1075ms |
| 并发排队 | 已实证与并发量无关（慢请求占比稳定 20~26%） |

### 剩余唯一可行的优化方向

**缩短 input 长度**。这需要客户端（DSH）侧配合：

1. 把上下文上限从 ~80 万降到 20~30 万，可让 TTFT p50 从 7.7s 降到 4.5s；
2. 或启用更激进的对话历史裁剪策略。

插件侧无法在不破坏对话完整性的前提下自动截断 —— 这是产品决策，不是缺陷。
