# traework minimax-m3.1-flash / Doubao-Seed-2.1-Pro 首字延迟与生成耗时分析

- 日期：2026-11-08
- 范围：traework-provider 生产流量（12h / 24h feed 窗口）
- 请求：判断首字延迟与生成时间偏高是否为插件缺陷，并参考同类开源反代实现

## 二、归因（三项证据）

### 1. 超长 input 是主因
按 input 规模分桶后 TTFT 中位数：

| input 区间 | traework minimax TTFT p50 | workbuddy deepseek TTFT p50 |
| --- | --- | --- |
| 50k-100k | 3364ms | 2448ms |
| 100k-200k | 3433ms | 2598ms |
| 200k-300k | 4393ms | 2853ms |
| >300k | 7809ms | —（样本不足） |

大 input（≥50k）归一化 prefill：traework **29.3 ms / 1k tokens**，workbuddy **22.4 ms / 1k tokens**。中位数仅差 31%，属同一量级 —— 平均值不是问题所在。

### 2. 长尾才是异常点
traework 在 100k-200k 区间的 TTFT p50 是 3433ms 但 p90 达 16349ms（**4.8 倍**），workbuddy 同区间 p90 仅 3240ms（1.25 倍）。说明 traework 的问题集中在长尾而非平均。

慢请求（TTFT>15s，占 14.6%）特征：
- input 中位 **361,136 tokens**，快请求为 251,214 tokens
- 集中在高峰时段：17 点 57 次、18 点 49 次、19 点 49 次（其余时段 4~34 次）
- 按账号分布集中：38586387(60)、23105196(52)、28207018(41)、44919566(37)、24336702(36)、39297886(34)；当前活跃账号 12022422 仅 6 次
- 慢请求集中的账号正是随后因配额耗尽被禁用的那批

### 3. 慢速账号机制工作正常
traework 的 `slow_account` 以「同模型全池中位数」为基准。全池同时变慢时基准同步抬高，不会误判 —— 这正是上游整体拥堵而非个别账号故障的正确表达，因此未触发降权是预期行为。

## 三、结论

**不是插件缺陷。** 延迟由三项上游特性共同决定：大 input prefill（25~36 万 tokens）、Trae 上游高峰时段性能衰减、以及慢账号路由到更慢的上游节点。插件侧转发链路未引入可观延迟（对照 workbuddy 同量级 input 的 p50 仅低 31%，与模型 prefill 效率差异相符）。

## 四、参考同类开源反代实现

`connectedgraph/trae2api-web`（Go，50 stars，2026-10-27 更新）`internal/upstream/client.go`：

- `ResponseHeaderTimeout: 120 * time.Second` —— 注释说明「首字节兜底，给上游预留足够推理时间」
- `StreamHTTP: &http.Client{Transport: tr}` —— **流式客户端不设 `http.Client.Timeout`**，注释为「单测专用客户端，不能超时，否则超长 SSE 会被 HTTP.Timeout 切断」；其单测显式断言 `if c.StreamHTTP.Timeout != 0 { t.Errorf(...) }`
- 流式透传使用 `http.Flusher` + `X-Accel-Buffering: no-cache`

## 五、据此落地的改动

| 项 | 改动前 | 改动后 | 依据 |
| --- | --- | --- | --- |
| traework `sharedHTTPClient` | 仅 `Timeout: 120s` | 补 `DialContext(10s)` / `TLSHandshakeTimeout(10s)` / `ResponseHeaderTimeout(120s)`，置空 `TLSNextProto` 禁 h2 | 对齐开源实现与 workbuddy 0.21.14 |

## 六、未覆盖与后续

- 生产主路径走宿主桥 `host.http.do_stream`，插件侧超时配置仅在桥不可用时生效；占位提示 —— 真正影响长流的宿主 HTTP 客户端超时属跨项目范围，本仓库不改。
- 流式路径未单独创建「不设整体 Timeout」的客户端：当前流式已走宿主桥，插件侧 client 不参与生产流式。
- 建议后续观测：若 Trae 上游在高峰时段持续衰减，可考虑在插件侧引入「首字延迟超阈值即主动换号重试」（需先确认换号能改善，本批数据中慢请求跨多个账号，暂不具备该前提）。

### 结论细化

1. **首字长尾才是用户可感的主要痛点**：TTFT p50 仅 3.9~8.4s，但 p90 达 32~70s。中位数正常、尾部分位异常，符合上游排队特征。
2. **生成速度是模型固有差异**：Doubao 35.3 tok/s 明显低于 workbuddy 的 165.4 tok/s；但该请求 input 中位 166894 tokens，KV cache 极大，decode 阶段每 token 需扫全量 KV，速度下降属预期。
3. **对照 workbuddy 首字≥10s 仅 0.2%（vs traework 15.2%~29.9%，差 76~150 倍）**是最强异常信号。但两者 upstream 与服务商不同，且 workbuddy 的样本几乎都是 deepseek-v4.1-flash（推理模型、输出短）。
4. 插件侧已排除的项：`buildTraePayload` 不注入固定 system prompt（不额外放大 input）；流式读取无固定轮询延迟（`time.After` 仅作超时守卫）；`hostHTTPStream.Read` 直接透传 payload 不缓冲整帧。
