# traework 首字 20~110s 长尾归因：连接级响应头压制 + 预算未覆盖上传

- 日期：2026-11-29
- 影响版本：≤0.5.66（修复见 0.5.67 / 0.5.68 / 0.5.69）
- 现象：用户反馈「输入 45~71 万 token，首字 30s、160s，正常应在 10s 以下」，且「几乎到了无法使用的地步」。生产 120 分钟 TTFT `p50=4.5s p90=34.6s p99=149s max=239s`，`>15s` 占 49/202。

## 一、结论

25~35s 的 TTFT 台阶由**两个独立缺陷叠加**造成，与模型速度、并发、账号质量都无关：

1. **上游响应头被链路压住**（连接级、可换连接绕开）；
2. **插件侧单次尝试预算没管住请求体上传**，使重试环的上界失效。

## 二、证据链

### 证据 1：上游自身处理只要 1~1.6s

直测 `llm_utils_chat`（绕过插件与 CPA），读上游自报的 `event:timing_cost`：

| 字段 | 取值 |
|---|---|
| `server_processing_time` | 901~1575 ms |
| `first_sse_event_time` | 1006~1509 ms |
| `queue_timing` | 3~24 ms |

即使 810KB body / 152k token 也如此。也就是说 20~110s 的长尾里，真正属于模型的只有 1 秒多，**其余全部发生在响应头到达之前**。

### 证据 2：长尾是连接级的，换连接即可绕开

同一 body（810KB）交错对照 8 次：

| 策略 | p50 | p90 | max |
|---|---|---|---|
| 单次干等 | 2.8s | 80.7s | 80.7s |
| 6~8s 看门狗 + 最多 3 次重发 | 3.0s | 11.7s | 11.7s |

trial1 日志：第 1 次 8s 超时 → 第 2 次 2.0s 成功。**卡住后换新连接几乎立刻恢复**。

### 证据 3：请求体大小决定暴露面

随机交错 4 档 body × 9 轮（n=36），`>10s` 占比：

| body | 慢次数 |
|---|---|
| 8 KB | 0/9 |
| 128 KB | 0/9 |
| 512 KB | 1/9 (11%) |
| 810 KB | 4/9 (44%) |

健康窗口内响应头只要 1.4~3.1s。生产 body 恰为 810KB（`input_chars p50=456,692`），踩在 44% 档。

## 三、已推翻的假设

| 假设 | 推翻依据 |
|---|---|
| 上游 prefill 慢 | 380k/600k 上下文 header 只要 3.5~4.1s；`timing_cost` 显示处理 1~5.6s |
| HTTP/2 vs HTTP/1.1 | 上游 ALPN 只接受 http/1.1；h1/h2 无一致差异（1500KB: h1 0.062/0.062 vs h2 0.076/0.642） |
| 宿主 operation bridge 串行化 | `http_operation_bridge.go` 只有 per-operation mutex，无全局锁、无 worker pool |
| 单账号或并发争用 | 台阶率按并发（1→13%、2→12%、3→11%、4→13%）与账号（16 个号 7~22% 均摊）均无相关 |
| 门控缓冲 | `gate_ms` p50=34ms p90=1039ms p99=1456ms，量级远不够 |
| 本地资源耗尽 | cpu 0.98%、mem 336MiB/2GiB、pids 117 |
| 持久连接可解决 | 持久连接、换账号、降并发、改 payload 形态（补 `model_name`/`session_id`/`config_source`）均无效；gzip 请求体被上游 `4001` 拒绝 |

## 四、修复链

### 0.5.67 — 短预算 + 换连接重试

- `hostHTTPDoStream` 由「单次 open，超时即放弃」改为**重试环**：第 1 次走宿主桥（保留 request-log 与宿主传输策略），第 2..N 次走插件直连（可被 `ResponseHeaderTimeout` 真正中断，不会每重试一次就在宿主侧多漏一份仍在等待的上游请求）；上游已给出 4xx/5xx 结论时不重试。
- `hostBridgeOpenTimeoutDefault` 180s → **6s**（语义由「等到上游尾部」改为「单次尝试预算」）。旧的 180s 让每次重试前白等三分钟，是把上游拥塞全量转嫁给客户端。
- 新增 `streamOpenMaxAttemptsDefault = 3` 与配置项 `stream_open_max_attempts`；最坏总耗时上界 = 6s × 3 = 18s。
- 上下文预算 460,000 → **290,000 字符**（≈810KB → ≈512KB body），暴露面 44% → 11%。
- 每次尝试落 `[traework] stream open retry` 日志（attempt/budget/elapsed/body_bytes/reason），恢复落 `stream open recovered`。

### 0.5.68 — 修正面板失效元数据

配置面板字段说明仍写旧默认值（180 / 460000），且 `stream_open_max_attempts` 未暴露。

### 0.5.69 — 预算覆盖上传阶段（关键补丁）

**0.5.67 的漏洞**：只靠 transport 的 `ResponseHeaderTimeout`，而它的计时起点是**请求体写完**之后，上传本身完全不受约束。生产 1.2MB body 上传要 ~19s，于是出现：

```
elapsed_ms=25193 budget_ms=6000 body_bytes=1200517
elapsed_ms=32019 budget_ms=6000 body_bytes=1200517
elapsed_ms=81766 budget_ms=6000          ← 最大单次尝试 81.8s
```

**修法**：每次尝试用 `context.WithCancel` + `time.AfterFunc(预算)` 覆盖「建连 + 上传 + 等响应头」。

**刻意不用 `WithTimeout`**：它的 deadline 会一直有效，6s 后会把已经拿到响应头、正在正常生成的长流一起掐断，表现为正文生成中途断流。这里拿到响应头就 `openTimer.Stop()` 停表，`cancel` 转交给 `hostHTTPStream.Close` 在流结束时回收。

## 七、踩坑记录

- 生产 `stream_direct_forced: true` 是早前 A/B 实验遗留，会让日志里 `via_bridge` 恒为 `false`，宿主桥路径从未被尝试。默认应为 `false`。
- 插件日志 tag 是 `[traework]`，但正则 `\[traework\].*?ttft_ms` 会跨行失配（`.*?` 吃掉换行）。正确做法：先按 `'[traework]' in line` 过滤行，再单行 regex。
- `docker logs` 的 stdout 与 stderr 是分流的两路，`subprocess.run(capture_output=True)` 必须两者都读，否则会漏掉全部插件日志。
- `ResponseHeaderTimeout` 的计时起点是「请求体写完」，不是「请求开始」——想约束上传必须用 context deadline。
