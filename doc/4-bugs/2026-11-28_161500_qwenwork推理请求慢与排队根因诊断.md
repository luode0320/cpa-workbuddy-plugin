# QwenWork 推理请求「慢 + 排队」根因诊断（插件侧缺陷）

- 文档类型：Bug 主文档（根因定位）
- 日期：2026-11-28
- 插件：`qwenwork-provider`（生产版本 0.2.21，落盘 `qwenwork-provider-v0.2.21.so`）
- 生产主机：45.207.222.65（CPA 容器 `cli-proxy-api`，管理端口 8317）
- 用户原始判断：「有些推理请求很慢的问题，我们直接用 QwenWork 的客户端时没有这个问题的，也没有排队，也就是他肯定是我们的插件的问题，不是账号也不是网络的问题，找到问题并解决（优先参考 github 找 QwenWork 的反代项目，看看他们有没有相关的处理，而我们是有 bug 的）」

## 1. 结论（先给答案）

**用户判断成立：这是插件缺陷，不是账号也不是网络。** 根因不是单一 bug，而是 **6 个插件侧缺陷叠加**，其中 3 个是主因：

| 编号 | 主因 | 一句话机制 | 社区是否已有正确处理 |
|---|---|---|---|
| **R1** | **会话种子塌缩** | 所有对话被压成**同一个上游 MaaS session**（生产实测 session_key 恒为 `header:1`），上游按会话排队 + 前缀缓存串味 → 「越聊越慢」「排队」 | ✅ 社区一致口径：种子优先级 宿主会话名 → `prompt_cache_key` → `session_id` → `user` → (system+首条 user 消息)，并**明确禁止**把全部对话撞成一会话 |
| **R2** | **慢号让位机制三处同时失效** | ①TTFT 计时基准放在发请求**之后** → TTFT 恒为 0；②异步流把**客户端别名**当 upstreamModel 传下去 → 慢速样本键与调度查询键对不上；③准入闸门要求账号池 > 20，生产只有 8 个 → 机制整体休眠 | ❌ 社区无此机制（我方独有），但当前**等同不存在** |
| **R3** | **客户端断连不取消上游请求** | `host_callback_id` 未透传 → 宿主拿不到 callback context → 上游 ctx 退化为 `context.Background()` → 客户端已放弃的请求仍在上游占并发 → **上游排队被放大** | ✅ workbuddy 2026-11-07 已补齐同一链路，**qwenwork 漏移植** |

放大器 3 个：

| 编号 | 放大器 | 机制 |
|---|---|---|
| **A1** | **上游「模型池忙」被当账号故障** | 裸 429（上游 `All models failed`）计入账号阶梯冷却 → **健康号被逐个误冷却** → 可用池变小 → 流量集中到少数账号 → 更堵。社区口径：这类 429 应归 503 排队类，**不冷却账号** |
| **A2** | **排队帧判据过窄 + 不透出退避提示** | `isQueueFrame` 只做子串匹配（`isQueued`/`queueCount`/`10605`），漏 `serviceAvailable:false` 语义；且已解析出的 `retryAfterSeconds` 没有透出 → 客户端立即重试撞同一队列 |
| **A3** | **宿主重试预算 ×100** | 生产 `config.yaml`：`retry.request-retry: 100` / `max-retry-credentials: 100`。插件每返一次错（400/429/502/504）宿主就最多再打 **100 轮 × 100 个凭据** 次上游 → 一次错误被放大成分钟级延迟（宿主侧配置，非插件代码，但插件错误率是它的乘数） |

### 3.1 官方桌面客户端逆向（最直接的对照组）

用户说「直接用 QwenWork 的客户端时没有这个问题，也没有排队」——**同一个客户端、同一份工作负载**，唯一差别是走不走我们的插件。因此最有价值的对照组就是官方客户端的真实出站实现。

真实安装：`D:\qwork\QwenWorkCN\2.2.1-26112604\`（`D:\qwenwork` 是空目录）。`resources\app.asar`（491.95 MB）中 `out/main/main.js` 为主进程 bundle。

#### 官方客户端的 MaaS 出站请求头全集（`buildAuthenticatedUpstreamHeaders` / `buildUpstreamHeaders`）

```http
POST {服务端下发的 base_url}/v1/chat/completions
Authorization: Bearer <MaaS access_token>
Accept: application/json
Content-Type: application/json
x-session-id: <产品会话 UUID>          ← 关键：会话绑定头
x-mm-client-request-source: qwenwork_desktop
x-mm-device-type: windows
x-mm-client-request-id: <turnId>
x-mm-client-trace-id: <每 turn 随机 32 位 hex>
x-mm-request-set: <requestSetId>
x-mm-device-ua: <device ua>
x-qwenwork-app-mode: <appModeId>
User-Agent: <...>
```

**我方此前只发 `Authorization` + `Content-Type` + `Accept`**：`x-session-id` 与全部 `x-mm-*` 归因头都没有。

- `x-session-id` 缺失 ⇒ 上游拿不到「这张票属于哪个会话」的绑定，请求退化成**无归属流量**；
- 本插件的票据是按「账号×会话」签发的（`POST /api/desktop-sessions` 带 `session_id`），但请求侧从不带 `x-session-id`，**签发侧与会话侧对不上**；
- 官方客户端另有 `bodyIdleTimeoutMs = 0`（**关闭空闲超时**，长流不被掐）、上游连接超时 300s；本插件依赖宿主 `host.http.stream_read` 的空闲判定，生产实测出现 `duration=3m3.755s err=upstream 504: stream timeout`。

#### 官方客户端的票据语义（与本插件对照）

| 维度 | 官方客户端 | 本插件（修复前） | 判定 |
|---|---|---|---|
| 票据粒度 | 账号 × 会话（`sessionScope(sessionId)`） | 账号 × 会话 | 一致 |
| 刷新提前量 | `ttl/2`（ttl 未知时 600s）；引擎每 `ttl/4` 重取 | 固定 30 分钟 | 一致，**不是缺陷** |
| 轮换失败 | 保留旧票 + 30s 退避 | 回退重新签发 | 略有差异，本轮不改 |
| 换票并发 | 同 session scope 的 mint in-flight 去重 | 同（`inflight` map） | 一致 |
| **请求侧会话头** | **`x-session-id` 必发** | **不发** | 🔴 **R1 的直接缺口** |
| **客户端归因头** | **`x-mm-*` 全套** | **全无** | 🔴 同上 |

#### 官方客户端的排队语义

- `10605` 在客户端是 **"Model Overloaded"（模型过载）**，不是排队码；`10500` 是 Service Busy。
- 真正的排队态来自引擎自报事件（`queue_type` / `queue_count` / `wait_time_ms`），**不在 HTTP 响应里**。
- 客户端**不做本地串行化/排队**；每 turn 一条 route，辅助执行上限 16，单辅助 ≤2 次模型调用。
- 客户端唯一实际重试是 **401 → 刷新 token → 重放 1 次**；主 chat 路径 `maxRetries = 0`。

⇒ **官方客户端不会排队，是因为它把会话、票据、归因头都对齐了，并且不本地串行化**；本插件在这三点上都缺。

## 4. 根因判定

### R1（主因）：会话身份在上游侧没有落地 —— 请求缺 `x-session-id` + 全量流量塌缩成同一个上游会话

R1 由三个可独立验证、且必须同时修的子项构成：

**R1-a 出站缺会话绑定头与客户端归因头（最直接的缺口）**

- 我方 `applyMaasHeaders` 只发 `Authorization` + `Content-Type` + `Accept`；官方客户端必发 `x-session-id` 与全套 `x-mm-*`（见 §3.1 逆向证据）。
- 本插件的票据是**按会话签发**的（`POST /api/desktop-sessions` 带 `session_id`），但请求侧从不带 `x-session-id` ⇒ **签发侧与会话侧对不上**，请求在上游侧是无归属流量。
- 这是「官方客户端不排队、我们的插件排队」之间**唯一完全对称的差异**。

**R1-b 全部对话塌缩成同一个上游 MaaS session**

- 我方 `session_auth.go:117-137` 的会话种子链只有 header/metadata，**无 `prompt_cache_key`、无消息兜底**；生产实测会话键恒为 `header:1`（客户端发的 `X-Session-ID: 1`）。
- 后果：**一个账号上的全部对话共用一个上游 MaaS session**。社区文档明确记载这种形态的表征是「服务端缓存全部串味 → 越聊越慢」；上游按会话排队时表现为「排队」。
- 对照官方客户端：官方客户端的会话是**产品会话**（一次对话一个），与「一个账号一个会话」量级完全不同。

**R1-c 路由侧同样塌缩，全部流量钉死单一账号**

- `X-Session-ID: 1` 这类低熵标识被当成合法会话键采信 ⇒ `pickSessionAuth` 把全量流量粘在一个账号上（生产实测 14:50~15:10 全部落在 `67dd3bed`、15:20~17:40 全部落在 `95a733e8`），其余账号空转。
- 同仓 `traework` 插件 2026-11-10 已因同一生产现象落地「低熵会话标识剔除」，**qwenwork 漏移植**。

### R2：慢号让位机制三处同时失效

1. `stream.go:299` `collector.markAttemptStart(time.Now())` 位于 `hostHTTPDoStream`（`:234`）**之后** → TTFT 测的是「响应头到首帧」，恒为 0~1ms（生产 feed 铁证）。workbuddy 的同名机制基准在发请求之前，故其 TTFT 正常。
2. `main.go:1023` `go pumpUpstreamStream(..., req.Model, req.Model, ...)` —— **upstreamModel 位置传的是客户端别名**，慢速样本按别名记账，而调度侧 `scheduler.go:229-234` 按 `resolveUpstreamModel()` 查 → 键对不上。workbuddy 对应位置传的是解析后的 `upstreamModel`。
3. `slow_account.go:53` `defaultSlowMinPoolSize = 20` > 生产池 8 → `slowPoolAdmitted` 恒 false → 连样本都不记。

### R3：客户端断连不取消上游请求

- `main.go:921-925` `executorStreamRequest` 无 `HostCallbackID` 字段；`host_bridge.go:58-61` 的 wire 结构也没有 → 宿主 `resolveCallbackContext` 拿不到 ctx → 上游 ctx 退化为 `context.Background()`。
- workbuddy 全链路已补（`workbuddy/host_bridge.go:99-102`、`:289`、`workbuddy/main.go:940`、`:1024`），并有专门回归测试 `workbuddy/host_bridge_timeout_test.go:83-201`。
- 后果：客户端超时/断连后，插件仍在读上游；**上游看到的并发数远大于真实在途请求** → 上游排队更严重、TTFT 抬高。

### A1：上游「模型池忙」被当账号故障

- `policy.go:196-207` `isSoftRateLimit` 把裸 429 判为软限流；`policy.go:334-339` `isTransientThrottle` 把它并入**阶梯冷却**；`accountFailover.go:248` 走进 `recordAccountFailure` 记账路径。
- 社区口径：这是**模型池共享容量**问题（换号无用），应归 503 排队类，**不冷却账号**。
- 生产实测 24h 内 27 次 429（minimax）。每次都会把一个健康号推进阶梯冷却。

| 排除项 | 证据 |
|---|---|
| 不是账号问题 | 同一批账号在 traework/workbuddy 上正常；qwenwork 侧 3 个账号轮流承流时延迟分布相近（p50 7.9~14.0s），没有单个坏号 |
| 不是网络问题 | traework/workbuddy 走同一台宿主、同一出口 IP，TTFT 与延迟正常；qwenwork 的「慢」集中在**无前缀缓存**的请求上（`cache_tokens=0` 那条 `frt=67.8s`），这是上游 prefill 行为 |
| 不是宿主本身 | 同宿主同时间窗的 traework 请求并发正常（`exec stream async done` 每分钟多条） |
| **是插件问题** | 会话种子塌缩、TTFT 计时基准错位、upstreamModel 传参错位、`host_callback_id` 丢失、429 分类错误 —— 5 项全部在 `qwenwork/` 源码内，且全部能在 workbuddy（同架构、已修）或社区实现中找到正确口径 |

## 6. 修复范围（本轮）

见 `doc/3-实施/2026-11-28_162000_qwenwork推理慢与排队修复_实施总览.md`。

| CYCLE | 内容 | 目标 |
