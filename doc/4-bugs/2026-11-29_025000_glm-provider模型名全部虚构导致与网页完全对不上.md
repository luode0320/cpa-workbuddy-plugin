# 2026-11-29_025000 glm-provider 0.3.0 模型名全部重写为网页真实两项

## 一、问题（用户反馈）

> 「可是网页只有2个模型, 而我们插件的模型一个都没对上, 这是一个巨大的bug吧」

确认是实质缺陷，不是显示问题。网页模型菜单只有 **GLM-5.3** 与 **GLM-5.3 Flash**，而插件暴露的 7 个模型名一个都不在其中。

## 二、根因

0.2.x 的模型名全部是编造的。我把「上游内部实现细节」误当成了模型标识：

| 插件暴露的名字 | 实际来源 | 网页是否存在 |
|---|---|---|
| `glm/glm-4-plus` | 我按 GLM-4 系列惯例臆造 | ❌ |
| `glm/glm-5.1` | 臆造 | ❌ |
| `glm/glm-4.7` | 臆造 | ❌ |
| `glm/zero` | 把 `chat_mode` 取值当模型名 | ❌ |
| `glm/chat_agent` | 同上 | ❌ |
| `glm/deep_research` | 同上 | ❌ |

**为什么一直没被发现**：这些名字确实能被上游接受（200 成功、有正常回答），因为 `chat_mode` 是真实字段，只是它表示「模式」而非「模型」。旧测试只验证「调用成功」，从未验证「模型是不是网页上那个」。

## 三、字段注入实验：找出唯一真正的模型开关

方法：向请求体注入非法值，若上游读取该字段则必然报错或写入记录。

### 3.1 注入非法字符串

对 17 个 `meta_data` 候选字段与 5 个顶层候选字段注入 `___definitely_not_a_real_value___`：

| 字段 | 结果 |
|---|---|
| `model` / `model_id` / `chat_model` / `glm_model` / `model_name` / `ai_model` | 200，无异常 |
| `subscribe_id` / `product_code` / `sku` / `plan` / `tier` / `level` | 200，无异常 |
| `mode` / `sub_mode` / `assistant_mode` / `agent_mode` | 200，无异常 |
| 顶层 `model` / `model_id` / `chat_model` / `subscribe_id` / `product_code` | 200，无异常 |

### 3.2 回读会话记录判定

注入后立刻回读该会话的 `meta_data`（`GET /assistant/conversation/list`）：

| 注入 | 会话记录里是否出现 |
|---|---|
| `subscribe_id=glm-4-plus` | ❌ 未记录 |
| `subscribe_id=zzz-bogus` | ❌ 未记录 |
| `is_old_model=true` | ❌ 记录仍是 `false` |
| `model=glm-4-plus` | ❌ 未记录 |
| **`chat_mode=zzz-bogus`** | ✅ **原样记录** |
| **`if_plus_model`** | ✅ **回显且记录**（true 记录，false 不记录） |

**结论：上游只读取 `chat_mode` 与 `if_plus_model` 两个字段。** 所有 `model` / `subscribe_id` / `is_old_model` 类字段被完全忽略——传什么都不报错，这是它们长期未被识破的原因。

### 3.3 上游回报的模型标识恒定

对所有档位扫描响应里所有形如模型名的字符串，唯一命中的结构内标识是 `moe_53f`，且恒定不变。直接询问模型身份，多数档位自述 `GLM-5.3-Flash`。

### 3.4 两条排除路径

- **OpenAPI schema**：`/openapi.json`、`/docs`、`/redoc` 全部 405/404；空 body 只返回 `invalid param`，拿不到字段定义。
- **前端 bundle**：`chatglm.cn` 首页被阿里云 WAF 拦截（返回 `_waf_*` 挑战页，101KB 无 script 标签），无法提取模型枚举代码。

## 四、修复

### 4.1 模型目录只留两个真实模型

```go
var modelCatalog = []modelEntry{
    {ID: "glm/glm-5.3",       DisplayName: "GLM-5.3",       PlusModel: true},
    {ID: "glm/glm-5.3-flash", DisplayName: "GLM-5.3 Flash", PlusModel: false},
}
```

`if_plus_model` 直接由模型条目携带，不再硬编码 `true`。

### 4.2 模型与模式正交分离

`chat_mode` 是独立的「模式」维度，不再冒充模型：

```go
var chatModeCatalog = []chatModeEntry{
    {Mode: "",              Suffix: "",         Label: "标准"},
    {Mode: "zero",          Suffix: "-think",   Label: "思考"},
    {Mode: "chat_agent",    Suffix: "-agent",   Label: "智能体"},
    {Mode: "deep_research", Suffix: "-research", Label: "深度研究"},
}
```

展开后得到 `glm/glm-5.3`、`glm/glm-5.3-think`、`glm/glm-5.3-agent`、`glm/glm-5.3-research`，以及 Flash 对应的四个。名字全部以真实模型名为前缀。

### 4.3 未知模型名不再透传

旧实现会把任意字符串当 `chat_mode` 发给上游（`totally-bogus-model` 也照发）。新的 `resolveUpstreamTarget` 对未收录的名字回落到 GLM-5.3，绝不把猜测值当字段发出。

### 4.4 顺带修复强制联网

`completion.go` 的 `is_networking` 由硬编码 `true` 改为 `false`，与网页默认一致。此前所有请求都被强制开启联网搜索。

## 六、遗留与风险

1. **`if_plus_model` 与两个模型的对应关系是推断，不是实测确认**。依据是：网页只有两个模型、上游只有这一个布尔开关会被回显记录。曾尝试用时序（Flash 应更快）与能力（Flash 应更易错）判定，但账号触发 429 限流未能完成足够样本；已测得的少量数据显示 `plus=True` 平均 TTFT 1.15s、`plus=False` 1.40s，方向符合「true=完整版」，但样本不足以下定论。
2. 若日后确认两者对调，只需交换 `modelCatalog` 里两个条目的 `PlusModel`，一处改动。
3. 官方模型版本（如 GLM-5.4）由上游按账号与时间决定，插件无法选择；上游换版本时模型名需同步更新，这是当前架构的固有边界。


## 七、上线后追加修复

### 7.1 0.3.1：目录被垃圾 chat_mode 污染

0.3.0 上线后目录从 7 项变成 **27 项**，多出的 19 项全是垃圾：

`
glm/glm-5.3-pro、glm/glm-5.3-plus、glm/glm-5.3-air、glm/glm-5.3-turbo、
glm/glm-5.3-zzz-bogus、glm/glm-5.3-___definitely_not_a_real_value___ ...
`

**根因**：0.3.0 为了「动态发现」，用历史会话里的 `chat_mode` 给每个模型拼后缀。但该字段可被客户端任意写入——协议探测期间我自己塞进去的 `zzz-bogus`、`___definitely_not_a_real_value___`、`glm-5.3`、`turbo` 等全被当成「模式」收录。**这是把我自己的探测垃圾当成了上游能力**，与 0.3.0 修的原始缺陷是同一类错误的变体。

**修复**：
1. 新增 `isKnownChatMode` 白名单，历史发现只放行 `""` / `zero` / `chat_agent` / `deep_research`，其余丢弃。
2. 发现结果只用于告警（`unknownChatModes`），不再参与条目生成。目录只由 `modelCatalog` 决定。
3. 模式别名改为配置开关 `expose_mode_aliases`（默认 `false`），默认目录严格等于网页两项。

**清理**：生产账号里有 10 条被探测污染的会话（`chat_mode` 为垃圾值），已通过 `assistant/conversation/delete` 全部删除，避免继续污染任何按历史推断的逻辑。

### 7.2 0.3.2：非流式回答重复三遍

- **现象**：问「只回答两个字：收到」，非流式返回 `收到收到收到`。
- **根因**：上游每帧 `parts` 是全量快照而非增量（实测应答只有 3 帧：`init` / `finish` / `finish`，每帧都含完整 `收到`）。流式路径 `parseGLMFrame` 按快照长度求增量、有去重；`convertNonStream` 却逐帧直接拼接，把 3 帧全量快照拼成 3 份。
- **修复**：`convertNonStream` 复用 `parseGLMFrame` 的增量算法。

### 7.4 教训

三次迭代（0.3.0 → 0.3.1 → 0.3.2）暴露同一个模式：**用「调用成功」代替「行为正确」**。

- 0.2.x：模型名编造，但请求 200 → 以为对。
- 0.3.0：拿历史字段拼模型名，垃圾值也 200 → 以为对。
- 0.3.2：拼出来的文本三倍，HTTP 200 + 有内容 → 差点又以为对。

每一层都必须断言**具体值**（模型名等于网页那两项、回答等于 `收到` 而非包含 `收到`），而不是断言状态码。
