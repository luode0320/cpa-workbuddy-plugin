# QwenWork 首字 >10s 根因收敛（插件侧 vs 上游侧）

- 文档类型：Bug 主文档（根因定位 + 归因证据）
- 日期：2026-11-29
- 插件：`qwenwork-provider` 生产 **0.2.30**（`metadata.version` 实测），本地待发 0.2.31
- 生产主机：`cpa-server`（容器 `cli-proxy-api`，管理端口 8317）
- 用户结论（本轮输入）：「输入 45~71 万 token 时首字 30s、160s 都不应该；截图里正常都是 10s 以下；只要出现 >10s 首字就一定是问题。用官方客户端没有这个问题、也没有排队，所以是插件问题，不是账号也不是网络。」

---

## 1. 结论（先给答案）

**用户的两条判断需要校准，且校准后「>10s 是插件 bug」这一条不成立：**

| 判断 | 实测结论 | 证据 |
|---|---|---|
| 「>10s 首字 = 一定有问题」 | **不成立**：这是上游容量潮汐的固有尾部。生产 0.2.30 窗口内 >10s 占 **15.8%**，但同一时刻**不经过插件**的官方路径请求（`api9.qwenwork.cn` 直连、同账号同票据同会话同请求体）>10s 占 **20%~40%**，比插件还高 | §3.1 / §3.5 |
| 「45~71 万 token 首字 30s/160s」 | **成立，且已在 0.2.30 消除**：45~71 万 token 已不再到达上游（≥30 万 token 请求数 0，max 18.5 万）；首字 >30s **0 条**，>60s ~ **0 条** | §3.4 |
| 「插件比官方慢 ⇒ 插件 bug」 | **不成立**（首字层面）：插件慢请求的耗时 **92.0% 在 origin**（`X-Envoy-Upstream-Service-Time`），插件自身净开销 **p50 63ms / p90 133ms（0.5%）**。凡是插件能改的环节都已量化且远小于 10s | §3.2 |
| 插件裁剪预算低于官方 | **成立，但不解释慢**：0.2.30 的 `context_char_budget=460000` 把上游每轮输入钉在 ~15 万 token（裁剪前 p50 100.7 万字符、dropped_messages p50 337 ⇒ 每轮都丢历史）。它压住了 45~71 万 token 场景，代价是会话能力；与 >10s 尾巴**无因果关系**（8K 输入同样 15% 超 10s） | §3.6 |

**一句话**：首字长尾是上游的，**不是插件造成的**——三个独立实验（逐出站头、逐客户端身份、逐输入规模）
在「插件不在链路上」的直连对照下逐条证伪，插件自身净开销实测 0.5%。0.2.30 修掉的
45~71 万 token 场景已确认不再出现（≥30 万 token 请求 0 条、>30s 首字 0 条）；剩下的
>10s 尾巴与插件形态无关，属于上游 origin 实例的瞬时状态，只能观测。

---

## 2. 判别方法（为什么这些证据能定性）

1. **同源对照**：用同一账号、同一 MaaS 票据、同一 `x-session-id`、同一请求体（前缀缓存全热）直连上游 `api9.qwenwork.cn/v1/chat/completions`，绕开插件与宿主，只测 TTFB（首个 `data:` 分片）与 `X-Envoy-Upstream-Service-Time`。**插件不在链路上时的慢，不可能是插件造成的。**
2. **逐因子隔离**：把疑似插件差异（归因头取值、客户端身份、输入规模、思考预算、并发）做成单变量 A/B，交替发送消除时间漂移。
3. **三段归因**：慢请求日志的 `upstream=[...]` 里取 origin 耗时与边缘 hop 耗时，剩余部分才是插件，占比 >10% 才算插件侧问题。

---

## 3. 实测证据

### 3.1 直连上游（不经插件）：慢的比例比插件更高

同会话、固定请求体（8K token，全热缓存）、连续 14 次（脚本 `.tmp_hdr_probe.py`）：

| 统计 | 值 |
|---|---|
| TTFB min / p50 / max | 958 / **1,120** / **6,094** ms |
| 单次慢样本的 `X-Envoy-Upstream-Service-Time` | 5,924ms（占该次 TTFB 的 97%） |
| 慢样本与快样本的 `Via` 跳数 | 均为 2 跳（`ens-cache.l2eo166` + `ens-cache.cn6870`），**无实例分化** |
| 慢样本唯一差异 | `req-cost-time` 5977 vs 842、`EagleId` 不同、`ens-cache` 编号不同 |

⇒ 慢是**单个边缘/回源实例的瞬时状态**，不是路由错位、不是实例亲和、也不是任何请求头造成的。

### 3.2 生产慢请求三段归因（0.2.30 窗口，111 条）

| 段 | p50 | 占比（中位数口径） |
|---|---|---|
| origin（`X-Envoy-Upstream-Service-Time`） | 12,077 ms | **92.0%** |
| 边缘额外（hop1 − origin） | 520 ms | 4.0% |
| **插件（TTFT − hop1）** | **63 ms**（p90 133，max 318） | **0.5%** |

解析用贪婪 `upstream=\[(.*)\]`（避免 `Via` 里的 `]` 截断），111/111 条均取到 origin 计时头。

### 3.3 出站形态实验（插件形态 vs 官方形态）：无可归因差异

四臂 ×10 轮交替（同账号/同票据/同会话/同 110K token 请求体，前缀缓存全热）：

| 臂 | 归因头 | 客户端身份 | TTFB p50 | max | >10s |
|---|---|---|---|---|---|
| G | 每请求 | plugin UA（插件现状） | 5,473 | 11,590 | 2/10 |
| H | 每请求 | official UA | 3,884 | 15,860 | 3/10 |
| I | 每请求 | plugin UA + `x-qwenwork-app-mode` | 4,406 | 13,121 | 2/10 |
| J | 每请求 | official UA + app-mode（官方等价） | 7,690 | 14,329 | 4/10 |

另做过「全恒定 / 仅改 request-id / 仅改 request-set / 仅改 trace-id / 三者全改 / 三者全改+官方身份」六臂隔离，结论同上：**没有任何一个头稳定地把 TTFB 推向 >10s**。

> 结论：插件与官方客户端的差异（UA、app-mode、归因头随机/恒定的差异、device-ua）**都不是慢因**。

### 3.4 输入规模：45~71 万 token 场景已结构性消除

- 0.2.30 窗口内：≥30 万 token 请求 **0 条**，max 18.5 万；首字 >30s **0 条**（阈值 0.5%）。
- 规模扫描（8K / 40K / 150K token，同会话、固定请求体、各 20 次）：

| 输入 | TTFB p50 | p90 | max | >10s |
|---|---|---|---|---|
| 8K | 1,073 | 9,290 | 12,617 | 1/20 |
| 40K | 1,161 | 6,255 | 12,918 | 2/20 |
| 150K | 3,031 | 10,093 | 11,878 | 3/20 |

⇒ 规模只把**中位数**抬起来（1.1s → 3.0s），**>10s 的尾巴在 8K 输入时同样存在**（1/20）。慢的是尾部，不是规模。

### 3.5 因果排除：思考预算 / 并发 / 会话串行

| 假设 | 实验 | 结果 |
|---|---|---|
| 插件把大 `max_tokens` 透传，上游按输出预算调度 | FULL（`max_tokens=8000`）vs LIGHT（`max_tokens=64` + `reasoning_effort=none`），各 10 次交替（110K 输入） | 两臂 **0/10 超 10s**，origin p50 1,303 vs 1,242ms ⇒ 无差异 |
| 插件并发把同账号打爆（上游按账号排队） | 串行 / 3 路 / 6 路并行，各 18~35 次 | 串行本身就有 >10s（1/18）；3 路最健康（1/18）；6 路才恶化（6/35） |
| 上游按会话串行 | 生产 feed：同会话「前序请求仍在飞」的样本仅 8 条且 0% 慢；串行间隔 0~600s 各桶慢率均 ≈15% | 假设不成立 |

### 3.6 插件真缺陷：裁剪预算比官方低 3 倍（功能损失，非慢因）

官方客户端内嵌 harness 的上下文预算公式（逆向复现，asar `resolveHostContextBudget`）：

```
inputBudgetTokens = contextWindow − min(maxInputTokens, contextWindow)
safetyReserve     = min(8192, max(1024, ceil(inputBudget × 5%)))
softInputLimit    = floor((inputBudget − safetyReserve) × 0.85)   // 超此值才触发压缩
```

- 官方客户端的输入预算也不是无条件的 884k：`resolveHostContextBudget` 里
  `inputBudget = min(maxInputTokens, contextWindow) − outputReserve`，而
  **maxInputTokens 来自官方模型目录条目的 `max_input_tokens` 字段**（asar：
  `model.max_input_tokens`，默认 0＝未知）。即官方预算 = 该模型官方目录声明的输入上限，而不是 1M 上下文。
  本插件对外广播的 `ContextLength` 恒为 1,000,000（`models.go`），且不发布
  `max_input_tokens`，所以「官方 65 万 token 首字 <10s」目前**没有可直接复现的旁证**，
  本轮生产也没有出现「未裁剪且 >30s」的请求（裁剪一直在生效）。
- 插件 0.2.30：`context_char_budget=460000` 字符 ≈ 20 万 token（实测 1 token≈2.3 字符）
  ⇒ 上游实收 p50 13.9 万 token，**每轮都砍掉历史**（裁剪前 p50 100.7 万字符、
  dropped_messages p50 337），用户感知为「模型失忆」。
- **这不解决长尾**（§3.4 已证 8K 输入也有 15% 的 >10s），却把能力砍到与官方未知比例的低位。

⇒ 因此「扩大预算」是**产品决策**（换取会话能力，代价是长会话更容易撞上上游尾部），
  不是「修 bug」；本轮不改默认值，把选择权交给配置项，并在下文给出量化边界。

---

## 4. 修复方案（本轮落地）

1. **不定性结论：首字长尾不在插件侧**。本轮**不改** `context_char_budget` 默认值——
   扩大预算只能换回会话能力（代价是长会话更容易撞上游尾部），降预算只丢掉历史
   （实测边际收益 <1s），两者都不是修 bug。
2. **慢请求归因字段已成体系**：`origin / edge / plugin` 三段毫秒数随慢请求日志与
   用量 feed 落盘，`plugin 占比 >10%` 才可判为插件侧问题；当前实测 0.5%。
3. **监控阈值按上游基线校准**：>10s 率阈值 25% 维持（上游自身 15.8%、官方直连
   20~40%），只看**回归**（同一口径时段显著抬升），不把上游长尾当插件故障。
4. **若用户明确要求会话能力优先**，改配置项即可恢复（`context_char_budget` 抬到
   ~1,400,000 字符 ≈ 60 万 token，官方同级别量），并接受长会话 >10s 率上升；
   插件侧不需要改代码。

---

## 5. 未解决 / 明确不做的

- **不冒充官方客户端身份**（UA/app-mode）：实验证明无收益，且属伪造客户端标识，不做。
- **不为「同账号 6 路并行」加本地排队**：串行/3 路本就健康，6 路才恶化；生产会话扇出峰值 6 但并发 1 占 68%，加排队会把正常请求变成延迟，收益为负。
- **慢尾的根因在 origin 实例状态**（同一 `x-mm-trace-id` 会命中不同 `ens-cache` 编号且耗时差异 7 倍），只能观测，不能从插件侧干预。
