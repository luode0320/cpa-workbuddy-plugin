## 一、缺陷 C：内容审核拦截未进入失败分类（含 200→403 重映射）

### 1.1 现象

`glm-5.3-flashx` 近 24h：1671 次请求失败 **1465 次（88%）**，
`qwen3.8-flash` 14 条同源。日志错误模板聚合显示
`sensitive content` 命中 **924 次**，是该时段最大失败源。

每次失败前上游要先思考 **14~23 秒**才被审核截断
（`conductor_execution` 实测 `duration=14.421s / 17.268s / 23.331s`），
用户每次白等 15~20 秒。

### 1.2 根因（两层）

**第一层**：`isContentModerationFailure`（`policy.go:371`）早在 2026-11-09
就已实现，但**只被 `envelopeHTTPStatusForError` 用于决定对外状态码，
从未进入 `classifyUpstreamFailure`**。这类失败落到判定链最后一步
`failureScopeNone`：既不写冷却、也不写禁用，插件没有任何机制让它退出路由。

**第二层（0.5.46 修复后仍无效的真因）**：
`reconcileAfterExecutorErrorForModel`（`executor.go:845`）在记账前把
`status == 200` 重映射成 **403**：

```go
if status == 200 { status = 403 }
```

上游的内容审核是以 **HTTP 200 + event:error** 下发的，因此
`classifyUpstreamFailure` 实际收到的是 `(403, "sensitive content …")`。
0.5.46 把审核判定放在判定链第 7.5 步（账号级 4xx **之后**），
`isAccountLevel4xxExcludingRateLimit(403)` 先命中并返回 `failureScopeAccount`，
审核分支**永远走不到**。

生产印证：0.5.47 部署后 5 分钟，`glm-5.3-flashx` 单请求 `duration` 仍为
`p50=27.9s / p90=33.3s / max=63.1s`，扇出 10 个账号，
`model circuit opened` 日志**一条都没有**。

### 1.3 修复（0.5.48）

把 `isContentModerationFailure` 从第 7.5 步上移到**第 4.5 步**
（模型级限流之后、账号级 4xx 之前），归入 `failureScopeModelRateLimit`。

选该维度而非 account / account_model 的理由：前两者
`disablesAccount()==true`，会把与账号健康无关的审核失败写盘禁用、逐个摘掉整池；
只有 `model_rate_limit` 同时满足 `recordsCooldown()==true`（写冷却）与
`disablesAccount()==false`（不禁用账号）。

### 1.4 验证

`TestContentModerationClassifiedAsModelRateLimit` 增加 403 生产形态断言
「不得被账号级 4xx 吞掉、不得写盘禁用」。哨兵：把判定移回账号级 4xx 之后
该用例立即 FAIL。

## 二、缺陷 D：模型级熔断窗口不退避

### 2.1 现象

0.5.47 引入的熔断用**固定 60s 窗口**，`isModelCircuitOpen` 在窗口到期时把
`modelCircuitHits` / `modelCircuitAuths` 整组 `delete`，计数归零后要重新
累计 3 个账号才再开闸。

0.5.48 部署后 15 分钟实测：`glm-5.3-flashx` **`done`=0、`attempt error`=136，
即 100% 失败**；熔断开闸 **8 次**，间隔恒为 **60~90 秒**，
`cross_auth_hits` 从 3 一路涨到 10。

### 2.2 修复（0.5.50）

新增 `modelCircuitStreak` 记录连续开闸次数，驱动指数退避：
首次 60s，此后 120s → 240s → 480s → 960s …封顶
`modelCircuitMaxWindow = 30min`。窗口到期时**不再清零 streak**，
只把 hits 降到 `threshold-1`；只有 `resetModelCircuit`（任一真实成功）才清零。

### 2.3 验证

`TestModelCircuitWindowBacksOff`（退避阶梯与封顶）、
`TestModelCircuitWindowSurvivesReopen`（窗口过期不得清 streak）。
哨兵：把到期分支改回 `delete` 后后者立即 FAIL。

## 三、缺陷 E：refresh runner 漏接实例守卫

### 3.1 现象

`/proc/2904368/maps` 实测进程内同时 mmap **9 代** `.so`
（`v0.5.41/42/44/45/46/47/48/50/51`）。`main.go:141` 的
`cliproxyPluginShutdown` 是有意空实现，每代 goroutine 都活到进程结束。

`refresh_runner.go` 的 `init() { go globalRefresh.run() }` 是**事件驱动 worker**，
但两处覆盖清单（`guardedLoops` 与 `TestInstanceGuardCoversEveryGoroutineLoop`
的 files 列表）**同时漏掉了它**。而它正是 `gradeCreditsForAuth` 的唯一上游。

`v0.5.41` 的编译期禁用线是 **100**，于是 `04:16:18` 一次性把
`remain = 19/37/65/66/67/69/71/75/81/85/87/91/92` 的 **12 个健康号**
全部写盘禁用，可用池从 10 掉到 **8**。

日志顺序可证是插件自己写的：`low-credit disabled` **先于**宿主
`auth file changed (CREATE)`。

### 3.2 修复（0.5.51）

双重防线：
- **防线 1**：`doFetchOne` 入口先判 `pluginInstanceSuperseded()`，
  挡在真正产生副作用的那一行之前；
- **防线 2**：`drainBatch` 派发任务前调 `retireIfSuperseded("refresh runner")`。

### 3.3 验证

`guardedLoops` 补入 `{"refresh_runner.go", "refresh runner"}`，新增
`TestDoFetchOneRejectsSupersededInstance` 锁定「守卫必须存在且早于
gradeCreditsForAuth」。哨兵：同时移除两处后两个用例均 FAIL。

## 四、缺陷 F/G/H：纠正循环的三个递进缺口

### 4.1 缺陷 F：只认阈值指纹（0.5.52）

`refresh_runner` 修好后，旧代仍在写 `disabled:true +
low_credit_disable_below:100`。新增 `stale_disable_correct.go`，
按**阈值指纹**识别跨代写入：盘上 `low_credit_disable_below` 大于当前生效线时，
这条禁用不可能是本代写的（本代只写 `effectiveLowCreditDisableBelow()`）。

释放条件五条全满足：`disabled` 为真、带 `low_credit_disable`、
盘上阈值 > 生效线、当前余额 >= 生效线、无 `manual/failover/exhausted`。

实测：`05:17:47` 一次 `sweep released 23 account(s)`，
账号池 `2/51 → 23/51`。

### 4.2 缺陷 G：3 分钟周期不足（0.5.53）

0.5.52 的 3 分钟周期不足以对抗旧代：`05:17:47` 释放后，
`05:20:52` 旧代一次 tick 又把整池打回 **0/51**。
净效果是 `disabled: 69` 对 `re-enabled: 69` 的持续拉锯。

修复：周期 3 分钟 → **45 秒**，首轮延迟 45 秒 → **10 秒**，
并新增前置过滤（`hostAuthListAll` 结果已带 `Disabled`，未禁用的跳过不读物理文件）。
新增 `TestStaleDisableCorrectIntervalBeatsOldGeneration` 机械锁定
「周期 <= 1 分钟、首轮 <= 15 秒、且严格小于 `watchdogIntervalDefault`」。

实测：`05:31:35` 一次释放 **30 个账号**。

### 4.3 缺陷 H：漏掉无标记孤儿（0.5.54）

`correctStaleDisable` 的条件 2 要求盘上必须有 `low_credit_disable` 标记，
否则直接 return。但宿主重建 auth 文档时会把 note 与**全部**标记一起抹掉
（`host.auth.save` 只保留白名单键），盘上只剩 `disabled:true`。

生产签名分布（06:16）：

| 数量 | 标记 | `below` | 性质 |
|---|---|---|---|
| 7 | `low_credit_disable` | 10 | 0.5.53 按正确阈值禁的（真耗尽） |
| 10 | `low_credit_disable` | 100 | 旧世代写的 |
| **11** | **无任何标记** | — | **孤儿，纠正循环完全没覆盖** |

11 个孤儿里 **5 个余额充足却被禁用**：
`remain = 46 / 65 / 79 / 681`，其中 `1976299962238316` 是 remain=681 的活跃账号。

修复：判据拆成两型——2a 有标记型仍用阈值指纹；
2b 孤儿型用「`manual/failover/exhausted` 三者皆无」本身作为无主证据。

实测：`06:26:31` 首轮 `released 27 account(s)`。

## 五、缺陷 I：首字闸门在上游空闲期间无法放行（最关键）

### 5.1 现象

`gate delay`（上游首帧 → 客户端首帧）全量 6091 个样本：

```
p50=289ms  p90=1274ms  p99=1583ms  max=25780ms
gate_ms<=0: 2613 (42.9%)
```

`>2000ms` 的 45 条中，**42 条是 `minimax-m3.1-flash`（93%）**：

| 样本 | 异常点 |
|---|---|
| `gate_ms=19850` 而 `ttft_ms=10001` | **首字早已到达，客户端多等 19.8 秒** |
| `gate_ms=11902` 但 `chunks=14` | 仅 14 个分片却积压 11.9 秒 |

该模型 gate 分布：`p50=546ms` 但 **`p99=16003ms`**。

### 5.2 根因

`pumpTraeStreamAttempt` 的「持有超时」判据 `heldTooLong`
（`stream.go:1003`）**只在 `output` 事件回调里计算`：

```go
heldTooLong := !result.FirstOutputAt.IsZero() &&
    time.Since(result.FirstOutputAt) >= pseudoGateMaxHold
```

上游若在首帧之后长时间不发新事件（只送心跳 / 注释 / 半个帧），
`scanSSE` 的 `r.Read` 会一直阻塞，**回调根本不会被调用**，
判据就永远算不到——已缓冲的首字被一直压到下一个事件到达。
`pseudoGateMaxHold = 1200ms` 因此形同虚设。

### 5.3 修复（0.5.55）

- `scanSSE` 新增**可选** `onIdle` 回调（可变参数实现，
  **既有 4 个调用点零改动**），在每个读批次解析结束后调用一次；
- `pumpTraeStreamAttempt` 把放行动作抽成 `flushPending` 闭包，
  同时挂在 `output` 回调（攒够 600 健康字符）与 `onIdle`（上游空闲超时）两处；
- 通过新增 `scanSSEWithIdle` 显式传入，语义清晰不依赖隐式全局。

### 5.4 验证（端到端实测）

构造 >20k 字符输入触发闸门，实测：

```
minimax-m3.1-flash        首字 2168 / 2442 / 3034 / 3616 ms
DeepSeek-V4-Pro-Official  首字 3917 / 4434 / 13281 ms

0.5.55 后 gate_ms: p50=1293  p90=1347  max=1347
gate>2000ms 的: 0 条
```

| 指标 | 0.5.54 | 0.5.55 |
|---|---|---|
| gate max | **25,780 ms** | **1,347 ms** |
| gate >2000ms | 45 / 6,091 | **0** |

`gate_ms` 被牢牢收敛在 `pseudoGateMaxHold = 1200ms` 附近（实测 1,347ms 含调度抖动），
证明 `onIdle` 在每个读批次结束后都正常触发了。

## 六、对用户三个疑问的实测裁决

### 6.1 「会不会是连接池的问题？」——已排除

**同一账号**跨输入规模的 TTFT（8 个账号全部单调）：

| 账号 | <150k | 150–400k | 400k+ |
|---|---|---|---|
| `1976299962238316` | 4,844 ms | 8,330 ms | 13,475 ms |
| `2187406194281248` | 4,485 ms | 8,040 ms | 12,316 ms |
| `4298468521433865` | 6,845 ms | 9,189 ms | 16,805 ms |

同一账号、同一链路、同一连接池，TTFT 完全随输入规模单调增长（约 2.7–3.5 倍）。
**连接池不会按输入规模变化。**

补充事实：`host_bridge.go:134/393` 注释明确——生产流式请求默认全部走
宿主桥 `host.stream.do`，**插件的连接池配置对它无效**
（`MaxIdleConnsPerHost=64` 等配置只影响直连回退路径）。
插件已内置 `stream_direct_forced` 开关用于 A/B 对照。

### 6.2 「20w 输入 + 500 输出，首字 20s+」——数据不支持

精确匹配该场景（`150k <= input <= 260k` 且 `300 <= output <= 700`）的
**430 条样本**：

```
TTFT p50 = 8,163 ms          ← 不是 20s
traework  p50 = 7,281 ms  (n=272)
workbuddy p50 = 9,766 ms  (n=158)   ← traework 反而快 25%
```

### 6.3 「trae 比 workbuddy 慢很多」——部分区间成立，主因是输入规模

| 输入区间 | traework | workbuddy |
|---|---|---|
| 50k–150k | 5,484 ms (n=1168) | **3,280 ms** (n=2782) |
| 150k–300k | **7,476 ms** (n=2191) | 8,775 ms (n=614) |
| 300k–500k | 10,685 ms (n=2181) | **5,641 ms** (n=264) |

真实输入 p50：`traework` **46.5 万** vs `workbuddy` **9.8 万**，相差 **4.8 倍**。
比较的不是同规模请求。

### 6.4 「workbuddy、trae 都要注意上下文超限」——已证伪

输入超过 100 万 token 的 7 条请求**全部成功**：

```
23:01  traework  in=1,000,357  out=328  failed=False
23:07  traework  in=1,019,841  out=106  failed=False
23:20  workbuddy in=1,039,214  out=347  failed=False
23:21  workbuddy in=1,039,214  out=548  failed=False
```

分桶失败率：600k–800k `4/2562 = 0.2%`、800k–950k `0/68`、
950k–1.1M `0/20`（traework）与 `0/4`（workbuddy）。
全量日志中 `context` / `length` / `too long` / `truncat` 关键词命中数为 **0**。

**上下文窗口不是瓶颈，插件侧不含任何长度截断逻辑。**

## 七、遗留：跨代 13 实例对抗，插件侧无法消除

排查末期 `/proc/2904368/maps` 显示 mmap 代数已从 8 代累积到 **13 代**
（`v0.5.41/42/44/45/46/47/48/50/51/52/53/54/55`）。

`strings` 逐代核对是关键证据：

```
v0.5.41  "watchdog loop" 文案: 0   ← 无 retireIfSuperseded 闸门
v0.5.42  "watchdog loop" 文案: 0
v0.5.44  "watchdog loop" 文案: 0
v0.5.45  "watchdog loop" 文案: 1   ← 0.5.45 才引入该闸门
```

**这三代的 watchdog 里根本没有实例守卫，无条件永久运行**，每 5 分钟
（多代交错 tick）用编译期常量 100 重写禁用标记。实测对抗节奏：

```
07:00:51–52  旧代禁用 23 个账号（remain=12/19/25/27/36）
07:01:07     0.5.55 sweep 全部释放（30 秒后）
             ↓ 5 分钟后重复
```

账号池在 **23–30** 之间震荡。

**根治需要重启容器清空 13 代 mmap，用户硬约束明确禁止。**
在不重启的前提下，当前 45 秒纠正周期 + 30 秒恢复已是理论上限。

另：每安装一次新版就多一代 watchdog，对抗会随热重载次数**加剧**。
建议在重启窗口出现前**停止继续热重载**，新改动走本地 `cgo-shim-build` 验证。
