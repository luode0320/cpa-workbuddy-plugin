# TraeWork 签到 x-device-id 拼接与尾零风控 9074 拦截

结论：是缺陷。TraeWork 签到接口（`/trae/api/v2/ug/checkin_credits/claim`）对请求头 `x-device-id` 实施了格式与号段风控校验：只接受真实 SOLO 客户端形态的 16 位纯数字设备 ID（以 `1`~`3` 开头、无连续尾零填充，如真实样本 `3418807932843306`）。现有代码存在两处叠加缺陷：① `checkin.go` 的 `deviceIDFor(baseDeviceID, userID)` 将设备 ID 与用户 ID 用连字符拼接为 `<baseDeviceID>-<userID>`（33 字符含 `-`），100% 命中服务端风控返回业务码 `9074`（`"当前参与用户太多，请稍后再试"`）；② `browserlogin.go` 的 `randomDeviceID()` 从 16 个十六进制字符中过滤十进制数字后末尾补 `'0'`，导致生成的 `deviceId` 末尾带 3~10 个连续 `'0'` 且首位可能落在 `'6'`~`'9'`（如「用户04878311608」的 `9670064000000000`），即便不拼接 `-userID` 也同样被服务端 9074 拦截；且签到失败重试时始终复用同一个被拦截的 `x-device-id`，导致自动与手动重试全部失败。

影响：生产环境未签到账号（含「用户04878311608」`1114256688551036`、「用户35650007802」`2433670276462265`、「用户23601284588」`4491956683805020` 等）在插件内手动签到与每 4 小时自动签到均持续返回 `9074 当前参与用户太多，请稍后再试`，多个账号出现连续多日断签。

范围：`traework/checkin.go`、`traework/browserlogin.go`、`traework/checkin_headers_test.go`、`traework/browserlogin_test.go`。不涉及对话推理链路、不涉及宿主桥接。

非范围：不改动管理面板 UI 结构；不改动签到定时班次（仍为每 4 小时）与重试队列周期。

变化：
1. `deviceIDFor(baseDeviceID, userID)` 改为生成符合真实 SOLO 客户端规范的 16 位纯数字设备 ID：当单输入已是合法 16 位客户端设备 ID（首位 `1`~`3`、纯数字、无连续 4 个及以上尾零）且无 `userID` 时直接复用；否则基于 `sha256(baseDeviceID + ":" + userID)` 确定性派生 16 位纯数字 ID（首位 `1`~`3`，末位 `1`~`9`），既消除 `-` 拼接与存量尾零畸形 ID，又保持同机多账号设备 ID 互异。
2. `checkinAccount(a *traeAuth)` 在首次请求若仍遇到 `9074`（`isBusyThrottleMsg`）或 `9095` 设备级去重拦截（`DeviceBlocked`）时，自动切换为新生成的合法 16 位随机数字设备 ID 重试（最多重试 3 次），不再复用已触发风控或已被占用的同一 `x-device-id`。
3. `randomDeviceID()` 改为基于 `crypto/rand` 直接生成 16 位纯数字（首位 `1`~`3`，中间 14 位 `0`~`9`，末位 `1`~`9`），根除 `randomHex(8)` 过滤非数字后末尾补 `'0'` 的缺陷。

完成标准：本地 `python scripts/cgo-shim-build.py traework` 编译、`go vet`、单元测试（含必失败哨兵反证）全绿；`6-review` 风格回归通过；发布 `traework-provider 0.2.5` 并部署到生产服务器热重载后，对「用户04878311608」及全量 TraeWork 账号调用插件 `/checkin` 接口均返回 `ok: true` 且积分真实到账。

术语说明：`x-device-id` 是 Trae 客户端请求头中的 16 位纯数字设备标识；业务码 `9074` 是上游对异常设备指纹或分桶限流返回的拒绝码（文案为「当前参与用户太多，请稍后再试」）；业务码 `9095` 是同一 `x-device-id` 当日已被另一账号签到时返回的设备级去重拒绝码（文案为「当前设备今日已经签到，请明日再来哦～」）。

验证状态：生产环境已复现并通过多组单变量对照实验锁定根因；「用户04878311608」在对照实验中替换为合法 16 位数字 `x-device-id` 后当场签到成功（积分包从 2 个增至 3 个，剩余积分从 130 增至 230）。代码修复、本地单测与生产 0.2.5 部署验收推进中。

## 根因

1. **`deviceIDFor` 字符串拼接破坏 16 位数字设备 ID 格式契约**（`traework/checkin.go:34`）：
   `deviceIDFor` 返回 `baseDeviceID + "-" + userID`（如 `9670064000000000-1114256688551036`），非 16 位纯数字，直接命中上游 `/claim` 风控返回 `9074`。
2. **`randomDeviceID` 十六进制过滤补零导致尾零畸形与号段越界**（`traework/browserlogin.go:265`）：
   `randomHex(8)` 仅有 16 个十六进制字符，过滤掉 `a-f` 后只剩 6~10 个十进制数字，不足 16 位全部在末尾补 `'0'`，且首位可能落在 `'6'`~`'9'`（超出真实 SOLO 客户端 `1`~`3` 开头号段），导致生成的 `deviceId`（如 `9670064000000000`）即使不拼 `-userID` 也被上游 `9074` 拦截。
3. **签到重试固定复用同一 `deviceID`**（`traework/checkin.go:108`）：
   `checkinAccount` 在循环外计算一次 `deviceID`，遇到 `9074` 或 `9095`（设备去重拦截）时未切换新的合法 16 位 `deviceID`，导致重试永远命中同一拦截。

## 修复方案

1. **重写 `deviceIDFor(baseDeviceID, userID string)`（`traework/checkin.go`）**：
   - 新增 `isValidCheckinDeviceID(id string) bool`：校验是否为 16 位纯数字、首位在 `'1'`~`'3'` 之间、且末尾不以 `"0000"` 结尾。
   - 新增 `deriveCheckinDeviceID(seed string) string`：使用 `sha256` 对种子计算摘要并确定性映射为 16 位纯数字（第 1 位 `'1'~'3'`，第 2~15 位 `'0'~'9'`，第 16 位 `'1'~'9'`）。
   - `deviceIDFor(baseDeviceID, userID)`：两者均空返回 `""`；仅 `baseDeviceID` 非空且已满足 `isValidCheckinDeviceID` 时直接返回 `baseDeviceID`；其余情况返回 `deriveCheckinDeviceID(baseDeviceID + ":" + userID)`。
2. **增强 `checkinAccount` 风控/设备碰撞轮换重试（`traework/checkin.go`）**：
   - 当上游返回 `isBusyThrottleMsg(msg)`（9074）或 `DeviceBlocked(msg)`（9095）且 `attempt < 3` 时，调用 `randomDeviceID()` 切换为全新的合法 16 位数字设备 ID 并重试。
3. **修复 `randomDeviceID()`（`traework/browserlogin.go`）**：
   - 使用 `crypto/rand` 读取 16 字节随机数，直接映射为 16 位纯数字字符串（首位 `'1'~'3'`，中间 14 位 `'0'~'9'`，末位 `'1'~'9'`），消除末尾补 `'0'` 与号段越界问题。
