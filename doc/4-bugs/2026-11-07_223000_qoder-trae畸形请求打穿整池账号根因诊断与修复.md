# qoder/trae 生产高强度压测：畸形请求打穿整池账号根因诊断与修复

## 一、问题描述

用户要求「对生产的 qoder、trae 插件高强度测试 deepseek-flash，看有什么 bug 并及时修复」。本轮在生产 45.207.222.65 上对 `qoderwork-provider`（dfmodel）与 `traework-provider`（deepseek-flash / qwen3.8-max）做了参数矩阵、并发、工具调用、错误路径四轮压测。

**发现的最高危缺陷**：一次客户端请求体畸形的请求，就能把插件管理的**整个账号池**逐个写盘禁用，之后所有正常请求返回 503 `auth_unavailable`，直至 10 分钟探活把号捞回。

### 2.3 归属判定：插件缺陷，不是上游问题

上游行为完全正确且可预期 —— 同一个请求体换任何账号都会被同样拒绝。问题在插件把「请求体不合法」记在了账号头上。

## 三、根因

两个插件的失败分类**只能按 HTTP 状态码识别「请求形状问题」**：

- `traework`：`isRequestShapeFailure(status int)` 只认 **400/422**；
- `qoderwork`：`isModelLevelFailure(body)` 只认「后端池不可用」类文案（`all backends failed` / `no available backend` 等）。

而两个上游都把客户端请求体错误包在 **HTTP 200 的 `event:error` 帧**里：

| 插件 | 上游实际返回 |
|---|---|
| qoderwork | HTTP 200 + `provider_error: Error in upstream response` |
| traework | HTTP 200 + `tool call failed: invalid_parameter_error:wizard is not one of [...]` |

状态码判据命中不到 → 落进通用账号级分支 → `recordAccountFailure` / `recordFailureScoped` 记账 → 写盘禁用 → 同一请求换号 → 换到的下一个号收到同样的请求体、同样的错误 → 再禁用……直到池空或换号预算耗尽。

## 四、修复

### 4.1 新增按正文的请求形状判据

两个插件各自新增一组 marker 与判定函数（qoderwork 命名为 `isRequestShapeFailure(body)`，traework 命名为 `isRequestShapeErrorBody(body)` 以避开既有同名状态码判据）：

```go
var requestShapeFailureMarkers = []string{
    "is not one of", "invalid_parameter", "invalid parameter",
    "invalid request", "cannot unmarshal", "unmarshal",
    "missing required", "required field", "field validation",
    "bad request", "tool call failed",
}
```

### 4.2 豁免分支严格限定 HTTP 200

这是本轮修复最关键的一处设计取舍。初版写成 `status != 0` 后收到两次既有测试拦截：

| 尝试 | 被拦截的用例 | 说明 |
|---|---|---|
| `status != 0 && ...` | `status=0 body="{\"error\":\"invalid request body\"}"` | status==0 是传输层失败，body 是**插件本地拼的错误文本**而非上游响应 |
| `status == 200 \|\| status >= 500` | `status=401 body="{\"error\":\"invalid request body\"}"`、`status=500 ...` | 401/403/404/405 是确定性凭据问题、402 是额度耗尽、5xx 是服务端故障，都必须照旧记账 |

最终形态：

```go
// traework/failure_class.go
if status == http.StatusOK && isRequestShapeErrorBody(body) {
    return failureScopeNone
}
// qoderwork/accountFailover.go
if status == http.StatusOK && isRequestShapeFailure(body) {
    return false
}
```

既有测试 `TestClassifyUpstreamFailureMatchesLegacyCountGate`（14 个状态 × 15 种正文全枚举，断言「分类需要记账 ⟺ 历史门槛记账」）因此保持全绿 —— 它正是防止这类改动悄悄放宽记账范围的门禁。

### 4.3 traework 附带修复：`max_completion_tokens` 别名被丢弃

同一批压测发现的第二个缺陷：`openAIRequest` 只有 `max_tokens` 字段，新客户端（DSH / Codex 系）只发 `max_completion_tokens` 时该值被 `json.Unmarshal` 静默丢弃。

生产实测（通过 feed 归因确认落在 traework 的轮次）：请求 `max_completion_tokens=12`，实际产出 **1091 字符 / 1119 tokens**（`finish=stop`，完全未被约束）。

修复：结构体补 `MaxCompletionTokens int`，新增 `effectiveMaxTokens(req) int`（显式 `max_tokens` > 别名 > 0=未传），流式与非流式两处 `buildTraePayload` 调用统一改走它。

修复后同条件实测：`max_tokens=12` → 12 token / `finish=length`；`max_completion_tokens=12` → 12 token / `finish=length`（两者一致，别名已生效）。

## 六、未覆盖与边界

- **上游语义差异**（非缺陷，记录备查）：
  - traework 的 `qwen3.8-max` / `minimax-m3` / `mimo-v2.6-flash` / `step-5-preview` / `Doubao-Seed-Code` **完全忽略 `max_tokens`**（`mt=12` 仍输出 1091 字符 / 2280 tokens）；`glm-5.3-flash` / `deepseek-v4.1-flash` 正常遵守。

## 七、方案迭代：0.5.15 / 0.13.8 正文匹配方案失效，改前置校验（0.5.16 / 0.13.9）

### 7.1 第一次方案为何没修好（生产复验实测）

0.5.15 / 0.13.8 上线后按同一脚本复验，结果**与修复前完全一致**：

```
[dfmodel] 基线: ok=True fin=stop wall=1.36s
[dfmodel] 畸形: ok=False st=500 err={"error":{"message":"upstream 200: provider_error: Error in upstream response"
[dfmodel] 复测1..5: 全部 503 auth_unavailable
>>> [dfmodel] 0/5 正常请求成功

[deepseek-flash] 畸形: err=upstream 200: tool call failed: The parameter `messages.role` ...
[deepseek-flash] 复测1..5: 全部 503 auth_unavailable
>>> [deepseek-flash] 0/5 正常请求成功
```

**失效原因**（两条，都是原理级的）：

| 插件 | 上游实际报错 | 为何正文匹配拦不住 |
|---|---|---|
| qoderwork | `provider_error: Error in upstream response` | 报错里**没有任何**可用于识别「请求形状」的文案，正文匹配从原理上不可能生效 |
| traework | `tool call failed: The parameter \`messages.role\` ... are not valid: invalid value: \`wizard\`, supported values are: ...` | 与早期实测的 `wizard is not one of [...]` 是**两种不同措辞**；marker 表命中了后者，漏了前者 |

结论：**按上游报错正文去猜「这是不是客户端错误」本身就是错的抽象**。上游措辞会变、可能无信息量，而「请求体是否合法」是本地就能确定的事实。

### 7.2 真正修复：发请求前校验 role

两个插件各自新增合法角色表与校验函数，在**流式与非流式两个入口**、构造上游请求体之前拦截：

```go
var validOpenAIRoles = map[string]bool{
    "system": true, "user": true, "assistant": true,
    "tool": true, "developer": true, "function": true,
}
```

非法 role → 直接返回 `invalid request: messages[N].role "X" is not a valid role`（HTTP 400），
**请求根本不发往上游**，因此不会触发任何账号记账、不会换号、不会写盘禁用。

原有的正文判据（`isRequestShapeFailure` / `isRequestShapeErrorBody`）保留为第二道防线，
覆盖 role 之外的其他请求形状错误（参数类型错误、字段越界等），但不再是主防线。

### 7.3 方案对比

| 维度 | 正文匹配（0.5.15 / 0.13.8） | 前置校验（0.5.16 / 0.13.9） |
|---|---|---|
| 判定依据 | 上游报错措辞 | 本地请求体结构 |
| 上游换措辞 | 失效 | 不受影响 |
| 上游无信息量报错 | 失效 | 不受影响 |
| 是否需要先打一次上游 | 需要（才能拿到报错） | 不需要 |
| 换号/记账副作用 | 仍会触发一次 | 完全不触发 |

## 八、复验结论：插件侧已修复，剩余放大来自宿主重试策略

### 8.1 0.5.16 / 0.13.9 生产复验实测

| 项目 | 修复前（0.5.14 / 0.13.7） | 0.5.15 / 0.13.8（正文匹配） | 0.5.16 / 0.13.9（前置校验） |
|---|---|---|---|
| 畸形请求返回值 | 500，耗时 1~2s（打了上游） | 500，耗时 1~2s（打了上游） | **500，耗时 0.01~0.04s**，报文 `invalid request: messages[0].role "wizard" is not a valid role` |
| 是否发往上游 | 是 | 是 | **否** |
| 账号是否被写盘禁用 | 是（8/8、9/9 全禁） | 是 | **否（disabled=0）** |
| 是否产生 failover 禁用日志 | 是 | 是 | **否（0 条）** |
| 畸形请求后的正常请求 | 503 | 503 | 503（原因见下） |

### 8.2 503 的真正来源：宿主 CPA 的 request-retry: 30

过滤掉 coze 插件的日志噪声后，宿主日志显示**同一次畸形请求被扇出到全部账号**：

```
23:24:44 [3096bc5c] upstream execution failed: provider=traework-provider auth_file=traework-1835541700020409.json
  duration=1ms err=invalid request: messages[0].role "wizard" is not a valid role
23:24:44 [3096bc5c] ... traework-2033439621254311.json duration=1ms err=同上
23:24:44 [3096bc5c] ... traework-2310519631118649.json duration=1ms err=同上
（池内 10 个账号全部遍历一遍，每次 1ms —— 说明插件根本没发上游，是宿主在自己重试）
```

宿主配置：

```yaml
retry:
  request-retry: 30          # 任何失败都重试 30 次并换账号
  max-retry-credentials: 0   # 0 = 不限账号数
```

宿主把插件返回的 400 当成「这个账号不行，换下一个」，遍历完全部账号后由宿主自己合成
`503 auth_unavailable`。**这一层放大发生在插件之外**，插件侧无论如何记账都无法阻止。

### 8.3 决定性对照：池本身完全健康

不发畸形请求、只连发正常请求（与畸形测试间隔数分钟）：

```
dfmodel        5/5 全部 200（1.05~1.53s）
deepseek-flash 5/5 全部 200（1.38~1.96s）
```

证明：0.5.16 / 0.13.9 的账号池**没有被畸形请求破坏**，之前版本的「整池被写盘禁用、需要等探活」的故障形态已经消失。

### 8.4 剩余问题的处置建议（属宿主侧，未改动）

宿主 `config.yaml` 支持按请求范围分类错误，可以把插件的 400 声明为终态、不做账号轮转：

```yaml
request-scoped-errors:
  - status: 400
    match:
      - "invalid request:"
    action: "stop"     # 直接返回错误，不换号、不冷却
```

该配置项在宿主 `config.yaml` 的注释里已有官方说明（`request-scoped-errors` / `action: stop`）。
**本轮未擅自改动生产宿主配置**——它属跨项目写入范围外的宿主配置变更，且需要先确认
`request-scoped-errors` 是否对插件路径生效。建议由用户决定是否启用。

### 8.5 边界与未覆盖

- 本轮修复把「一次畸形请求污染账号池」彻底消除了（账号不再被禁用），但**没有消除宿主的 30 次无用重试**，因此畸形请求本身仍会返回 503 而非 400。这是宿主策略，不是插件缺陷。
- 宿主的 `request-retry: 30` 对**任何** 400 类业务错误都会放大（当前配置下放大倍数是池内账号数），影响面不限于本插件。
