# coze 兜底种子写死上游下线模型致别名 400 根因诊断

- 时间：2026-11-20 22:18
- 版本：coze-provider 0.7.7 → 0.7.8（插件侧）；宿主侧配置热修已于 22:16 先行完成
- 环境：生产（cpa.luode.vip / 45.207.222.65，容器 `cli-proxy-api`，network=host）
- 发现渠道：用户在 CPA 管理台「测试渠道连接 → 混合」里点测 9 个模型，`doubao-seed-pro` 红字失败

## 1. 现象

管理台弹窗原文（截图逐字）：

```text
渠道 混合 模型 doubao-seed-pro 测试失败
bad response status code 400, message: unknown provider for model doubao-seed-pro,
body: {"error":{"message":"unknown provider for model doubao-seed-pro",
"type":"invalid_request_error","code":"model_not_found","param":"model"}}
```

同一提供商的另一条别名 `gpt-image-2` 正常；同一弹窗里 `doubao-seed-pro` 之外 8 个模型均未测试。
管理台「认证文件 → OAuth 模型别名」当时的两条映射：

| name | alias |
|---|---|
| `coze/doubao-seedream-5-0-pro` | `gpt-image-2` |
| `coze/doubao-seed-2-0-pro-260215` | `doubao-seed-pro` |

## 2. 取证

### 2.1 400 的产出点：宿主根本没找到 provider

`F:\CLIProxyAPI\sdk\api\handlers\handlers_routing.go:159-224` `getRequestDetailsWithOptions`：

```go
baseModel := thinking.ParseSuffix(modelName).ModelName
providers := util.GetProviderName(baseModel)
if len(providers) == 0 && baseModel != resolvedModelName {
    providers = util.GetProviderName(resolvedModelName)
}
if len(providers) == 0 {
    // sjson.Set body error.message = "unknown provider for model " + modelName
    // StatusCode = 400
}
```

`F:\CLIProxyAPI\internal\util\provider.go:46-79` `GetProviderName` 只查 `GlobalModelRegistry().GetModelProviders(modelName)`，**没有任何字符串启发式兜底**。`F:\CLIProxyAPI\internal\registry\model_registry.go:1581-1630` 里查不到就返回 nil。

⇒ `unknown provider for model` 的语义是「这个名字从未被注册进全局模型目录」，与插件、上游、账号是否健康**完全无关**。这是一条误导性极强的报错，看起来像服务商配置错，实则目录里没有这个名字。

### 2.2 生产目录实证：一条别名进了目录，另一条没有

`GET http://127.0.0.1:8317/v1/models`（Bearer 管理密钥）共 **70 条**，`owned_by=coze-provider` 19 条：

- `gpt-image-2` **存在**（第一条别名生效）
- 搜 `seed-pro` **0 条**（第二条别名完全没进目录）
- `coze/doubao-seed-2-0-pro-260215` **存在**（原名在）

三发 `POST /v1/chat/completions`（max_tokens=1）：

| 模型名 | HTTP | body 摘要 |
|---|---|---|
| `doubao-seed-pro` | **400** | `unknown provider for model doubao-seed-pro`（与截图 byte 级一致） |
| `coze/doubao-seed-2-0-pro-260215` | **503** | `auth_not_found: no auth available (providers=coze-provider, ...)` |
| `gpt-image-2` | **503** | `only supported on /v1/images/generations`（已正确路由到 coze-provider，只是端点不匹配） |

### 2.3 别名配置本身没问题

`GET /v0/management/oauth-model-alias` 回读，`coze-provider` 两条映射**原样存在**，`fork` 均 true。生产 `config.yaml` 第 816-870 行是 `oauth.model-alias`（新键名，与顶层 `oauth-model-alias` 经 `config_v8.go:46` 的 legacy 映射等价）。`oauth.excluded-models`（第 757-815 行）里**没有 coze-provider 段**，排除规则也不是成因。

### 2.4 关键证据：别名只对「目录里真实存在的 name」生成

`F:\CLIProxyAPI\sdk\cliproxy\service_models.go:1025-1134` `applyOAuthModelAliasEntries`：

```go
entries := forward[key]                      // key = strings.TrimSpace(model.ID)
if len(entries) == 0 {
    entries = forwardFolded[strings.ToLower(key)]
}
if len(entries) == 0 {
    out = append(out, model)                 // ← 匹配不到就原样放行，静默跳过
    continue
}
```

⇒ **别名不是独立注册的实体，而是"附着在某个已存在模型上的克隆"**。`name` 在本次 models 列表里不存在时，整条别名被丢弃，不报错、不兜底、不留日志。

对照项解释了为什么 `gpt-image-2` 一直好用：它的 `name`=`coze/doubao-seedream-5-0-pro` 确实在多模态目录里（`/api/coze_claw/resource/get_multimodal_model_catalog` 的 image_gen 分组）。

### 2.5 为什么 `coze/doubao-seed-2-0-pro-260215` 不在本次 models 列表里

12 个 coze 账号逐个查 `GET /v0/management/auth-files/models?name=<file>`：

- **12/12 全部不含 `coze/doubao-seed-2-0-pro-260215`，也不含 `doubao-seed-pro`**；
- 修复前含 `gpt-image-2` 的有 7 个，也有的账号没有（多模态目录需账号等级）。

上游直连实证（用 `coze-1c009ed5e8da50cb.json` 的 cookie，curl `POST https://www.coze.cn/v1/model/list`，`Referer: https://www.coze.cn/`）：

| `image_generation` | 2 条（seedream-5-0-260128、seedream-5-0-flash-260915） |

**上游 llm 已经不再返回 `doubao-seed-2-0-pro-260215`**（该模型已下线），多模态目录里也没有。

## 3. 根因

### 3.1 直接层：名字从未注册 → 400

`doubao-seed-pro` 不在 `GlobalModelRegistry` ⇒ `GetProviderName` 返回空 ⇒ 400。报错文案与账号、上游、插件版本无关。

### 3.2 别名不生成层：name 指向了下线模型

`F:\cpa-plugin\coze\models.go:565-587` `modelForAuth`：

```go
models := staticFallbackModels()
if sa, errAuth := authForModelRequest(&req); errAuth == nil {
    if discovered, errDiscover := cachedDiscoveredModels(sa, false); errDiscover == nil && len(discovered) > 0 {
        models = discovered          // ← 有账号时用动态目录【整表覆盖】静态种子
    }
}
```

`discovered` 就是 2.5 实测的上游目录，**不含 pro-260215** ⇒ 覆盖后该 name 消失 ⇒ 宿主 `applyOAuthModelAliasEntries` 匹配不到 ⇒ `doubao-seed-pro` 永不生成。

链条：

```text
上游下线 pro-260215
  → discoverModels 拉不到它
  → modelForAuth 用 discovered 整表覆盖种子
  → 该 name 不在 models 列表
  → applyOAuthModelAliasEntries 匹配不到、静默跳过
  → doubao-seed-pro 未注册
  → GetProviderName 返回空
  → 400 unknown provider for model doubao-seed-pro
```

### 3.3 同一病灶的另一半：种子里的下线模型仍在全局目录里

`F:\cpa-plugin\coze\models.go:520-544` `staticFallbackModels` 把 `doubao-seed-2-0-pro-260215` 写死为旗舰种子。`modelStatic`（:554-563）的返回被宿主**原样登记进全局模型目录**，所以即便 12 个账号的动态目录里都没有它，`/v1/models` 里仍有 `coze/doubao-seed-2-0-pro-260215`——用户选中它必然 `503 auth_not_found`（2.2 已实测）。

⇒ 一条下线模型同时造成「别名注册不出来（400）」和「目录里有必挂模型（503）」两个症状。

## 4. 修复

### 4.1 宿主侧：把别名源改到现役模型（生产已执行，2026-11-20 22:16）

先备份：`cp -a config/config.yaml config/config.yaml.bak.20261120_221624`（79583 bytes）。

```bash
curl -s -X PATCH http://127.0.0.1:8317/v0/management/oauth-model-alias \
  -H "Authorization: Bearer <管理密钥>" -H "Content-Type: application/json" \
  -d '{"channel":"coze-provider","aliases":[
        {"name":"coze/doubao-seedream-5-0-pro","alias":"gpt-image-2","fork":true},
        {"name":"coze/doubao-seed-2-1-turbo-260628","alias":"doubao-seed-pro","fork":true}]}'
```

返回 `{"status":"ok"}`。落盘确认：`config.yaml:868-870` 已是 turbo-260628 / doubao-seed-pro / fork: true，全文 1368 行，`grep doubao-seed-2-0-pro-260215 config.yaml` 无命中。

**选型理由**：别名源必须是目录里**真实存在**的模型，而 llm 家族现役最强的就是 `doubao-seed-2-1-turbo-260628`；同时保留 `gpt-image-2` 那条不动，避免扩大改动面。`PATCH` 只替换该 channel，宿主 `persist` 后异步重载 ⇒ **热生效，未重启容器**。

## 6. 教训

1. **`unknown provider for model X` 不是"服务商配错了"，而是"X 从未注册"**。看到这条 400 应当直接查 `/v1/models` 里有没有 X，而不是去翻服务商配置。它把「模型目录问题」包装成「提供商问题」，是最容易跑偏的一类报错。
2. **别名是"克隆"不是"新建"**：`oauth-model-alias` 的 `name` 必须指向目录里**真实存在**的模型 ID，否则整条映射被静默丢弃——不报错、不告警、不留日志。配别名前先确认 name 在 `/v1/models` 里。
3. **"插件目录能覆盖"与"配置能生效"是两个独立可失效点**：`modelForAuth` 的整表覆盖让静态种子的存在感归零，但 `modelStatic` 又把它塞进全局目录。同一个数组，两条注册路径行为相反，维护时必须同时看。
4. **上游模型下线是静默的**：`/v1/model/list` 只是"少返回一条"，不返回任何"已下线"标记。写死上游模型名的兜底种子天然带保质期，必须把「下线模型不得回到兜底目录」变成断言，否则下一次换模型又会静默失效。
5. **两条路径的目录来源不同会掩盖问题**：面板「测试渠道连接」走的是宿主全局路由（先过 `GetProviderName`），而面板「测试」按钮走 `/test-active`（插件内部直连上游）。前者 400 后者成功时，差异本身就是定位线索。
