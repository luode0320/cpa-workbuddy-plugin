# workbuddy-provider deepseek-v4.1-flash 首字延迟与生成时长极端长尾根因诊断

## 一、问题描述

- **现象**：用户报告 workbuddy-provider 使用 `deepseek-v4.1-flash` 时，部分请求「首字延迟非常久、生成时间非常非常长」。
- **用户疑问**：「结合 GitHub 其他的项目看看，是不是我们的插件有问题？」
- **结论（本诊断）**：**插件不是当前常态延迟的原因，但插件确实存在 3 个真实缺陷**，其中 2 个会**放大**长尾、1 个会让**极端长尾无法自愈**。极端长尾（>60s）全部来自上游传输层（`status_code=0`），请求体与参数均正常。

## 二、证据链（生产 45.207.222.65 实测，2026-11-07）

### 2.1 延迟分布（usage feed 全量 16,944 条 deepseek-v4.1-flash 样本）

| 指标 | p50 | p90 | p99 | max |
|---|---|---|---|---|
| 首字延迟 TTFT | 3,479 ms | 5,336 ms | 7,993 ms | **150,478 ms** |
| 总耗时 latency | 5,533 ms | 10,200 ms | 36,906 ms | **694,166 ms** |
| 生成耗时（latency−TTFT） | 1,496 ms | 6,232 ms | 31,738 ms | **690,251 ms** |

**判读**：p50 完全正常（5.5s）。问题集中在 p99 之外的极端长尾：
- TTFT > 15s：**29 条 / 16,813（0.17%）**
- 生成时间 > 20s：**299 条 / 16,813（1.78%）**
- 总耗时 > 60s：**46 条（0.27%）**

### 2.2 长尾全部是传输层失败，不是参数问题

对 `in=0`（零输入 token = 请求体未到达上游推理层）的 132 条记录核查，最慢 6 条**全部 `status_code=0`**（传输级），形态为「**HTTP 200 已建立 + 首字已返回，但后续流长时间无数据或缓慢产出**」：

```
lat=694166  ttft=3915    out=2      failed=False status=0
lat=629912  ttft=968     out=0      failed=True  status=0
lat=604394  ttft=4328    out=0      failed=True  status=0
lat=603123  ttft=3014    out=0      failed=True  status=0
lat=568201  ttft=8725    out=2      failed=False status=0
lat=398583  ttft=4805    out=450    failed=False status=0
```

**决定性对比**：慢速冷却的阈值配置 `slow_min_ttft_ms=3000`，而全池 TTFT p50=3,479ms、p90=5,336ms —— **一半以上请求本来就超过该阈值**，说明「慢」是上游大 input 场景的结构性特征，不是插件引入。

### 2.3 直连上游 vs 经插件 对照实验（同时段同 prompt）

**实验 A：长输出（要求逐条数 1..300），`reasoning_effort=max`**

| 路径 | TTFT | 总耗时 | 吞吐 |
|---|---|---|---|
| 直连 `copilot.tencent.com` | 1.70s | 5.56s | **267.0 tok/s** |
| 经插件 `127.0.0.1:8317` | 2.60~3.35s | 5.33~7.84s | 162.5~227.8 tok/s |

**实验 B：大 input（122,200 字符 → 67,637 prompt tokens），`reasoning_effort=max`**

| 路径 | TTFT | 总耗时 | completion |
|---|---|---|---|
| 直连上游 | 2.75~3.79s | 2.75~3.79s | 17~18 |
| 经插件入口 | 2.64~3.08s | 2.64~3.08s | 16~46 |

**判读**：同条件下插件与直连**同一量级**（大 input 场景甚至略快）。插件转发链路（SSE 逐帧 emit、无聚合、无 ReadAll）**没有引入可观延迟**。长输出场景插件吞吐略低（约 −20%）属宿主 32KB 分块 + 逐帧 RPC emit 的正常开销，不是数量级问题。

## 三、根因

### 3.1 主因（非插件缺陷）：上游 reasoning 与正文共享 output 预算

生产 `reasoning_effort=max` 占绝对多数（16,090/16,818 = 95.7%）。该项目记忆已确认的事实再次被本批数据验证：

- 长尾请求里 `out=17750~21943` 且 `reas=14140~18227` 的记录成组出现（如 `src=tau****5` 连续 5 条，out 19,898~21,943），耗时 119~145s；
- 这类请求的 `in` 只有 70 token，**说明耗时完全由 reasoning 生成驱动**，与上下文无关；
- 对照 `effort=none`（377 条）：lat p50=2,086ms、TTFT p50=1,656ms，比 `max` 快 **2.7 倍**。

**结论**：`reasoning_effort=max` + 大 max_tokens 让模型可无限推理，这是长生成的根本来源，**插件层无法消除**（上游无独立思考上限字段）。

### 3.2 插件缺陷一：`sharedHTTPClient` 缺 `ResponseHeaderTimeout` / `TLSHandshakeTimeout`

`workbuddy/host_bridge.go:34-41`：

```go
sharedClient = &http.Client{
    Timeout: 120 * time.Second,
    Transport: &http.Transport{
        MaxIdleConns:        20,
        IdleConnTimeout:     90 * time.Second,
        MaxIdleConnsPerHost: 5,
    },
}
```

**只有整体 `Timeout`，没有任何分阶段超时**。GitHub 同类项目一致把它列为「首字卡死」首因：

- `linguo2625469/workbuddy2api-panel` `internal/upstream/transport.go`：`DialContext` 10s + `TLSHandshakeTimeout` 10s + `ResponseHeaderTimeout` 60s + 禁 h2，注释实录「kongjianguan 实测半开 TCP **单次 TTFB 卡 936s**」；
- 该文件还记录：`ForceAttemptHTTP2=false` **不够**，ALPN 仍会协商出 h2，必须置空 `TLSNextProto`，否则报 `http2: timeout awaiting response headers`。

**生产印证**：本批 `TTFT max=150,478ms`（150 秒）的请求，前 150 秒处于「无任何数据」状态。若有 `ResponseHeaderTimeout=60s`，该请求应在 60s 内快速失败并换号，而不是让用户等满 150 秒。

**注意**：该 client 仅在宿主桥不可用时兜底（`host_bridge.go:251`），生产走宿主 `host.http.do_stream`；但宿主 `http_bridge.go:126` 用 `helps.NewProxyAwareHTTPClient(ctx, cfg, c.auth, 0)` —— **timeout 传 0 = 无总超时、也无分阶段超时**，比插件兜底路径更无约束。这解释了 `lat=694166ms`（**11.5 分钟**）为何能跑完。

### 3.3 插件缺陷二：`HostCallbackID` 定义但从未透传（客户端断连无法传导上游）

`workbuddy/main.go:915-919` 定义了 `executorStreamRequest.HostCallbackID`，但全仓 grep 该字段**仅在结构体定义处出现一次，无任何使用点**。

对比 `traework`（同构插件，已修复）：`traework/host_bridge.go:328` 把 `HostCallbackID` 放入 wire 外层，绑定宿主保留到流结束的 callback context；`traework/host_bridge.go:299` 还有 `hostBridgeReadTimeout=90s` 保护。

宿主侧证据（`rpc_client_stream.go:17-23`）：宿主**确实下发** `HostCallbackID`，且 `host_callbacks.go:160` 用 `resolveCallbackContext(callbackID, ctx)` 把它转换成能感知客户端断连的 ctx。**我们丢弃了这个 ID，等于放弃了宿主提供的取消传播通道**。

**后果**：客户端放弃等待后，插件的 `pumpUpstreamStream` 仍以 `context.Background()`（`main.go:993`）续读上游，直到上游自然结束。这条死流会持续占用 goroutine + 宿主 stream 槽位。生产 `Threads=425`、`load average 4.34`，与此类泄漏形态一致（需进一步压测确认相关性）。

### 3.4 插件缺陷三：未注入 `stream_options.include_usage`

全仓 grep `stream_options|include_usage` **零命中**。GitHub 多数同类项目均注入（`sixzjd` `upstream.js:1110`、`ithtelab` `gateway.py:1327`、`3304711297` `converter.py:4516`），注释一致：「官方客户端总在流式调用里要 usage，上游只有被要求时才在末帧上报」。

**生产印证**：本批 16,944 条记录 `output_tokens` 全部有值，说明**当前上游恰好默认返回 usage**，故此项当前无实际影响，属健壮性缺口而非现症根因。

## 四、与 GitHub 同类项目的对照结论

调研了 9 个真实反代项目源码（`tonny0812` / `lovingfish` / `zqcccc` / `sixzjd` / `dingminhua` / `linguo2625469` / `ardeyouxipianyi` / `ithtelab` / `3304711297`）：

| 维度 | 社区现状 | 我们的现状 | 判定 |
|---|---|---|---|
| SSE 缓冲 | 全部逐行读即刻转发，无一聚合 | `bufio.Scanner` 64KB/4MB 逐帧 `streamEmit` | ✅ 一致，无缺陷 |
| usage 阻塞 | 无一为拿 usage 等到 `[DONE]` | `publishUsage` 异步 fire-and-forget | ✅ 一致 |
| `ResponseHeaderTimeout` | 多家显式设置（60s） | **缺失** | ❌ 缺陷一 |
| 禁 h2 | `linguo` 显式置空 `TLSNextProto` | 未处理（宿主默认 transport） | ⚠️ 潜在 |
| 客户端断连传播 | `traework` 已透传 callback context | **`HostCallbackID` 未使用** | ❌ 缺陷二 |
| `stream_options` | 多数注入 | **未注入** | ⚠️ 缺陷三 |
| 强制开思考 | 多家对 deepseek 注入 `effort=high`（比我们更激进） | 未注入；生产由客户端自带 `max` | ✅ 我们更保守 |

**关键反直觉事实**（`dingminhua/dsh-connect-workbuddy` `src/off-thinking.ts` 实测）：
1. `deepseek-v4.1-flash` **拒绝 `reasoning_effort:off`**（HTTP 400 / `code=11133`）；
2. 「不发该字段」= 完全不思考；发任何档位（含 `max`）= 思考。
3. 因此**若目标是降延迟，唯一安全的关思考路径是「完全不发 `reasoning_effort`」**，绝不能发 `off`。

本次实测同账号验证：不带 `reasoning_effort` 时 `reas_chars=0`，带 `max` 时 `reas_chars=350~790` —— **与社区结论完全一致**。

## 五、修复建议（按优先级）

| # | 缺陷 | 建议 | 风险 |
|---|---|---|---|
| P0 | 宿主桥无超时 | 插件侧无法改宿主；建议在插件兜底 client 补 `ResponseHeaderTimeout=60s` + `TLSHandshakeTimeout=10s` + `DialContext` 10s，并置空 `TLSNextProto` | 低；仅兜底路径生效 |
| P1 | `HostCallbackID` 未透传 | 照 `traework` 模式透传，使客户端断连能中止上游读 | 低；纯增量 |
| P2 | 缺 `stream_options.include_usage` | 仅当客户端未显式指定时 `setdefault` 注入 | 低 |
| — | 极端长尾本质 | `reasoning_effort=max` 由客户端控制，插件不应擅自改写（社区中有项目强制 `high`，反而更慢） | — |

## 六、未决与边界

- **未证实**：`Threads=425` 与死流泄漏的因果关系。需在 P1 修复后对照观察线程数。
- **未证伪**：`lat=694166ms` 那一批（2026-11-03 集中出现，同一分钟内多个账号）更可能是当期上游集群异常，不排除与插件无关。
- **已知边界**：宿主 `http_bridge.go` 的 `NewProxyAwareHTTPClient(..., 0)` 是宿主代码，跨项目写入红线内不可改；只能在插件侧做兜底与观测。
