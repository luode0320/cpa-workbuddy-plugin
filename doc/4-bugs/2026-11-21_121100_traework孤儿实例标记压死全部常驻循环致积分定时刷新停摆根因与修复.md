# traework 孤儿实例标记压死全部常驻循环，积分定时刷新静默停摆 14 小时

- 时间：2026-11-21 12:11 发现 / 2026-11-21 13:37 根因锁定并提交修复 / 2026-11-21 14:06 生产热重载生效 / 2026-11-21 14:30 孤儿接管实弹验收通过
- 版本：traework-provider 0.5.57（故障版本）→ 0.5.58（修复版本）
- 环境：生产 45.207.222.65（`cpa-server`），容器 `cli-proxy-api`，管理台 https://cpa.luode.vip/management.html
- 发现渠道：用户提供两张 TraeWork 账号面板截图，报告「定时刷新好像没有生效，有些号没有刷新积分，我们记得是 1 小时一次的是吗？」

## 1. 现象

面板 70 个账号卡片里，前几张（用户417319 / 用户725420 / 用户103388）的快照时间显示 `2026-11-21 12:11:16 ~ 12:11:20`，看起来刚刷新过；向下滚动后大量卡片（用户196904 / 用户382617 等）的快照时间停在 `2026-11-20 23:49:19`，超过 12 小时未更新。

三个反直觉的观察点，是本次定位的关键线索：

| 观察 | 事实 | 说明 |
| --- | --- | --- |
| 面板不是全停 | 前几张卡 12:11 刚更新 | 说明并非「整个插件崩溃」 |
| 面板也不是全活 | 多数卡停在 11-20 23:49 | 时间点统一，像某一轮之后就再没跑过 |
| 用户以为周期是 1 小时 | 代码里没有 1 小时的积分周期 | 口径需要纠正：真实周期 10 分钟 |

## 2. 取证

### 2.1 周期口径：真实是 10 分钟，不是 1 小时

`traework/watchdog.go:39`：

```go
watchdogIntervalDefault time.Duration = 10 * time.Minute
```

`traework/watchdog.go` 的 `watchdogLoop`（:143-205）首轮 `waitHostReadyForWatchdog(15s)` + `watchdogFirstTickDelay()` 抖动后 `runWatchdogTick()`，之后 `time.NewTimer(watchdogIntervalDefault)` 循环，每轮 `flushCounters()` + `runWatchdogTick()`；`runWatchdogTick()`（:105-121）= `hostAuthList()` → 全量 targets → `globalRefresh.EnqueueAll(targets, "watchdog")`。

全插件 grep `time.Hour` 只命中 `session_auth.go`（会话粘性）、`keepalive.go`（保活留窗口）、`auth_delete_test.go`，**traework 目录内不存在任何 1 小时的积分刷新周期**。1 小时量级只出现在 workbuddy（每小时串行扫描）与 coze（1 小时巡检）。用户口中的「1 小时」应是与 4 小时签到/保活槽位记混：

```go
// traework/checkin.go:484
autoCheckinTimes = []int{0, 4, 8, 12, 16, 20}
// traework/keepalive.go:42
keepaliveHours = []int{0, 4, 8, 12, 16, 20}
```

`README.md:63` 已写明：「每日签到 00/04/08/12/16/20（≤5 分钟抖动）；Token 保活共用同一六槽时刻表；**watchdog 每 10 分钟刷新积分并发一次活跃 ping**」。

### 2.2 不是「有些号」，是全部号从 11-20 23:49 起停摆

把容器内 `/CLIProxyAPI/data/traework-credits.json` 拉回本地解析（按 `fetched_at[:16]` 计数）：

- 顶层 `updated_at = 2026-11-20T15:49:20Z`，`accounts` 共 **70** 条；
- `fetched_at` 分布：`2026-11-19T22:37` 2 条、`2026-11-19T22:47` 3 条、`2026-11-20T15:39` 1 条、`2026-11-20T15:49` 4 条、`2026-11-20T15:59` 4 条、**`2026-11-20T23:49` 56 条**；
- 文件 mtime 自 `2026-11-20 23:49` 起 14 小时未再滚动（期间 `workbuddy-credits.json` 持续更新）。

**截图里那几条「很新」的卡，是用户手动点「刷新」的结果**，不是 watchdog 产出：日志 12:11:11~12:11:23 有完整链路 `GET .../panel` 200 34ms → `GET .../accounts` 200 430ms → 连续 6 次 `GET .../credits?auth_index=<hash>`（596/297/333/219/287/319 ms），与截图 12:11:16~12:11:23 的快照时间一一对应。

### 2.4 根因：实例守卫只写标记，不判所有者存活

`traework/instance_guard.go`（修复前）：

```go
instanceGuardOnce sync.Once
instanceGuardID   string

func pluginInstancePath() string {
    return filepath.Join(os.TempDir(), "cpa-traework-provider-instance")
}

func claimPluginInstance() {
    instanceGuardOnce.Do(func() {
        instanceGuardID = strconv.FormatInt(time.Now().UnixNano(), 36) + "-" + strconv.Itoa(os.Getpid())
        _ = os.WriteFile(pluginInstancePath(), []byte(instanceGuardID), 0o644)
    })
}

func pluginInstanceSuperseded() bool {
    claimPluginInstance()
    raw, err := os.ReadFile(pluginInstancePath())
    if err != nil {
        return false // 读不到标记时不阻断循环
    }
    return strings.TrimSpace(string(raw)) != instanceGuardID
}
```

机制拆解：

1. 标记内容 = `<纳秒 36 进制>-<pid>`，判定只看「文本是否等于自己的 ID」，**不看写它的进程是否还活着**；
2. 任何加载过该插件的**短命进程**（`docker exec ... ./CLIProxyAPI --version`、`--help`、任何 import 型 CLI）启动时都会跑 `init()` → `claimPluginInstance()` → 覆写标记，然后自身退出；
3. 留下的孤儿标记让 pid 1 长驻实例的 `pluginInstanceSuperseded()` **从此恒为 true**；
4. 十个 `go xxxLoop()` 在各自下一拍 `retireIfSuperseded(loop)` 命中后 `return` —— 无 supervisor、无重启、无任何宿主 API 能复活。

**生产复现（决定性）**：13:05:58 前标记为 `dn077061ruh9-952`（mtime `2026-11-21 01:01:30`）；执行 `docker exec cli-proxy-api sh -c 'cd /CLIProxyAPI && ./CLIProxyAPI --version'`（仅打印版本 + 打印全部 `plugin registered` 行，其中含 `plugin loaded plugin_id=traework-provider version=0.5.57`）后，13:05:59 标记变为 `dn0mlp9ckt4o-1930`（Base36 解码 `13:05:59.121211`，pid **1930** = 那条短命命令）。workbuddy 标记同步变为 `dn0mlpa0gx1h-1930`。

对照事实：`ls /proc/952` → 进程已不存在；`/proc/1/maps` 中 traework 只有 5 段、单一 inode，全部指向 `traework-provider-v0.5.57.so`；11-20 之后**没有任何 traework 插件加载/热重载日志**。即：毒标记来自容器内其它工具的一次性执行，不是插件世代并存。

### 2.5 为什么 workbuddy 没事

| 插件 | 是否有实例守卫 | watchdog 是否带闸门 | 事故表现 |
| --- | --- | --- | --- |
| traework | 有 `instance_guard.go` | **有**（`watchdog.go:162,195`） | 十个循环全线停摆 |
| workbuddy | 有 `instance_guard.go` | 无（仅 failover probe/reconcile 有） | 积分刷新照常 |
| coze / 其余 11 插件 | 无 | 无 | 不受影响 |

`workbuddy/watchdog.go:158-202` 的 `watchdogLoop` 没有 `retireIfSuperseded`；`coze/` 目录 grep `retireIfSuperseded|instanceGuard` = 0 命中。**守卫铺得最全的那个插件，反而因为判据不完整而全线停摆。**

## 3. 修复（0.5.58）

### 3.1 新增跨平台进程存活探测

`traework/instance_pid_unix.go`（`//go:build !windows`）：

```go
func processAlive(pid int) bool {
    if pid <= 0 {
        return false
    }
    err := syscall.Kill(pid, 0)
    if err == nil {
        return true
    }
    // EPERM 说明进程存在但无权发信号，仍算存活
    return errors.Is(err, syscall.EPERM)
}
```

`traework/instance_pid_windows.go`（`//go:build windows`）：`os.FindProcess` + `proc.Release()`。

### 3.2 孤儿判定：只有**可证明已死**的 pid 才接管

`traework/instance_guard.go` 新增：

```go
func orphanOwnerMarker(owner string) bool {
    owner = strings.TrimSpace(owner)
    if owner == "" {
        return true
    }
    idx := strings.LastIndex(owner, "-")
    if idx < 0 || idx == len(owner)-1 {
        return false
    }
    pid, err := strconv.Atoi(owner[idx+1:])
    if err != nil || pid <= 0 {
        // 解析不出 pid：保留历史「任何非己标记代表更新实例」语义
        return false
    }
    if pid == os.Getpid() {
        return false
    }
    return !processAlive(pid)
}
```

`pluginInstanceSuperseded()` 在 `owner != instanceGuardID` 之后先判 `orphanOwnerMarker(owner)`，为真则改写标记接管并 **放行循环**（`return false`）；`claimPluginInstance()` 接管前打日志 `[traework] taking over orphan instance marker (previous %s no longer alive)`。

### 3.3 首版踩坑：不可解析的标记不能当孤儿

首版把「解析不出 pid」判成 `true`（孤儿），**打挂了既有测试** `traework/probe_guard_test.go:89 TestRunFailoverProbeTickStopsWhenSuperseded`，报 `被取代的实例不得继续探活，实际探测 2 个账号` —— 因为该测试写入的标记文本是 `"newer-instance"`（纯文本无 pid）。这条约束已写进代码注释：**不可解析 ≠ 已死，只能当「未知且更新」**，否则会破坏宿主热重载的去重语义。

### 3.4 测试

`traework/instance_guard_test.go` 新增：

- `backupInstanceMarker(t)`：备份/还原标记，避免污染真实环境；
- `deadPID()`：从 `1<<22` 起递增，找到第一个 `!processAlive` 的 pid；
- `TestPluginInstanceSupersededTakesOverOrphanMarker`：伪造死 pid 标记 → `pluginInstanceSuperseded()` 必须返回 false 且标记被接管为 `instanceGuardID`；
- `TestOrphanOwnerMarkerKeepsUnknownMarkersAuthoritative`：`no-pid-suffix-` / `newer-instance` / `trailing-` / `stamp-abc` 不得判孤儿；空串必须判孤儿；自身 pid 不算孤儿；
- `TestPluginInstanceSupersededDetectsNewOwner` 的新实例标记改为带**存活 pid**（`os.Getpid()`），与孤儿语义区分。

`python scripts/cgo-shim-build.py traework` → build + vet + test 全绿（`ok github.com/luode0320/cpa-workbuddy-plugin/traework ~5.5s`）。

### 4.3 宿主 API 能力边界（本轮实测，供后续排障参考）

| 端点 | 行为 |
| --- | --- |
| `POST .../plugins/<id>/enable` / `disable` | **账号级**（`{"action":"enabled","count":70}`），不是插件级 |
| `PUT .../plugins/<id>/config` | 只触发 config.yaml 重载，**不重载 .so** |
| `POST .../plugins/<id>/reload` / `restart` | 404，不存在 |
| `POST .../plugin-store/<id>/install?version=<同版本>` | `overwritten=true`，字节一致时**不会 hot reload** |
| `DELETE .../plugins/<id>` + 重 install | 有 `plugin loaded` 但 **`init()` 的 `sync.Once` 已执行完，常驻循环不会复活** |

结论：**恢复常驻循环的唯一手段是让 `.so` 字节变化**（发新版本 install 触发 `hot reloaded`）。删标记、`DELETE` + 同版本重装、改 config 全部无效。

## 7. 教训

1. **pid/世代型锁必须能判持有者存活**。只写不验，等于把「偶发短命进程」放大成「永久停摆」；
2. **不可解析的锁内容不能当「已死」**。只能当「未知且更新」，否则破坏热重载去重语义，还会打挂既有测试暴露出来的契约；
3. **常驻循环静默 `return` 是最高危形态**。`doFetchOne` 全链路没有成功/失败日志，导致停摆 14 小时无人发现 —— 后续需要补轮次心跳与结果日志；
4. **容器内禁止跑 `./CLIProxyAPI <任意参数>`**。它会重跑 `init()` 并污染实例标记，属操作红线；
5. **`docker logs | grep -c` 必须带 provider 前缀**。不带 `\[traework\]` 时，workbuddy 的 514 条探活日志会淹没 traework 的沉默，让人误判「探活还在跑」；
6. **workflow_dispatch 发布必须显式带 `allow_partial=true`**。`darwin/arm64` 的 macos-14 runner 偶发拿不到，会把整次 release 拖成 skip，且取消由系统触发而非人为；
7. **「写得最规范」不等于「最安全」**。同一套守卫，traework 铺满十个循环、workbuddy 只铺部分、coze 完全没有 —— 判据不完整时，覆盖率越高伤得越重。
