# traework 积分禁用标记不落盘致 14 个余额 100+ 账号永久孤悬池外（缺陷⑳）

- 发现时间：2026-11-11 00:16（CST）
- 影响版本：traework-provider ≤ 0.5.43
- 修复版本：0.5.44
- 严重级别：P0（账号池静默缩水 27%，直接推高首字延迟与错误率）
- 关联文档：`2026-11-08_210000_traework首字延迟与生成耗时偏高根因分析.md`（同族缺陷第一阶段）

## 1. 现象

生产 CPA（`45.207.222.65`）`/accounts` 在 2026-11-11 00:16:07 显示：总数 41，
`disabled=true` 14 个。这 14 个号的积分余量是 100~190，`credit_tier=normal`、
`cooling_down=false`、`exhausted=false`、`fail_count` 多为 0 —— **有钱、可用、
健康，但没有任何流量**。它们既不出现在候选池，也不会被任何路径自动恢复。

## 2. 取证

### 2.1 磁盘真相（42 个 auth 文件）

`docker cp cli-proxy-api:/CLIProxyAPI/mysqlstore/mysqlstore/auths/. /tmp/auths_probe/`
后逐文件解析：

| 分组 | 数量 | `disabled` | `note` | `low_credit_disable` |
| --- | --- | --- | --- | --- |
| 已恢复正常 | 27 | false | 积分回升启用 · 余NNN | 不存在 |
| 卡死 | 14 | true | **空 / None** | **不存在** |
| 无法解析 | 1 | — | — | — |

关键点：**27 个已恢复账号的 note 完好保留**。这证明宿主没有擦掉 note，
note 属于宿主白名单内的可存活字段；而 14 个卡死号的 note 是空的，
说明它们的停用**从未写过盘**。

### 2.2 日志归因（`docker logs --since 6h`，493,217 行）

8 条禁用记录，全部来自低积分路径：
`3911438854011684` / `3841070106942115` / `129118851563984` /
`2011482758065523` / `4474388807957692` / `1747599967915383` /
`3084606107818668` / `3278120156406128`。

`--since 12h` 再查 `via cpa api|cpa disable api|re-enabled`：27 条命中
**全部**是 `low-credit re-enabled`，且都不带 `via cpa api` 后缀 ——
宿主管理 API 在生产不可达（`errCPAManagementNotConfigured`），
**解禁分支从未对这批号触发过**。

## 3. 根因

`credit_disable.go` 旧实现：

```go
apiErr := setHostAuthDisabled(name, authIndex, true)
if apiErr == nil {
    log.Printf("... disabled via cpa api ...")
    return nil          // ← 标记与 note 从未落盘
}
```

配合宿主行为「重建 auth 文档只保留白名单键
（`type/provider/logo/note/disabled/auth/account`）」，形成闭环失效：

1. 禁用时 API 成功 → 宿主真相源 `disabled=true`，磁盘上零标记；
2. 宿主重建文档 → 即使写了标记也会被剥离；
3. 积分回升时 `gradeCreditsForAuth` 第 100 行 `if !disabled || !ours || ...`
   → `ours=false` → 直接 return，不解禁；
4. `lifecycle.go` 明确「Files disabled without any marker … equally left alone」；
5. `anomaly_purge.go` 只认 `Session expired` 前缀的 note。

**三条恢复路径全部绕开，账号永久孤儿化。**

## 4. 修复（0.5.44）

1. `disableForLowCredits` / `reenableForLowCredits` 一律**先落盘、再打宿主 API**。
   落盘幂等，API 成功与否都不再跳过；写盘失败时仍尝试 API，让路由先挡住消耗。
2. 新增归属第二判据 `lowCreditDisableFromNote`：note 前缀 `积分不足停用` 即认定为
   本机制所禁。note 在宿主白名单内可存活，是标记被丢弃后的唯一线索。
3. `gradeCreditsForAuth` 解除守卫 `!disabled || !ours` 收窄为 `!ours`：
   盘上陈旧 `disabled=false` 不再被当成「已解禁」。
4. `reenableForLowCredits` 归属复核同口径，否则 note-only 文档走不到解禁。
5. 严格保留边界：`manual_disable` / `failover_disable` / `exhausted_disable`
   一律不接管。

## 5. 生产止损（已执行）

备份现场（`ts=20261111_002109`：`traework-failover.json` +
`auths/` 全目录）后，对 14 个号逐个
`PATCH /v0/management/auth-files/status {"disabled": false}`：
**14 成功 0 失败**，`/accounts` `disabled` 由 14 → **0**，51 个账号全部可用。

- `TestLowCreditNoteDoesNotAdoptEnabledDoc`：「积分回升启用」与 lifecycle 的
  「耗尽停用」文案不得被判为归属。

## 7. 设计教训

> 任何插件自有状态一旦写进宿主管理的 auth 文档，就是**临时数据**。
> 宿主会按白名单重建文档，未知键必然蒸发。
> 归属标记必须落在插件自己的 sidecar（`data/traework-*.json`），
> 或在宿主白名单内的字段（note）上做可识别指纹。

同族推论：0.5.43 修的是「池子被一次抽干」，0.5.44 修的是「抽干后无法恢复」。
两版必须同时在线，池子才既有深度、又有自愈能力。
