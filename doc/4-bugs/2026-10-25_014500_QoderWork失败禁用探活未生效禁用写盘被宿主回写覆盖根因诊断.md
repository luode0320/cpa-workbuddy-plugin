# QoderWork 失败禁用探活未生效（禁用写盘被宿主回写覆盖）根因诊断

- 编号：BUG-QODERWORK-FAILOVER-DISABLE-NOT-PERSISTED-20261025
- 发现时间：2026-10-25 01:32（用户判断：「生产有很多失败的账号，但都没有禁用，说明失败禁用探活没有生效」）
- 判定时间：2026-10-25 01:45
- 状态：**已定位根因，未修复**
- 关联：`workbuddy/failover_disable.go`（对照基线，同机制在 workbuddy 生效）、`doc/4-bugs/2026-10-25_011500_QoderWork生产KimiK31Pro测试失败上游后端不可用根因诊断.md`（同期上游降级，是本次大量失败的触发源）

## 1. 现象

生产 qoderwork 有 18 个账号，其中 10 个 `exhausted`、多个持续失败，但 `/accounts` 返回 `disabled=false`（18/18），物理 auth 文件与数据库 `auth_store` 中均无 `failover_disable` 标记。

与此同时日志明确显示机制**在运行**：

```
2026/10/25 01:11:39 [qoderwork] failover disabled account: auth=qoderwork-019fd0a6-...json model=kmodel_latest
2026/10/25 01:12:01 [qoderwork] failover disabled account: auth=qoderwork-01a01535-...json model=gfmodel
2026/10/25 01:14:39 [qoderwork] failover disabled account: auth=qoderwork-01a0b730-...json model=kmodel_latest
...
2026/10/25 01:14:42 [qoderwork] failover state NOT confirmed by host: want_disabled=true auth=qoderwork-01a0b730-...json
```

两小时窗口内 `failover disabled account` 出现 **27 次**，`failover disable skipped` / `failover disable write failed` 均为 **0 次**——写盘函数返回成功，但宿主没有吸收。

## 2. 决定性证据

### 2.1 workbuddy 同机制生效，qoderwork 不生效

| 插件 | DB 中 `failover_disable=true` 的账号数 |
| --- | --- |
| `workbuddy-provider` | **2**（13 个账号中） |
| `qoderwork-provider` | **0**（18 个账号中） |

DB 顶层键对照（同一张 `auth_store` 表）：

```
workbuddy:  ["auth","logo","note","type","account","disabled","provider",
             "failover_disable","failover_disable_at","failover_disable_model"]
qoderwork:  ["auth","logo","note","type","account","disabled","provider"]
```

两插件 `failover_disable.go` 逐函数同构（`carryFailoverKeysIntoMetadata` 的接入点 `main.go` / `oauth.go` 也一一对应），差异不在代码逻辑，而在**写入结果能否存活**。

### 2.2 直接写 spool 后标记消失

在宿主机直接改 spool 文件（`/usr/local/src/cli-proxy-api/mysqlstore/mysqlstore/auths/qoderwork-019fd0a6-....json`）写入 `disabled:true` + `failover_disable:true`，随后：

| 观测 | 结果 |
| --- | --- |
| 静态等待 12 秒（无请求触发） | 标记**存活**（mtime 不变、`failover_disable` 计数=1） |
| 触发一次 `POST /test-active` 后 | 标记**消失**，`disabled` 回到 `false`，文件被重写为 |
| DB `auth_store.content` | 始终 `disabled=false`、**无 `failover_disable` 键** |

重写后的文件内容带 `"note":"CN · 积分未知"`、`failed_count:1`——这是插件 `buildAuthFileJSON` 白名单重建的产物（`authfile.go:209-217` 固定输出 `type/provider/logo/disabled/note/auth/account`，其余键只有 `extra` 显式搬运才保留）。

### 2.3 宿主单向以 DB 为准回写 spool

- `auth_store` 表结构与 `updated_at` 观测：workbuddy 账号的 `updated_at` 每几秒推进，qoderwork 停在 `01:31:04`；DB 与 spool 的 mtime 完全一致 ⇒ spool 由 DB 派生。
- 存在 `cooldown_store` 表，说明宿主有「store 为真相源、spool 为投影」的持久化层。
- 因此**只有进入 `auth_store.content` 的字段才能存活**；插件直写 spool 的字段会在宿主下一次回写时被覆盖。

## 3. 根因

**qoderwork 的 `failover_disable` 三个标记键（`failover_disable` / `failover_disable_model` / `failover_disable_at`）无法进入宿主持久化层，导致写盘结果被宿主以 DB 内容回写覆盖。**

具体断点：

1. 插件 `disableAccountForFailover` 用 `persistAuthDirect`（`os.Rename` 原子替换）直写 spool → **写盘本身成功**（日志 27 次成功、0 次失败）。
2. 宿主 spool 是 `auth_store` 表的投影，宿主按 DB 内容周期性/事件性回写 spool。
3. 插件把标记搬到宿主的唯一通道是 `carryFailoverKeysIntoMetadata` → 写入 `AuthData.Metadata`，靠宿主「吸收 auth 文件后用 Metadata 反向重建」把标记带回 DB。
4. 该通道只在 `handleParseAuth`（宿主 watcher 解析文件时回调）与 `oauth.go` 的授权路径生效。**宿主从 DB 回写 spool 时不走 `handleParseAuth`**，因此插件写进 spool 的标记被直接丢弃，DB 里从未出现这三个键。

对照 workbuddy 能生效，说明该通道在 workbuddy 的调用时序下能被触发（其账号有持续成功请求 → 成功路径写盘 → 宿主吸收 → Metadata 搬运）；而 qoderwork 这些账号正处于全池失败状态，成功路径不触发，搬运通道始终没有被走通的窗口。

## 4. 影响

- 失败禁用机制在 qoderwork 上**实质失效**：坏号不会写盘禁用，宿主持续把请求路由到已知坏号，每次请求都要轮满整池才失败（生产实测单请求轮转 9 个账号）。
- 内存冷却仍在工作（`isAccountCoolingDown` 的阶梯层），但它只对插件内调度生效，**宿主选择器看不见**，所以跨请求/同请求路由仍会打坏号。
- 与「上游降级」叠加时放大症状：整池同时坏 → 每次请求都打满全池 → 上游配额与响应时间双重浪费。

## 5. 修复方向（未实施，需用户裁定）

三个候选方案，风险与改动面递增：

| 方案 | 做法 | 改动面 | 风险 |
| --- | --- | --- | --- |
| A. 禁用改走 `host.auth.save` | 用宿主通道写禁用，让宿主直接落库 | 小（改 `failoverPersistFn`） | 代码注释明确写过「host.auth.save 通道会重新启用账号」，可能反向失效 |
| B. 失败后主动触发一次 parse 回传 | 写盘后调用宿主接口触发 `handleParseAuth`，让 Metadata 搬运生效 | 中 | 依赖宿主是否有该触发入口，需先验证 API |
| C. 改用宿主可见的禁用语义 | 不再自行写盘，改为调宿主的 disable 管理接口 | 中 | 需确认插件 ABI 是否暴露该能力；否则要改宿主 |

**建议 A 先做可行性验证**（最小改动、最快可验证），失败再退 B；C 属跨项目改动，仅在 A/B 均不可行时评估。
